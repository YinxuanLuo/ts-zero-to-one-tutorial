## 第一关 · 概念快问快答（20 题）

判断下面每句话是**对**还是**错**。不要猜，想清楚理由。

1. `let x = 1` 之后，`x` 的类型是字面量 `1`。
2. `interface` 在编译后会变成一个真实的 JavaScript 对象。
3. `any` 可以赋值给任何类型，任何类型也可以赋值给 `any`。
4. `unknown` 类型的值可以直接访问属性，比如 `u.name`。
5. `never` 是所有类型的子类型，可以赋值给任何类型。
6. 开启 `strictNullChecks` 后，`null` 不能赋值给 `string`。
7. `String` 和 `string` 是同一个类型。
8. `const a = [1, 'x']` 之后，`a` 的类型是 `(string | number)[]`。
9. `readonly number[]` 在运行时真的不可修改。
10. `as` 会在运行时做真正的类型转换。
11. TypeScript 的 `private` 成员在运行时是真的私有，外部访问不到。
12. 泛型参数 `T` 在运行时存在，所以可以写 `new T()`。
13. 一个参数更少的函数，可以赋值给一个参数更多的函数类型。
14. 写两个同名的 `interface A { }` 会报"重复定义"错误。
15. 写两个同名的 `type A = { }` 会报"重复定义"错误。
16. 一个返回 `string` 的函数，可以赋值给返回类型是 `void` 的函数类型。
17. `keyof { a: 1; b: 2 }` 的结果是 `'a' | 'b'`。
18. `Object.keys({ a: 1 })` 的返回类型是 `'a'[]`。
19. `enum` 可以被 Node 的原生类型擦除模式直接运行。
20. `Array<string>` 和 `string[]` 是完全等价的写法。

## 第五关 · 项目实战（5 题）

这一关要**真的写代码并跑起来**。每题我都给了验收标准。

**第 1 题 · 类型安全的事件总线**

实现 `createEventBus<Events extends Record<string, unknown>>()`，返回：

- `on<K extends keyof Events>(event: K, handler: (payload: Events[K]) => void): () => void`
- `emit<K extends keyof Events>(event: K, payload: Events[K]): void`

验收：

```ts
type MyEvents = {
  'user:login': { id: string };
  'cart:add': { itemId: string; qty: number };
};

const bus = createEventBus<MyEvents>();
bus.on('user:login', (p) => p.id.toUpperCase());   // p 自动是 { id: string }
bus.emit('cart:add', { itemId: 'a', qty: 1 });
// bus.emit('cart:add', { itemId: 'a' });          // 必须编译报错
// bus.on('nope', () => {});                       // 必须编译报错
```

**第 2 题 · `Result<T, E>` 工具箱**

实现：

- `ok<T>(value: T): Result<T, never>`
- `err<E>(error: E): Result<never, E>`
- `map<T, U, E>(r: Result<T, E>, f: (v: T) => U): Result<U, E>`
- `mapErr<T, E, F>(r: Result<T, E>, f: (e: E) => F): Result<T, F>`
- `unwrapOr<T, E>(r: Result<T, E>, fallback: T): T`

验收：全部方法都要有正确的类型推导（`map` 之后错误类型不变，`mapErr` 之后成功类型不变）。

**第 3 题 · 类型安全的表单校验**

给定：

```ts
type FormSchema = {
  username: string;
  age: number;
  newsletter: boolean;
};

type FormErrors<T> = Partial<Record<keyof T, string>>;
```

实现 `validate<T extends object>(values: T, rules: { [K in keyof T]?: (v: T[K]) => string | null }): FormErrors<T>`。

验收：写规则时 `v` 的类型必须自动对应字段类型（写 `age` 的规则时 `v` 是 `number`）。

**第 4 题 · 给全局加类型（`.d.ts`）**

写一个 `.d.ts`，让下面这段代码能通过类型检查：

```ts
window.__APP_CONFIG__;          // 类型是 { apiUrl: string; debug: boolean }
declare global {
  namespace NodeJS {
    interface ProcessEnv {
      MY_SECRET: string;
    }
  }
}
```

提示：注意 `declare global` 生效需要文件里有 `export {}`。

**第 5 题 · 把一个 JS 模块迁移到 TS**

给定这段 JS：

```js
// utils.js
export function groupBy(items, keyFn) {
  return items.reduce((acc, item) => {
    const key = keyFn(item);
    (acc[key] ||= []).push(item);
    return acc;
  }, {});
}

export function omit(obj, keys) {
  const result = { ...obj };
  for (const key of keys) delete result[key];
  return result;
}
```

要求：

- 改成 `.ts`，**全部加上精确类型**（不要用 `any`）。
- `omit` 的返回类型必须是"去掉了那些键"的类型（用 `Omit` 或泛型实现）。
- 写完后跑 `tsc --noEmit` 必须零错误。

## 第三关答案

### 第 1 题：漏分支

**问题**：`Status` 有三个成员，只处理了两个。
更糟的是：函数的返回类型是 `string`，但走完 `if` 之后会隐式返回 `undefined`。
为什么编译器没报错？因为 `renderStatus` 的**返回类型注解写的是 `string`**……

等等，这里其实**会**报错：

```text
error TS2366: Function lacks ending return statement and return type
  does not include 'undefined'.
```

但如果你**不写返回类型注解**，它就会被推断成 `string | undefined`，**静默通过**。这才是真正的坑。

**修改（一）：让它编译不过，逼你处理**

```ts
function assertNever(value: never): never {
  throw new Error(`分支未穷尽: ${JSON.stringify(value)}`);
}

function renderStatus(s: Status): string {
  switch (s) {
    case 'loading': return '加载中';
    case 'success': return '成功';
    case 'error':   return '失败';
    default:        return assertNever(s);   // 漏了分支这里就报 TS2345
  }
}
```

**修改（二）：如果你坚持用 `if`，至少加上收窄**

```ts
function renderStatus(s: Status): string {
  if (s === 'loading') return '加载中';
  if (s === 'success') return '成功';
  if (s === 'error')   return '失败';
  return assertNever(s);   // 走到这里 s 只能是 never
}
```

**核心教训**：**处理联合类型的 `switch` 一律加 `default: assertNever(x)`。**
这样以后给 `Status` 加成员时，所有处理点会立刻编译报错。

### 第 2 题：`if (name)` 吃掉了空字符串

**问题**：`if (name)` 用的是**真值判断**，它会同时排除 `''`、`0`、`false`、`NaN`。
所以 `greet('')` 会返回"你好，陌生人"，而不是期望的"你好，"。

**修改**：

```ts
function greet(name: string | null | undefined): string {
  if (name != null) {        // 只排除 null 和 undefined
    return `你好，${name}`;
  }
  return '你好，陌生人';
}
```

**核心教训**：真值判断只在"空字符串和 null 等价"时才能用。
否则用 `x != null`（同时排除 `null` 和 `undefined`）或显式比较。

### 第 3 题：`||` 吃掉了 `0`

**问题**：`input.pageSize || 20` 在 `pageSize` 是 `0` 时会返回 `20`。
`0` 是一个**合法的页大小**（甚至可以说"不分页"），被静默替换掉了。

**修改**：

```ts
function getPageSize(input: { pageSize?: number }): number {
  return input.pageSize ?? 20;    // 只有 null/undefined 才用默认值
}
```

**核心教训**：**设默认值一律用 `??`。** 这一条能避免线上事故。

### 第 4 题：`Object.keys` 返回 `string[]`

**问题**：`Object.keys(config)` 的返回类型是 `string[]`，不是 `('host' | 'port')[]`。
所以 `config[key]` 会报：

```text
error TS7053: Element implicitly has an 'any' type because expression of type
  'string' can't be used to index type 'Config'.
```

**修改（方案 A：类型安全的 keys 函数）**：

```ts
function typedKeys<T extends object>(obj: T): (keyof T)[] {
  return Object.keys(obj) as (keyof T)[];
}

const keys = typedKeys(config);      // ('host' | 'port')[]
for (const key of keys) {
  console.log(key, config[key]);     // config[key] 类型是 string | number
}
```

**修改（方案 B：改用 `Object.entries`）**：

```ts
for (const [key, value] of Object.entries(config)) {
  console.log(key, value);           // key: string, value: string | number
}
```

**核心教训**：`Object.keys` 的不精确是 TS 刻意的取舍（第 00 章哲学四）。
需要精确类型时自己包一层 `typedKeys`，并且清楚那里有一个 `as`。

---

### 第 5 题：泛型没有约束

**问题**：`T` 完全无约束，所以 `obj[key]` 报：

```text
error TS7053: Element implicitly has an 'any' type because expression of type
  'string' can't be used to index type 'T'.
```

**修改**：

```ts
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 1, name: 'Tom' };
const name = getProperty(user, 'name');    // string
// getProperty(user, 'nmae');              // ❌ TS2345，拼错立刻报错
```

**核心教训**：**`K extends keyof T` + `T[K]` 是泛型里最实用的组合。**

---

### 第 6 题：类型谓词"承诺过多"

**问题**：这个函数声称"返回 `true` 就一定是 `{ id: number }`"，但实现只检查了"是不是对象"。
`null` 被排除了，但 `{ name: 'x' }`（没有 `id`）或 `{ id: 'string' }` 都会通过检查。

**这是最危险的一类 bug**：编译期完全看不出问题，运行时才炸。

**修改**：

```ts
function isUser(value: unknown): value is { id: number } {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    typeof (value as { id: unknown }).id === 'number'
  );
}
```

**核心教训**：**类型谓词是"承诺"，编译器不会验证你的实现。**
写谓词时，实现必须真的覆盖了目标类型的每一项要求。
这也是为什么真实项目里推荐用 zod / valibot——它们把"校验"和"类型"绑在一起，不会脱节。

---

### 第 7 题：闭包里的收窄失效

**问题**：

```text
error TS18047: 'x' is possibly 'null'.
```

因为 `start` 在嵌套函数里被赋值了（`start = null`），TS 就不再在闭包内对它做收窄。

**修改（方案 A：先存 `const` 快照）**：

```ts
function makeCounter(start: string | null) {
  if (start === null) return () => '';
  const snapshot = start;          // 存成 const，收窄锁死
  return () => {
    return snapshot.toUpperCase();
  };
}
```

**修改（方案 B：如果确实要改，就显式处理）**：

```ts
function makeCounter(start: string | null) {
  if (start !== null) {
    return () => {
      start = null;
      return start?.toUpperCase() ?? '';
    };
  }
  return () => '';
}
```

**核心教训**：**进闭包之前把值存成 `const`**，这是函数式风格受欢迎的原因之一。

---

### 第 8 题：`as` 骗编译器

**问题**：`res.data` 是 `unknown`，这里用 `as` 直接断言成 `{ name: string }`。
**运行时它到底是不是这个形状，`as` 完全不管。**

如果后端返回 `{ name: 123 }`，`name.toUpperCase()` 就会在运行时崩：

```text
TypeError: name.toUpperCase is not a function
```

**修改**：

```ts
function isNamed(value: unknown): value is { name: string } {
  return (
    typeof value === 'object' &&
    value !== null &&
    'name' in value &&
    typeof (value as { name: unknown }).name === 'string'
  );
}

const res: ApiResponse = { data: { name: 'Tom' } };

if (!isNamed(res.data)) {
  throw new Error('响应格式不正确');
}
console.log(res.data.name.toUpperCase());   // 收窄后安全
```

**核心教训**：**`as` 是技术债。** 每写一个 `as` 都该问一句"我为什么能保证它？"。
真实项目用 zod 这类库在边界处做运行时校验。

### 第 9 题：判别属性不是字面量类型

**问题**：`status: string` 是宽类型，**收窄根本不生效**。
所以在 `case 'success'` 里，`s.data` 仍然是 `string[] | undefined`，只能靠 `?.` 兜着，
`case 'error'` 里 `s.error` 也是 `string | undefined`。

**修改**：

```ts
type State =
  | { status: 'idle' }
  | { status: 'success'; data: string[] }
  | { status: 'error'; error: string };

function handle(s: State): string {
  switch (s.status) {
    case 'success':
      return s.data.join(',');     // ✅ 这里 data 一定是 string[]
    case 'error':
      return s.error;              // ✅ 这里 error 一定是 string
    case 'idle':
      return '';
    default:
      return assertNever(s);
  }
}
```

**核心教训**：**判别属性必须是字面量类型。**
一旦写成 `status: string`，判别联合就退化成了普通的宽类型，所有好处全没了。
而且好消息是：**非法状态现在写不出来了**（`{ status: 'success' }` 不带 data 会报 `TS2741`）。

---

### 第 10 题：`T` 只出现一次

**问题**：`T` 只出现在参数位置，返回值是 `void`。
它没有建立任何"输入和输出之间的关系"，**等价于 `any`（但更啰嗦）**——
调用者还要纠结要不要写 `<T>`。

**修改**：

```ts
function log(value: unknown): void {
  console.log(value);
}
```

**核心教训**：**`T` 至少要出现两次（或出现在约束关系里）才有意义。**
判断标准：如果去掉 `T` 换成 `unknown` 之后调用方体验更好，那 `T` 就是多余的。

## 第四关答案

### 1. `interface` 和 `type` 的区别？该用哪个？

**一句话**：能描述对象形状时两者都能用，但 `interface` 支持声明合并、`type` 能描述联合/元组/条件类型。

**要点**：

- `type` 能表示的东西更多：联合 `A | B`、元组 `[A, B]`、原始类型别名、映射类型、条件类型。`interface` 不行。
- `interface` 可以**声明合并**（同名自动合并），这在给第三方库扩展类型时是刚需。`type` 同名会报 `TS2300`。
- `interface extends A, B` 支持多继承；`type` 要用交叉类型 `A & B`。
- 官方说法：`interface` 有类型缓存，超大型项目里交叉类型可能更慢（日常项目无感）。
- **团队规范建议**：默认用 `interface` 描述对象/类的契约；需要联合、元组、工具类型时用 `type`。

### 2. TypeScript 是结构化类型还是名义类型？`private` 为什么会破坏结构化？

**一句话**：基本是结构化（看形状不看名字），但 `private` / `protected` 成员会引入名义性。

**要点**：

- 结构化：`class Point { x = 0; y = 0 }` 可以直接赋值给 `interface Vec2 { x: number; y: number }`，两者毫无继承关系。
- 这是为了描述已有的 JavaScript——JS 本来就是"有属性就能用"的鸭子类型。
- **例外**：如果两个类都有 `private secret`，即使形状一样也不兼容：

  ```text
  error TS2322: Type 'B' is not assignable to type 'A'.
    Types have separate declarations of a private property 'secret'.
  ```

- 原因：`private` 的语义是"这是 A 的内部实现细节"，如果只看形状就兼容，A 的私有细节会通过 B 泄漏出去。

### 3. `any`、`unknown`、`never`、`void` 分别是什么？

**一句话**：`any` 双向黑洞；`unknown` 安全的"我不知道"；`never` 一个值都没有；`void` 返回了但没值。

**要点**：

| 类型 | 含义 | 典型场景 |
|---|---|---|
| `any` | 关闭所有检查，会传染 | 迁移旧 JS 时的临时逃生舱 |
| `unknown` | 什么都不能做，必须先收窄 | 外部数据：`JSON.parse`、`localStorage`、`catch` 变量、接口返回 |
| `never` | 空类型，是所有类型的子类型 | 永不返回的函数、穷尽检查 `assertNever` |
| `void` | 函数没有有意义的返回值 | 事件回调、`forEach` |

- `unknown` 是"有纪律的 any"。**能用 `unknown` 就不要用 `any`。**
- `catch (e)` 里的 `e` 在 `useUnknownInCatchVariables` 下就是 `unknown`。

### 4. TypeScript 的类型在运行时存在吗？

**一句话**：完全不存在，类型是"完全可擦除"的，这也是 TS 零运行时开销的原因。

**要点**：

- 这是官方设计目标之一：`Use a consistent, fully erasable, structural type system`。
- 后果一：**不能 `instanceof` 一个 interface**，也不能做运行时的类型判断。
- 后果二：**不能 `new T()`**，要 `new` 就把构造函数当参数传进来。
- 后果三：**`JSON.parse` 返回 `any`、接口返回的数据不受类型保护**，边界处必须做运行时校验（zod / valibot）。
- 后果四：类型不会让代码变慢——运行时根本没有它。

### 5. 什么是类型收窄？靠哪些手段收窄？

**一句话**：TypeScript 沿控制流分析，把一个变量"现在可能是哪几种类型"逐步缩小；这叫控制流分析。

**要点**：

- 和 Java/C# 不同：TS 里变量的类型**不是固定的**，它跟着 `if` / `switch` 一路变化。
- 主要手段：`typeof`、真值判断、`===` / `!==`、`in`、`instanceof`、`Array.isArray`、`switch` + 字面量、赋值、自定义类型谓词 `x is T`、断言函数 `asserts x is T`。
- 坑一：`typeof null === 'object'`，判对象时要加 `x !== null`。
- 坑二：`if (x)` 会同时排除 `''` / `0` / `false`。
- 坑三：变量在嵌套函数里被赋值过，闭包内的收窄会失效（`TS18047`）。

### 6. 什么是判别联合？为什么比"宽类型 + 可选字段"好？

**一句话**：把"多种情况"建模成几个互相排斥的精确形状，用一个字面量字段区分。

**要点**：

- 对比：

  ```ts
  // ❌ 非法状态可以被表示
  interface State { loading?: boolean; data?: User; error?: string }

  // ✅ 非法状态写不出来
  type State =
    | { status: 'idle' }
    | { status: 'loading' }
    | { status: 'success'; data: User }
    | { status: 'error'; error: string };
  ```

- 三个好处：进 `case 'success'` 后 `state.data` 直接可用（不需要 `?.` / `!`）；漏分支会编译报错；加新状态时所有处理点自动报错。
- 判别属性**必须是字面量类型**，写成 `status: string` 就完全失效。
- 这是"让非法状态无法表示"（make illegal states unrepresentable）最直接的落地。
- 实战场景：Redux action、API 响应、表单状态机。

### 7. 泛型的本质是什么？为什么"`T` 只出现一次就等于白写"？

**一句话**：泛型不是"万能类型"，它是**声明类型之间的关系**；只出现一次的 `T` 没有建立任何关系。

**要点**：

- `function identity<T>(x: T): T` 的价值不是"能接受任何类型"（`any` 也能），
  而是"**输出类型必须和输入类型相同**"——这个关系 `any` 表达不了。
- `function pair<T>(a: T, b: T)` 能拒绝 `pair(1, 'a')`，这就是关系在起作用。
- 只出现一次的 `T`（如 `function log<T>(v: T): void`）等价于 `unknown`，还让调用者多一份心智负担。
- 经验值：一个函数超过 3 个类型参数，通常说明设计该拆了。

### 8. `T extends U` 里的 `extends` 和类继承的 `extends` 是一回事吗？

**一句话**：不是。泛型里的 `extends` 意思是"必须能赋值给"，是约束，跟继承无关。

**要点**：

- 准确含义：`T extends U` 表示"`T` 的每一个可能取值，都必须能赋值给 `U`"。
- 因为 TS 是结构化类型，所以"能赋值给"看的是形状：

  ```ts
  function logX<T extends { x: number }>(p: T) {}
  logX({ x: 1, y: 2 });   // ✅ 对象字面量也行，没有任何继承关系
  ```

- 为什么需要约束：无约束的 `T` 可以是任何东西，所以"什么属性都不敢让你访问"（`TS2339`）。
- 黄金组合：`K extends keyof T` 配合 `T[K]`，这是所有类型安全取值函数的基础。

### 9. `keyof T`、`typeof x`、`T[K]` 分别是什么？

**一句话**：`keyof` 取键的联合，类型位置的 `typeof` 把值变成类型，`T[K]` 取属性类型。

**要点**：

- `keyof { a: 1; b: 2 }` → `'a' | 'b'`（列出所有列名）。
- **类型位置的 `typeof`** 和值位置的 `typeof`（JS 运算符）是两个东西：
  `type User = typeof user` 是把一个**值**变成**类型**（拍张照片存成图纸）。
  它只能用在"有名字的值"上。
- `type User = { id: number; name: string }`：
  `User['id']` → `number`，`User['id' | 'name']` → `number | string`，
  `User[keyof User]` → `number | string`。
- 组合用法（最常用）：

  ```ts
  function get<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
  }
  ```

- `as const` 配合 `typeof` 的经典套路：`const COLORS = ['red','green'] as const; type Color = typeof COLORS[number];`

### 10. 什么是分布式条件类型？为什么 `Exclude` 依赖它？

**一句话**：当条件类型的检查对象是**裸类型参数**且传入联合类型时，TS 会对每个成员分别求值再把结果联合起来。

**要点**：

- ```ts
  type MyExclude<T, U> = T extends U ? never : T;
  type Result = MyExclude<'a' | 'b' | 'c', 'a'>;
  // 分发过程：
  //   'a' extends 'a' ? never : 'a'  → never
  //   'b' extends 'a' ? never : 'b'  → 'b'
  //   'c' extends 'a' ? never : 'c'  → 'c'
  // 合并：never | 'b' | 'c' = 'b' | 'c'
  ```
- `Exclude` 就是靠这个分发实现的，`Extract` 同理。
- **阻止分发**：把类型参数包进元组，让它不再是"裸"的：

  ```ts
  type NoDistribute<T, U> = [T] extends [U] ? 'yes' : 'no';
  type R = NoDistribute<'a' | 'b', 'a'>;   // 'no'（整体判断，不分发）
  ```

- 另一个阻止分发的办法是加 `& {}` 或者用 `T & unknown`。

### 11. `infer` 是干什么的？写出 `ReturnType` 和"提取 Promise 内层类型"

**一句话**：`infer` 在条件类型里"就地声明一个待推断的类型变量"，把匹配到的部分取出来。

**要点**：

```ts
// ReturnType
type MyReturnType<T> = T extends (...args: never[]) => infer R ? R : never;

// 提取 Promise 内层类型
type Unwrap<T> = T extends Promise<infer U> ? U : T;

// 递归版（Awaited 的思路）
type DeepUnwrap<T> = T extends Promise<infer U> ? DeepUnwrap<U> : T;

type A = Unwrap<Promise<number>>;         // number
type B = DeepUnwrap<Promise<Promise<string>>>;  // string
```

- 注意事项：`infer` 只能出现在条件类型的 `extends` 右侧。
- `infer` 可以用在多个位置（如 `Parameters`：`T extends (...args: infer P) => unknown ? P : never`）。
- TS 4.7 起支持 `infer U extends string` 这种带约束的写法。

### 12. `satisfies` 和 `as`、和类型注解有什么区别？

**一句话**：`satisfies` 做**检查**但不改变推断结果；`as` 是**断言**（可能骗编译器）；类型注解会**放宽**推断。

**要点**：

```ts
type Config = Record<string, string | string[]>;

// ① 类型注解：值被放宽成 Config，key 信息丢失
const a: Config = { home: '/', about: '/about' };
a.hom;                  // ✅ 不报错（因为索引签名），运行时是 undefined

// ② as：不做检查，直接断言，可能骗编译器
const b = { home: '/', nope: 123 } as Config;   // ✅ 悄悄通过

// ③ satisfies：检查通过，同时保留最窄的推断
const c = { home: '/', about: '/about' } satisfies Config;
// c 的类型是 { home: string; about: string }
c.hom;                  // ❌ TS2339 报错！拼错立刻发现
```

- `satisfies` 的核心价值：**"既要类型检查，又要保留精确推断"**。
- 典型场景：路由表、主题配置、i18n 字典、常量对象。
- 记忆口诀：注解是"套上外套"，`as` 是"我说了算"，`satisfies` 是"体检但不换衣服"。

### 13. Vite / esbuild 会做类型检查吗？

**一句话**：不会。它们只做类型擦除（transpile），不做类型检查。

**要点**：

- 现代构建工具用 esbuild / swc / babel / rolldown，它们为了速度**只把类型语法删掉**，
  完全不理解类型对不对。
- 所以 `npm run dev` 没报错，**不代表类型是对的**。
- 后果：CI 里必须单独跑 `tsc --noEmit`：

  ```json
  {
    "scripts": {
      "dev": "vite",
      "build": "tsc --noEmit && vite build",
      "typecheck": "tsc --noEmit"
    }
  }
  ```

- 这也解释了 TS 7.0 为什么用 Go 重写编译器：既然 `tsc` 的主要职责变成了"当检查器"，
  那它的速度就是整个 CI 的瓶颈。
- 补充：`isolatedModules` / `verbatimModuleSyntax` 就是用来保证"每个文件都能被独立擦除"的开关。

### 14. `strict` 都打开了哪些开关？

**一句话**：`strict` 是一个总开关，在 TS 5.9 里包含 9 个子开关，核心是 `strictNullChecks`。

**要点**：

| 开关 | 防住什么 |
|---|---|
| `strictNullChecks` | ★ `null` / `undefined` 悄悄流进任何变量（Tony Hoare 的"十亿美元错误"） |
| `noImplicitAny` | 参数没写类型导致整个函数变成 `any` 黑洞 |
| `strictFunctionTypes` | 回调参数类型写窄/写宽导致运行时类型错配（函数参数按逆变检查） |
| `strictBindCallApply` | `bind` / `call` / `apply` 传错参数 |
| `strictPropertyInitialization` | 类属性声明了但构造函数里没赋值（`TS2564`） |
| `noImplicitThis` | `this` 隐式变成 `any` |
| `useUnknownInCatchVariables` | `catch (e)` 里 `e` 被当成 `any` 随便用 |
| `alwaysStrict` | 产物里不生成 `"use strict"` |
| `strictBuiltinIteratorReturn`（5.6 新增） | 内置迭代器（如 `Map.prototype.values()`）的 `next().value` 类型不准 |

**建议**：新项目**永远开 `strict: true`**。老项目迁移时可以先关几个，但要列进技术债清单。

### 15. TypeScript 的类型系统是"健全（sound）"的吗？

**一句话**：**不是**，而且这是刻意的——官方设计目标里明确写了"不追求健全，而是在正确性和生产力之间取平衡"。

**要点**：

两个证据：

1. **数组协变**：

   ```ts
   const strs: string[] = ['a'];
   const mixed: (string | number)[] = strs;   // ✅ 编译通过
   mixed.push(123);                            // ✅ 编译通过
   const s: string = strs[0];                  // ✅ 编译通过，但运行时这里有可能是 123
   ```

2. **`any` 和 `as`**：

   ```ts
   const n = 'hello' as unknown as number;
   n.toFixed(2);   // ✅ 编译通过，运行时 TypeError
   ```

其他例子：`Object.keys` 返回 `string[]`；`JSON.parse` 返回 `any`。

**为什么 TS 团队不修**：

- 官方非目标原文：`Apply a sound or "provably correct" type system. Instead, strike a balance between correctness and productivity.`
- 健全的代价是"难写"——Java 的泛型、Kotlin 的 `in`/`out` 型变标注都是例子。
- TS 的首要任务是**描述已有的海量 JavaScript 代码**，而不是发明一门新语言去限制它。
- **实践结论**：把 TS 当成"意图说明 + 廉价的第一道防线"，不要当成安全保证。
  外部数据一律做运行时校验。

## 第五关参考答案

### 第 1 题 · 类型安全的事件总线

```ts
type Handler<P> = (payload: P) => void;

interface EventBus<Events extends Record<string, unknown>> {
  on<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void;
  emit<K extends keyof Events>(event: K, payload: Events[K]): void;
}

function createEventBus<Events extends Record<string, unknown>>(): EventBus<Events> {
  // 内部存储必须放宽成 unknown 的映射，因为不同事件负载类型不同
  const handlers = new Map<keyof Events, Set<Handler<never>>>();

  function on<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void {
    let set = handlers.get(event);
    if (!set) {
      set = new Set();
      handlers.set(event, set);
    }
    set.add(handler as Handler<never>);

    // 返回取消订阅函数
    return () => {
      set?.delete(handler as Handler<never>);
    };
  }

  function emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    const set = handlers.get(event);
    if (!set) return;
    for (const handler of set) {
      (handler as Handler<Events[K]>)(payload);
    }
  }

  return { on, emit };
}

// ---- 验证 ----
type MyEvents = {
  'user:login': { id: string };
  'cart:add': { itemId: string; qty: number };
};

const bus = createEventBus<MyEvents>();

const off = bus.on('user:login', (p) => {
  console.log('登录:', p.id.toUpperCase());   // p 自动是 { id: string }
});
bus.emit('user:login', { id: 'u1' });
off();
bus.emit('user:login', { id: 'u2' });          // 已经取消订阅，不输出

bus.on('cart:add', (p) => console.log('加购:', p.itemId, 'x', p.qty));
bus.emit('cart:add', { itemId: 'sku-1', qty: 2 });
```

**验收要点**：`bus.emit('cart:add', { itemId: 'a' })` 必须报 `TS2345`（缺 `qty`）；
`bus.on('nope', ...)` 必须报 `TS2345`。
如果不需要取消订阅，把 `on` 的返回值改成 `void`，内部那个 `as Handler<never>` 的强转仍然需要——
这是"用泛型做异构容器"时几乎躲不掉的一处妥协，**要在注释里写清楚为什么**。

### 第 2 题 · `Result<T, E>` 工具箱

```ts
type Result<T, E> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: E };

function ok<T>(value: T): Result<T, never> {
  return { ok: true, value };
}

function err<E>(error: E): Result<never, E> {
  return { ok: false, error };
}

function map<T, U, E>(r: Result<T, E>, f: (v: T) => U): Result<U, E> {
  return r.ok ? ok(f(r.value)) : r;   // 失败分支原样传下去，E 不变
}

function mapErr<T, E, F>(r: Result<T, E>, f: (e: E) => F): Result<T, F> {
  return r.ok ? r : err(f(r.error));  // 成功分支原样传下去，T 不变
}

function unwrapOr<T, E>(r: Result<T, E>, fallback: T): T {
  return r.ok ? r.value : fallback;
}

// ---- 验证 ----
const a = map(ok(2), (n) => n * 2);              // Result<number, never>
const b = map(err('boom'), (n: number) => n * 2); // Result<number, string>
console.log(unwrapOr(a, 0), unwrapOr(b, -1));

const c = mapErr(b, (e) => ({ message: e, code: 500 }));
// c 的类型是 Result<number, { message: string; code: number }>
console.log(c.ok ? c.value : c.error.code);
```

**验收要点**：`map` 之后 `E` 必须保持原样；`mapErr` 之后 `T` 必须保持原样。
关键在于 `ok(...)` 返回 `Result<T, never>`，而 `never` 和任何 `E` 组合都不污染联合类型。

### 第 3 题 · 类型安全的表单校验

```ts
type FormSchema = {
  username: string;
  age: number;
  newsletter: boolean;
};

type FormErrors<T> = Partial<Record<keyof T, string>>;

type Rules<T> = { [K in keyof T]?: (v: T[K]) => string | null };

function validate<T extends object>(values: T, rules: Rules<T>): FormErrors<T> {
  const errors: FormErrors<T> = {};

  for (const key of Object.keys(rules) as (keyof T)[]) {
    const rule = rules[key];
    if (!rule) continue;
    // rule 的类型是 ((v: T[keyof T]) => string | null) | undefined
    const fn = rule as (v: T[keyof T]) => string | null;
    const message = fn(values[key]);
    if (message !== null) {
      errors[key] = message;      // FormErrors<T> 的索引赋值在这里是合法的
    }
  }

  return errors;
}

// ---- 验证 ----
const values = { username: 'ab', age: 12, newsletter: false };

const errors = validate(values, {
  username: (v) => (v.length < 3 ? '用户名至少 3 位' : null),  // v 是 string
  age: (v) => (v < 18 ? '必须年满 18 岁' : null),              // v 是 number
  // age: (v) => v.length,                                     // ❌ number 没有 length
  // nope: (v) => null,                                        // ❌ 不存在的字段
});

console.log(errors);   // { username: '用户名至少 3 位', age: '必须年满 18 岁' }
```

**验收要点**：写 `age` 的规则时 `v` 自动是 `number`；写不存在的字段 `nope` 必须报错。
注意 `validate` 内部有 2 处 `as`——这是"遍历泛型对象的键"时的常见妥协。
**重点不是消灭它们，而是把它们关在一个小函数里并写清楚理由。**

### 第 4 题 · 给全局加类型

新建 `global.d.ts`：

```ts
// 这两行让 TypeScript 把本文件当成"模块"，从而允许 declare global
export {};

declare global {
  interface Window {
    __APP_CONFIG__: {
      apiUrl: string;
      debug: boolean;
    };
  }

  namespace NodeJS {
    interface ProcessEnv {
      MY_SECRET: string;
    }
  }
}
```

使用：

```ts
// 注意：lib 里要有 DOM，或者安装 @types/node 的 web-globals
window.__APP_CONFIG__.apiUrl.toUpperCase();
window.__APP_CONFIG__.debug = true;

const secret: string = process.env.MY_SECRET;
```

**关键点（也是面试考点）**：

1. **`declare global` 只能写在"模块"里**。如果文件里没有任何 `import` / `export`，
   它会被当成全局脚本，此时 `declare global` 会报
   `TS2669: Augmentations for the global scope can only be directly nested in external modules`。
   加一行 `export {}` 就能把文件变成模块。
2. 这里用的是**声明合并**：`interface Window` 和 lib.dom 里已有的 `Window` 合并，
   而不是覆盖它。这正是第 07 章讲的"声明合并"的实际用途。
3. 通过 `ProcessEnv` 扩展环境变量类型，是 Node 项目里最常见的 `declare global` 用途。

### 第 5 题 · 迁移 JS 模块到 TS

```ts
// utils.ts

/**
 * 按 keyFn 的返回值分组。
 *
 * 泛型设计说明：
 * - T：元素类型
 * - K：分组键类型（必须能当对象键，所以约束成 string | number | symbol）
 * 返回类型用 Record<K, T[]>，调用方拿到后能精确知道键和值的类型。
 */
export function groupBy<T, K extends PropertyKey>(
  items: readonly T[],
  keyFn: (item: T) => K,
): Record<K, T[]> {
  const result = {} as Record<K, T[]>;
  for (const item of items) {
    const key = keyFn(item);
    const bucket = result[key];
    if (bucket) {
      bucket.push(item);
    } else {
      result[key] = [item];
    }
  }
  return result;
}

/**
 * 去掉指定的键，返回类型精确到"剩下的键"。
 *
 * 实现说明：这里必须有一处 as，因为 TypeScript 无法在运行时
 * 证明 delete 之后对象的形状——这是"类型系统不健全"的一个具体体现。
 */
export function omit<T extends object, K extends keyof T>(
  obj: T,
  keys: readonly K[],
): Omit<T, K> {
  // 第一处 as：把泛型对象看成"字符串键的字典"，才能安全地 delete
  const result = { ...obj } as Record<string, unknown>;
  for (const key of keys) {
    delete result[key as string];
  }
  return result as Omit<T, K>;
}

// ---- 验证 ----
interface Person {
  name: string;
  age: number;
  city: string;
}

const people: Person[] = [
  { name: 'Tom', age: 18, city: '北京' },
  { name: 'Jerry', age: 18, city: '上海' },
  { name: 'Spike', age: 20, city: '北京' },
];

// groupBy：返回类型是 Record<number, Person[]>
const byAge = groupBy(people, (p) => p.age);
console.log('按年龄分组:', Object.keys(byAge), byAge[18]?.map((p) => p.name));

// 也可以按字符串键分组，返回 Record<string, Person[]>
const byCity = groupBy(people, (p) => p.city);
console.log('按城市分组:', byCity['北京']?.map((p) => p.name));

// omit：返回类型是 Omit<Person, 'city'>
const withoutCity = omit(people[0]!, ['city']);
console.log('去掉 city 后:', withoutCity);
// console.log(withoutCity.city);   // ❌ TS2339：city 已经被去掉了
```

**验收要点**：

- `omit` 的返回类型必须是 `Omit<T, K>`，所以 `withoutCity.city` 要报 `TS2339`。
- `groupBy` 的返回类型必须是 `Record<K, T[]>`，且 `K` 要从 `keyFn` 的返回值推断出来。
- 不能用 `any`。有 `as` 的地方要**写注释说明为什么必须在这里**。

**这题的深层意义**：它同时用到了泛型、约束、索引访问、`keyof`、内置工具类型，
以及"类型系统不健全，所以边界处总要有一处断言"这个第 00 章的哲学。
**你能写出并解释清楚这 3 个 `as`，就说明你真的理解 TypeScript 了。**

# 结语：如果你都做完了

那么你现在应该能做到：

- 看懂任何 `tsconfig.json`，知道每行在干什么。
- 拿到一个业务需求，第一反应是"这个状态该用判别联合建模"。
- 看到 `any` 会本能地不舒服，并知道该换成 `unknown` 还是泛型。
- 看到 `switch` 联合类型会自觉地写 `default: assertNever(x)`。
- 知道类型的边界在哪里——哪些错误它替你挡住，哪些必须靠运行时校验。
- 面试里被问到任何一题，都能说出"是什么 + 为什么这么设计 + 什么时候不该用"。

**下一步建议：**

1. 把 `examples/project/` 那个小项目自己重写一遍，不看答案。
2. 找一个你写过的 JS 项目，从最外层的 API 层开始加类型。
3. 学 **zod**（或 valibot），把"运行时校验"和"类型"接起来。
4. 学你框架的类型：React 的 `PropsWithChildren` / `ComponentProps` / 泛型组件。
5. 面试前一晚看 [第 11 章 面试速查表](11-面试速查表.md)。

**最后一句：**

> TypeScript 的难点从来不是语法，而是**"什么时候该用什么建模"**。
> 而这个能力，只能靠在真实项目里反复做判断练出来。
> 你现在已经有全部工具了，接下来去用它。
