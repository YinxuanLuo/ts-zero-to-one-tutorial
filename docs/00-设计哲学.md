# 第 00 章 · 设计哲学：TypeScript 到底是个什么东西

> 本章**一个语法都不教**。
> 但读完它，后面每一章的"为什么必须这么写"你都能自己想出来。

---

## 0.1 先问你一个问题

假设你是一个从没碰过 TypeScript 的 JS 工程师，我给你看这段代码：

```ts
interface User {
  name: string;
}

if (something instanceof User) {
  // ...
}
```

编译器报错：

```text
error TS2693: 'User' only refers to a type, but is being used as a value here.
```

你心里大概会想："**User 怎么就不是值了？它明明就在那儿写着啊。**"

这个"明明在那儿写着"，就是所有 TS 新手困惑的根源。
这一章要干的事，就是把这个困惑一次性连根拔掉。

而拔掉它的钥匙，不是语法，是**设计哲学**。

---

## 0.2 JavaScript 的出身：一门"来不及小心"的语言

要理解 TS 为什么长成今天这样，得先知道它要描述的那个东西——JavaScript——是怎么来的。

1995 年 4 月，**Brendan Eich** 加入 Netscape。
他的任务本来是给浏览器做一个 Scheme 方言（一种函数式语言）。
结果公司跟 Sun 谈了 Java 的合作，市场部门要求"这门脚本语言必须长得像 Java"。
于是他要在**大约 10 天**里，把一门语言从零做出来。

10 天。

这个出身解释了很多你今天觉得"莫名其妙"的设计：

| 现象 | 原因 |
|---|---|
| `typeof null === 'object'` | 用类型标签位实现的，`000` 表示对象；`null` 是空指针，全是 `0`，撞上了同一个标签。这是个 bug，但修它会破坏已有网页，所以永远留着。 |
| 既有 `null` 又有 `undefined` | `undefined` 是后来补的，作为 `null` 的一种"拷贝"。两个都留下了。 |
| `[] + {}` 得到 `"[object Object]"` | 隐式类型转换规则为了"宽容"而设计，没时间做严格推导。 |
| `var` 变量提升的怪行为 | 实现简单优先。 |

**核心结论：JavaScript 的第一设计目标是"宽容"和"能用"，不是"严谨"。**

它把大量的错误推迟到了**运行时**：

```js
function greet(user) {
  return '你好，' + user.name;
}

greet();   // 不报错，一直跑到 user.name 才炸
// TypeError: Cannot read properties of undefined (reading 'name')
```

这就是 JS 的哲学：**先跑起来，出事了再说。**

对小脚本，这个哲学是对的。它让 JS 统治了浏览器。

---

## 0.3 但是，规模变了

JS 后来去做了一件它从没被设计过的事：**写大型应用**。

- 2009 年 Node.js 出现，JS 上了服务端。
- 2010 年代，前端变成几千个文件、几十万行代码的工程。
- 一个项目里，可能有 50 个人同时在改同一份代码。

这时"宽容"就变成灾难了。

想象你重构了一个函数，把某个参数从 `number` 改成了 `string`。
在 JS 里，你没有任何办法知道**还有谁在用它**。
你只能靠全局搜索、靠单元测试覆盖率、靠运气。

于是错误发生的时间被推迟到了**最贵的时候**：

```
写代码（0 分钟）→ 提交（1 小时）→ 测试（1 天）→ 上线（1 周）→ 用户发现（谁也不知道）
     ↑ 在这里发现错误，成本几乎为零
                                                        ↑ 在这里发现错误，成本最高
```

**TypeScript 要解决的真正问题，不是"防 bug"，而是"把发现问题的时间往前挪"。**

而且它挪得极其激进——挪到了你**还没写完这行代码**的时候。

## 0.4 TypeScript 的官方设计目标

下面这些不是我的总结，是 TypeScript 官方的 [Design Goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals) 原文。
我把每条都翻译成人话，因为你后面所有"为什么它不这么设计"的疑问，答案都在这里。

### 11 条目标（Goals）

| # | 原文 | 人话 |
|---|---|---|
| 1 | Statically identify constructs that are likely to be errors | **在你敲代码时就找出"很可能写错了"的地方** |
| 2 | Provide a structuring mechanism for larger pieces of code | **给大代码库一个结构化的办法** |
| 3 | Impose no runtime overhead on emitted programs | **编译出来的代码不许变慢** |
| 4 | Emit clean, idiomatic, recognizable JavaScript code | **输出的 JS 要干净、地道、一眼认得出** |
| 5 | Produce a language that is composable and easy to reason about | **要可组合、好推理** |
| 6 | Align with current and future ECMAScript proposals | **紧跟 ECMAScript 标准** |
| 7 | Preserve runtime behavior of all JavaScript code | **不许改变任何 JS 代码的运行时行为** |
| 8 | Avoid adding expression-level syntax | **不发明新的表达式语法** |
| 9 | Use a consistent, **fully erasable**, **structural** type system | **类型系统必须：一致、完全可擦除、结构化** |
| 10 | Be a cross-platform development tool | **跨平台** |
| 11 | Do not cause substantial breaking changes from TypeScript 1.0 | **不做破坏性变更** |

### 7 条非目标（Non-goals）—— 这部分更重要

知道自己**不做什么**，比知道自己做什么更能说明一个东西的本质。

| # | 原文 | 人话 |
|---|---|---|
| 1 | Exactly mimic the design of existing languages | **不照抄 Java / C# 的类型系统** |
| 2 | Aggressively optimize the runtime performance of programs | **不负责让你的 JS 跑得更快** |
| 3 | **Apply a sound or "provably correct" type system** | **不追求数学上"绝对健全"的类型系统** |
| 4 | Provide an end-to-end build pipeline | **不做构建工具**（所以有 Vite / esbuild / webpack） |
| 5 | **Add or rely on run-time type information**, or emit different code based on the results of the type system | **运行时不存在任何类型信息**；类型不能影响产物长什么样 |
| 6 | Provide additional runtime functionality or libraries | **不加运行时功能**（没有 `TS.sort()` 这种东西） |
| 7 | Introduce behaviour that is likely to surprise users | **不搞出人意料的行为** |

现在，**这 18 条能推出四条哲学，而这四条能解释你未来遇到的所有 TS 怪现象。**

## 0.5 哲学一：类型是"建筑图纸"，不是"建筑材料"

> 对应目标 3、4、7、9，非目标 5、6

### 类比

盖房子有两样东西：

- **图纸**：上面画着"这里是承重墙，厚 24cm"。
- **砖头水泥**：真正撑起房子的东西。

图纸能决定工人怎么砌墙。但**你住进去之后，是摸不到"承重墙"这三个字的**——图纸在开工前就被收走了。

TypeScript 的类型就是这个图纸。

### 证据

写一个 TS 文件：

```ts
type Greeting = `你好, ${string}`;

function greet(name: string): Greeting {
  return `你好, ${name}`;
}

console.log(greet('TypeScript'));
```

`tsc` 编译出来的 JS：

```js
function greet(name) {
  return `你好, ${name}`;
}
console.log(greet('TypeScript'));
```

**注意看：`type Greeting` 整行消失了，`: string` 消失了，`: Greeting` 消失了。**

这就是官方说的 **fully erasable（完全可擦除）**。

甚至不需要 `tsc`——你的 Node 就能干这事：

```bash
node 01-心智模型.ts
# 你好, TypeScript
```

Node 直接把类型"撕掉"然后就跑了，压根没管类型对不对。

### 这个哲学带来的三个直接后果

**后果 1：类型不会让代码变慢。** 因为运行时根本没有类型这回事。
（对比 Java：泛型也是擦除的，但 Java 有反射、有 `instanceof`、有大量运行时类型元数据。TS 是**全擦除**。）

**后果 2：类型不能用来做运行时判断。**

```ts
interface User { name: string }

// ❌ 编译不过
if (x instanceof User) {}
```

错误：

```text
error TS2693: 'User' only refers to a type, but is being used as a value here.
```

原因很直白：`User` 这张图纸在开工前就被收走了，运行时没有它，`instanceof` 拿什么比？

**后果 3：类型不可能校验运行时数据。**

```ts
interface ApiUser {
  id: number;
  name: string;
}

// 你写了类型，但这个类型对 res 的内容毫无约束力
const res = await fetch('/api/user');
const user = (await res.json()) as ApiUser;

console.log(user.name.toUpperCase());
```

如果后端挂了，返回 `{}`，那 `user.name` 就是 `undefined`，`.toUpperCase()` 直接崩。

**编译器不会拦你，因为编译的时候 `res.json()` 返回什么，它根本不知道。**

> 这是新手最大的幻觉："**我写了类型，所以数据是安全的。**"
> 真相是：**类型只约束你自己的代码，不约束外面的世界。**
> 外面的世界要用运行时校验库（zod / valibot / arktype）去挡。这个坑我们在第 09 章填。

**一句话记住它：类型活在"写代码的那一刻"，代码跑起来之后它就没了。**

## 0.6 哲学二：两个世界（Type Space 与 Value Space）★

> 这是整份教程最重要的一个心智模型。
> 学会它，你至少能省下 10 小时的困惑。

### 类比

想象一家剧院。剧院里有两个地方：

- **剧本**：写着"角色张三，男，30 岁，暴脾气"。
- **舞台**：真正站着一个演员，他会出汗、会忘词、会饿。

剧本上说"张三是个暴脾气"——这句话能**指导**演员怎么演。
但你没法把"张三是个暴脾气"这行字推上舞台去领盒饭。

**剧本是类型空间，舞台是值空间。**

### 规则

TypeScript 里，每一段代码要么活在**值空间**（运行时真实存在的），要么活在**类型空间**（只在编译期存在的），要么两边都活。

| 代码 | 值空间有吗？ | 类型空间有吗？ |
|---|---|---|
| `const n = 1` | 有，一个数字 `1` | 有，类型是字面量 `1` |
| `type Foo = { a: string }` | **没有** | 有 |
| `interface Foo { a: string }` | **没有** | 有 |
| `class Foo {}` | 有，一个构造函数 | 有，实例类型 `Foo` |
| `enum Foo {}` | 有，一个对象 | 有 |
| `function f() {}` | 有 | 有（但要写 `typeof f` 才能取到） |
| `declare const x: number` | **没有**（只是告诉编译器"有这么个东西"） | 有 |
| `<T>`（泛型参数） | **没有** | 有 |

### 两个世界的"传送门"：`typeof`

`typeof` 是你最容易懵的地方，因为它**在两个世界里意思不一样**。

```ts
const user = { name: 'Tom' };

// 在【值空间】：typeof 是 JS 的运算符，返回一个字符串
const t = typeof user;
//    ^? t 的类型是 string，值是 "object"

// 在【类型空间】：typeof 是"类型查询"，返回这个值的类型
type User = typeof user;
//   ^? User 就是 { name: string }
```

同一个词，位置不同，含义完全不同。
TS 的编译器靠"你现在在类型位置还是值位置"来决定用哪个意思。

同理还有 `as`：

```ts
const a = someValue as string;
```

`as` **只在类型空间做断言，运行时一行代码都不生成。**

### 用这个模型解释谜题

回到 0.1 节那个报错。现在你应该能自己解释了：

```ts
interface User { name: string }
if (x instanceof User) {}   // TS2693
```

`interface` 只活在类型空间，而 `instanceof` 是值空间的运算符。
你拿着剧本上的角色名，去舞台上找这个人——当然找不到。

反过来也有一模一样的报错：

```ts
const user = { name: 'Tom' };
type B = user;
```

```text
error TS2749: 'user' refers to a value, but is being used as a type here.
  Did you mean 'typeof user'?
```

`user` 只是舞台上的一个人，你怎么能把它写成剧本上的一行字？
编译器很贴心，还告诉你正确写法是 `typeof user`——用传送门把值搬过去。

### 杀手级推论：泛型为什么不能 `new`

```ts
function make<T>() {
  return new T();
}
```

```text
error TS2693: 'T' only refers to a type, but is being used as a value here.
```

**`T` 只是一个类型参数，它活在剧本里。**
`new` 需要舞台上一个真实存在的构造函数。剧本上写"某个类"，舞台上是不会凭空出现那个类的。

这就是为什么 Java 的泛型实现那么别扭，也是为什么 TS 里的工厂函数要写成这样：

```ts
// 把"构造能力"当参数传进去——从舞台上递一个真东西给函数
function make<T>(Ctor: new () => T): T {
  return new Ctor();
}

class Cat {
  meow() { return '喵'; }
}

const c = make(Cat);   // 传的是舞台上的真东西
```

**一句话记住它：TypeScript 有两个世界——剧本（类型空间）和舞台（值空间）。搞不清报错时，先问自己"我现在在哪个世界"。**

## 0.7 哲学三：看形状，不看名字

> 对应目标 9 里的 structural（结构化），非目标 1

### 类比

两种招聘标准：

- **名义制（nominal）**：只看毕业证。必须是"某某大学毕业"，别的学校哪怕课程一模一样也不要。（Java、C# 走这条路）
- **结构制（structural）**：只看你会什么。你说你会写 React、会调接口、会写测试，那就来。（TypeScript 走这条路）

TypeScript 选了结构制。原因是**它必须描述已有的 JavaScript**，而 JS 本来就是"看你会什么、不看你是谁"：

```js
function printName(obj) {
  console.log(obj.name);   // 我不管你是什么类，有 name 就行
}
```

TS 只是把这个事实**写下来**而已。

### 证据

```ts
class Point {
  x = 0;
  y = 0;
}

interface Vec2 {
  x: number;
  y: number;
}

const v: Vec2 = new Point();   // ✅ 通过！Point 和 Vec2 毫无继承关系
```

`Point` 是个 class，`Vec2` 是个 interface，它们之间**没有任何 `extends` / `implements` 关系**。
但因为形状一样（都有 `x: number` 和 `y: number`），TS 认为它们兼容。

反过来，形状缺一块就不行：

```ts
interface Dog { bark(): void }

class Cat { meow() {} }

const d: Dog = new Cat();
```

```text
error TS2741: Property 'bark' is missing in type 'Cat' but required in type 'Dog'.
```

注意错误说的是 **"Property 'bark' is missing"（缺了属性）**，而不是 **"Cat 不是 Dog"（类型不对）**。
这个措辞本身就在告诉你：TS 在看形状。

### 重要例外：`private` 会让它变回"名义制"

如果你在类里写了 `private` 成员，TS 就**不再只看形状**了：

```ts
class A { private secret = 1; name = 'a' }
class B { private secret = 1; name = 'b' }

const a: A = new B();
```

```text
error TS2322: Type 'B' is not assignable to type 'A'.
  Types have separate declarations of a private property 'secret'.
```

为什么？因为 `private` 的语义是"**这是 A 自己的内部实现细节**"。
如果只看形状就认为 B 兼容 A，那 A 的私有细节就通过 B 泄漏出去了。
所以一旦涉及 `private` / `protected`，TS 就退回到"必须是同一个声明"——**名义制**。

> 这是个高频面试点："**TS 是完全结构化的吗？**"
> 标准答案：**基本是结构化的，但 `private` / `protected` 成员会引入名义性。**

### 一个实际影响

因为结构化，写测试时你可以**不用 mock 库**：

```ts
interface UserRepo {
  findById(id: string): Promise<User>;
  save(u: User): Promise<void>;
}

// 一个对象字面量，只要形状对，就能当 UserRepo 用
const fakeRepo: UserRepo = {
  findById: async (id) => ({ id, name: 'Tom' }),
  save: async () => {},
};
```

**一句话记住它：TS 认形状不认户口本——除非你写了 private。**

## 0.8 哲学四：宁可不健全，也不能难用

> 对应非目标 3，这是最能体现 TS 团队"工程品味"的一条

先定义两个词：

- **健全（sound）**：编译器说安全的，运行时**一定**安全。
- **完备（complete）**：运行时安全的，编译器**一定**说安全。

真正的类型系统做不到两全（这是理论上的限制，叫"健全性与完备性不可兼得"）。
所以每门语言都要选一边站。

**TypeScript 明确选了"不健全"。** 官方原话：

> Apply a **sound or "provably correct" type system**. Instead, strike a balance between **correctness and productivity**.
> （不追求"可证明正确"的类型系统，而是在**正确性和生产力**之间取平衡。）

意思是：**它宁愿放过一些错误，也不愿意让你写不出代码。**

### 证据 1：数组是协变的（这是不健全的）

```ts
const strs: string[] = ['a'];

// string[] 可以赋给 (string | number)[] —— 因为 string 是 string|number 的子类型
const mixed: (string | number)[] = strs;

mixed.push(123);          // 编译通过！可是 strs 里现在混进了一个数字
const first: string = strs[0];   // 编译也通过！但它现在可能是 123
```

**这段代码编译完全没问题，但运行时是错的。**
TS 团队知道这件事，但为了让你能自然地写 `const all: (A|B)[] = aList`，他们选择接受。

（顺带说：Swift、Kotlin 用 `in`/`out` 型变标注来解决这个，但那会让类型写起来复杂得多。TS 选了简单。）

### 证据 2：`any` 是黑洞

```ts
const data: any = JSON.parse('{}');
const n: number = data;        // 通过
const s: string = data;        // 也通过
const x: 不存在这个类型 = data;  // 还是通过
```

`any` 会**双向**吞掉一切类型检查。
它的存在是刻意的：**给"我正在从 JS 迁移过来，这里先不管"留一个逃生舱。**

### 证据 3：`as` 可以骗编译器

```ts
const n = 'hello' as unknown as number;
n.toFixed(2);   // 编译通过，运行时 TypeError
```

### 证据 4：`Object.keys()` 的返回类型

```ts
const user = { name: 'Tom', age: 18 };
const keys = Object.keys(user);
//    ^? keys 的类型是 string[]，而不是 ('name' | 'age')[]
```

其实 TS 完全有能力返回 `('name' | 'age')[]`。但为了不破坏已存在的海量 JS 代码，它没有这么做。

### 所以，正确的态度是什么？

**把 TS 当成"意图说明 + 廉价的第一道防线"，不要当成"安全保证"。**

| 场景 | TS 能防吗？ | 该用什么 |
|---|---|---|
| 自己代码里的拼写错误、参数传错 | ✅ 非常擅长 | TS |
| 重构时漏改某个调用点 | ✅ 非常擅长 | TS |
| 后端返回了脏数据 | ❌ 完全防不住 | zod / valibot |
| `localStorage` 里被别人改过的值 | ❌ 完全防不住 | zod |
| 第三方 SDK 的文档和实现不一致 | ❌ 防不住 | 读源码 + 运行时校验 |
| 类型标注写错了（`as` 骗编译器） | ❌ 防不住自己骗自己 | code review |

**一句话记住它：TS 的目的是让你更快，不是让你绝对安全。它的每一个"不严谨"都是为了不挡住你。**

## 0.9 反面清单：TypeScript 明确不负责的事

把官方非目标翻译成工作里能用的判断标准：

| 你可能会期待 | TS 的实际态度 | 你该用什么 |
|---|---|---|
| "帮我校验接口返回的数据" | 非目标 5：运行时没有类型信息 | zod / valibot / arktype |
| "帮我让代码跑得更快" | 非目标 2：不优化运行时性能 | 算法 + 性能剖析工具 |
| "帮我打包、压缩、做产物" | 非目标 4：不做构建流水线 | Vite / esbuild / webpack / Rollup |
| "帮我加个 `Array.prototype.sum()`" | 非目标 6：不加运行时功能 | 自己写工具函数 |
| "编译时根据类型生成不同代码" | 非目标 5：禁止 | 用函数重载或分支 |
| "帮我自动生成 API 文档" | 不负责 | TypeDoc / 手写 |

**这张表能帮你避免 90% 的"我以为 TS 能……"。**

---

## 0.10 用这四条哲学，重看三段"奇怪"的代码

### 案例 1：为什么不能 `instanceof` 一个 interface？

```ts
interface Foo { a: number }
if (x instanceof Foo) {}
// error TS2693
```

**答案**：哲学一 + 哲学二。`interface` 只活在类型世界，`instanceof` 是值空间运算符，运行时要拿一个真实的构造函数来比。图纸被收走了。

**正确做法**：用 `in` 做属性收窄，或者干脆用 class / 判别联合。

```ts
if ('a' in x) { /* ... */ }
```

---

### 案例 2：为什么泛型不能 `new T()`？

```ts
function f<T>() { return new T() }
// error TS2693: 'T' only refers to a type...
```

**答案**：同上。`T` 是剧本上的占位符。要 `new` 就得从舞台上递一个真构造函数进来。

```ts
function f<T>(Ctor: new () => T): T { return new Ctor() }
```

---

### 案例 3：为什么 `as` 写错了也不报错？

```ts
const x = 'hello' as unknown as number;
x.toFixed(2);   // 编译通过，运行时炸
```

**答案**：哲学四。`as` 是你对编译器的**承诺**，不是**请求**。
你说了"我保证它是 number"，编译器就信了。
它选择相信你，因为不相信你的话，很多 JS 迁移场景根本没法写。

**结论**：`as` 应该被视为技术债。每写一个 `as`，都值得多问一句"为什么这里需要它"。

## 0.11 本章小结

如果这一章你只记住一句话，记这句：

> **TypeScript 不是一门新语言，它是给 JavaScript 加的一套"编译期说明书"。
> 说明书写得再好，运行时也不会有它的痕迹。**

四条哲学，随身携带：

| 哲学 | 一句话 | 它解释了 |
|---|---|---|
| 一、可擦除 | 类型是图纸，盖完就收走 | 为什么不能 `instanceof interface`；为什么类型不影响性能 |
| 二、两个世界 | 剧本 vs 舞台 | 所有 TS2693 / TS2749 报错；为什么泛型不能 `new T()` |
| 三、结构化 | 看形状不看户口本 | 为什么两个无关的类能互相赋值；为什么测试不用 mock 库 |
| 四、不健全 | 宁可放过，不愿挡住 | 为什么 `any` / `as` / 数组协变都不报错 |
