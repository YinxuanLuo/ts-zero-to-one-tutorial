# 第 01 章　环境搭建 + TypeScript 的心智模型

> 本章对应代码：`examples/01-心智模型.ts`（可运行）

先给你一颗定心丸：这一章只有一行代码是"新知识"，其余全是在帮你**建立正确的脑内模型**。模型错了，后面每一章你都会学得很痛苦；模型对了，后面三十章会越看越顺。

## 1.0　TypeScript 到底是个什么东西

用一句大白话：**TypeScript 就是"JavaScript + 一层写完就扔的说明书"。**

拆开说：

- 它**不是**一门新语言。它的语法是 JavaScript 的超集——所有合法的 JS 都是合法的 TS，你敲的还是 JS。
- 它**不改变**代码的运行方式。JS 里 `1 + '1'` 是 `'11'`，TS 里也还是 `'11'`。
- 它多出来的那部分东西——类型注解、`interface`、`type`——**只在你写代码的时候存在**。代码真正跑起来之前，这些东西会被**整块剥掉**。

正式一点的说法：TypeScript 是 JavaScript 的**静态类型检查器**（static type checker）加一套**类型语法**。"静态"的意思是"在代码运行之前"，检查器的工作是"读你的代码，告诉你哪里对不上"。

TypeScript 官方给自己的一句话定位是：

> TypeScript is JavaScript that scales.

翻译成人话：**TypeScript 是一套让 JavaScript 能扛住大团队大项目的方案。** 这是整个教程的纲领，1.8 节专门展开。

### 类比：TypeScript 是"一位站在你旁边的审稿人"

想象你在写一本书，要交稿给出版社。

- **JavaScript**：写完直接印刷，印出来才发现第 300 页主角名字从"张三"变成了"李四"。
- **TypeScript**：出版社多配了一位审稿人。你一边写，他一边看。看到你把一个数字塞进"人名"那一栏，他立刻说："这栏该填人名，你填了个数字，改一下。"

关键点：**他是在你写稿子的时候站在你旁边的，不是在书印好之后才出现的。** 书一进印刷厂，审稿人就下班了，他一个字都不会出现在成品书里。

这个"审稿人只在你写的时候存在"的性质，就是本章最重要的概念——**类型擦除**。下面全是它的展开。

### 顺便说清楚"TypeScript 7"这件事

你上网搜 TypeScript，可能看到 npm 上最新版已经是 **7.0.2**。那是 TypeScript 用 Go 重写编译器的新版本（社区叫 native port / typescript-go），主打编译速度大幅提升。

**但本教程统一以 5.9.3 为准**，原因很实在：

1. 5.9 是当前所有项目的实际主流版本，面试官和你的同事用的就是它。
2. 类型系统的核心概念（擦除、结构化类型、推断规则）在 5.9 和 7.0 之间**完全一样**，不存在学错的问题。
3. 配套工程里装的就是 `typescript@5.9.3`。

我提这一句，是为了让你以后看到别人说"TS 7 才是最新"时，不会怀疑自己学错了。

### 配套工程长什么样

教程代码都在 `examples/` 目录，你不用自己搭。

`package.json`（关键部分）：

```json
{
  "type": "module",
  "scripts": {

    "build": "tsc",
    "demo": "node --experimental-strip-types"
  },
  "devDependencies": {
    "@types/node": "^24.19.1",
    "typescript": "^5.9.3"
  }
}
```

`tsconfig.json`（全教程共用这一份）：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2023"],
    "module": "NodeNext",
    "moduleResolution": "NodeNext",

    "strict": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,

    "noEmit": true,
    "allowImportingTsExtensions": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "verbatimModuleSyntax": true
  },
  "include": ["**/*.ts"]
}
```

现在你一个字都看不懂没关系，第 02 章（类型基础与推断）会逐行拆。先记住三件事：

1. **`"strict": true`** —— 打开最严格的检查。教程全程开 strict，因为面试和真题项目都开。
2. **`"noEmit": true`** —— 只检查，不生成 `.js`。我们靠 `node x.ts` 直接跑。
3. **`"allowImportingTsExtensions": true`** —— 允许写 `import { x } from './lib.ts'`。注意是 **`.ts` 后缀**，不是 `.js`。

如果你要自己电脑上从零搭一份，就两条命令：

```bash
npm init -y
npm i -D typescript@5.9.3 @types/node@24
```

`@types/node` 是"Node 自带 API 的说明书"，装上它你才能在 TS 里用 `process`、`fs`、`path` 而不报错。

## 1.2　跑 TypeScript 的三种方式（2024 年之后变了天）

我知道你现在最想问："我写完 `.ts`，怎么跑起来？"

历史上有三条路。我把它们摆在一起对比，然后告诉你为什么现在有一条明显更省事。

### 路线 A：`tsc` 编译成 `.js`，再 `node` 跑

这是**最老、最经典、也最啰嗦**的一条路。

```bash
npx tsc            # 把 .ts 编译成 .js
node dist/main.js  # 跑编译产物
```

`tsc` 是 TypeScript 编译器（TypeScript Compiler）。它只做两件事：

1. **检查类型**，有问题就报错。
2. **把类型全部抹掉**，输出一份纯净的 JavaScript。

**适合场景**：真正要发布的库、要打包上线的项目、需要精确控制输出（比如同时出 ESM 和 CJS）。

**痛点**：多一个"产物目录"；调试时你看到的报错行号是 `.js` 的，不是 `.ts` 的；改一行要等一次完整编译。开发体验笨重。

### 路线 B：`tsx` / `ts-node` 这类"运行器"

这两个是社区工具，让你**直接跑 `.ts` 文件**：

```bash
npx tsx main.ts
npx ts-node main.ts
```

原理是：在内存里**偷偷调用 `tsc` 转译一次**，拿到 JS 再交给 Node 执行。你不用管 `.js` 产物。

**适合场景**：几年前这是开发时的标准做法。项目里已经有 `ts-node` 配置（比如配合 `nodemon` 热重载）就跟着用。

**痛点**：多一个依赖、多一层 `node_modules`、多一堆版本兼容问题（`ts-node` + ESM + NodeNext 当年是出了名的折磨人）。而且它对源码做的事**比 Node 多**，"tsx 跑得通"不等于"node 跑得通"，两边容易对不上。

### 路线 C（推荐）：`node x.ts` 直接跑

从 Node.js 22.6 引入实验性支持，到 Node 23.6 默认开启，**现在 `node` 已经能直接吃 `.ts` 文件了**：

```bash
node 01-心智模型.ts
```

这就是本教程从头到尾用的方式，你的 Node v24.21.0 完全支持。

它背后做的事叫 **type stripping（类型剥离）**，也叫**类型擦除加载**。大白话：**Node 自己拿把刀，把 `.ts` 里的类型部分"咔嚓"剪掉，剩下的当普通 JS 执行。**

它和路线 B 的本质区别：

| | `tsx` / `ts-node` | `node x.ts` |
| --- | --- | --- |
| 谁干活 | 第三方工具（内部调 tsc 转译） | Node 内核自己 |
| 需要安装吗 | 需要 | **不需要，零依赖** |
| 速度 | 要起一层工具 | 只做剪裁，几乎和跑 JS 一样快 |
| 会检查类型吗 | 部分会 | **完全不会**（下面详述） |
| 对语法的处理 | 更宽松，会真的"翻译" | 更严格，只认"能被剪掉"的语法 |

**这就是为什么 2024 年之后 `node x.ts` 变成最省事的选择**：零安装、零配置、零中间产物。新建一个文件，敲一行 `console.log`，`node` 一跑就有结果。

### 但有个必须知道的坑：Node 只剪裁，不翻译

Node 的类型剥离是 **strip-only（只剥离）**模式，它只做一件事：**把类型相关的字符删掉**。它**不会**把某种语法"翻译"成另一种语法。

大部分 TS 语法天生能被删掉——`interface` 删掉、`:` 后面的类型删掉、`as X` 删掉。但有几样**删不掉，因为它们会产生真实的运行时代码**：

- `enum`
- `namespace`
- 构造函数参数属性（`constructor(private step: number)`）
- 老式 `import x = require('y')`

你直接跑一个用 `enum` 的文件，Node 会给你很明确的报错：

```text
$ node 00-enum-probe.ts

file:///.../00-enum-probe.ts:1
enum Color { Red, Green }
^^^^^^^^^^^^^^^^^^^^^^^^^
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
    at parseTypeScript (node:internal/modules/typescript:68:40)
    ...
Node.js v24.21.0
```

关键词是 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` 和 `enum is not supported in strip-only mode`。

两条出路：

**出路一（推荐）**：换成 `as const` 对象加联合类型。1.6 节有完整代码，这也是现在社区的主流写法。

**出路二**：加开关让它"真的翻译"：

```bash
node --experimental-transform-types 00-enum-probe.ts
# enum ok: Red 0
```

代价是它还是实验性的，跑起来会打印一行 `ExperimentalWarning`。

> **还有一个开关要提前告诉你**：`tsc --erasableSyntaxOnly`。
> 在 `tsconfig.json` 里打开它，`tsc` 会禁止所有"不可擦除"的语法，逼你写 Node 能直跑的子集。报错长这样：
>
> ```text
> error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
> ```
>
> 配套工程**没有开**它（因为教程后面要讲 `enum`，得先让你能写出来）。但**你自己项目里强烈建议开**——它能在写代码时就拦住"这个语法 node 跑不了"，不用等到运行时。

### 什么时候用哪个

| 场景 | 用什么 |
| --- | --- |
| 学语法、写小脚本、跑练习题 | **`node x.ts`** ← 本教程全程用它 |
| 需要类型检查 | **`npx tsc --noEmit`** |
| 发布 npm 包 / 构建上线产物 | `tsc`（或别的打包器） |
| 老项目里已有 `ts-node` 配置 | 跟着项目走，别乱换 |

**关键理解**：`tsc` 和 `node x.ts` **不是竞争关系，是分工关系**。

- `node x.ts` 负责**跑**，它**不检查类型**。
- `tsc --noEmit` 负责**查**，它**不跑代码**。

把这两条命令背下来：

```bash
node x.ts                 # 跑起来
npx tsc --noEmit          # 检查类型（无输出 = 全部通过）
```

**一句话记住它：`node x.ts` 负责跑但不查，`tsc --noEmit` 负责查但不跑，两个一起用才是完整的。**

## 1.3　你的第一个 TS 文件

新建 `hello.ts`，两行：

```ts
// 一个最普通的字符串变量
const name: string = 'Ada';

console.log(`你好, ${name}`);
```

跑起来：

```bash
node hello.ts
# 你好, Ada
```

是不是觉得"这也太 JS 了"？对，**TS 的起点就是 JS**。唯一的区别是那个 `: string`。

```
const name: string = 'Ada';
      ──┬─  ──┬───   ──┬──
        │     │        │
        │     │        └── ③ 真实的值，运行时存在
        │     └── ② 类型注解（type annotation），运行时会消失
        └── ① 变量名，运行时存在
```

只有 ② 是 TS 独有的。而且**它消失了也不影响 ① 和 ③**。这就是下一节的主角。

### 目录结构说明

```
examples/
├── package.json          # "type": "module"，ESM 风格
├── tsconfig.json         # 全教程共用的 TS 配置
├── node_modules/         # typescript@5.9.3、@types/node@24
├── 01-心智模型.ts         # 本章配套代码（可运行）
├── 00-smoke.ts           # 环境冒烟测试
└── ...
```

三条规矩，现在记住，后面不重复：

**规矩一：文件名用中文 + 数字编号。** 教程里所有文件名都对得上章节号。你自己练习随便命名，但**别用空格**。

**规矩二：相对导入必须写 `.ts` 后缀。**

```ts
import { tag } from './lib.ts';   // 对
import { tag } from './lib';      // 不行，Node 找不到
import { tag } from './lib.js';   // 不行，文件根本不存在
```

这跟写 CJS 时的直觉相反（那时习惯不写后缀），但在"Node 直跑 TS"这套体系里，**`.ts` 后缀是必须的**。

**规矩三：只导入类型时，用 `import type`。**

```ts
import { type Id, tag } from './lib.ts';   // 可以
import type { Id } from './lib.ts';        // 也可以
```

因为配套工程开了 `verbatimModuleSyntax`，忘了会报：

```text
error TS1484: 'Product' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

**为什么这么设计？** 因为类型在运行时不存在。这条规则逼你把"我要一个类型"和"我要一个真实的值"分清楚——**这个区分的习惯，正是本章心智模型的实践**。具体规则第 02 章细讲。

**一句话记住它：TS 文件就是 JS 文件加一层可擦除的注解，相对导入记得写 `.ts`。**

## 1.4　核心心智模型：类型擦除（type erasure）

进入全章重头戏。这节吃透了，TypeScript 就没有神秘感了。

### 先用大白话说它解决什么问题

我写代码时，脑子里有大量"我知道但没写下来"的信息：

> "这个 `user` 一定有 `name` 字段，`name` 一定是字符串。"
> "这个函数传进来的必须是数字。"
> "这个列表里装的都是 `Todo`。"

这些信息本来只存在于**我的脑子**和**随口写的注释**里。我一去倒咖啡，信息就丢了。

TypeScript 要做的事就是：**把我脑子里的这些信息，变成能写进代码里的文字，让编译器和同事都能看见。**

但是——**这些信息对程序运行毫无用处**。CPU 不关心 `name` 是不是字符串，它只关心内存里那个字节是 `0x41` 还是 `0x42`。所以这些信息在执行的时候是纯粹的负担。

于是 TypeScript 的方案非常干脆：

> **写的时候全在，跑的时候全没。**

这就是**类型擦除**。正式定义：**TypeScript 的类型信息在编译/转译成 JavaScript 的过程中被完全移除，不产生任何运行时表示。**

### 类比：建筑图纸 vs 建好的房子

- **图纸**上画着"这根梁必须承重 5 吨"、"这面墙必须 12 厘米厚"。
- **房子**盖好之后，你在墙里摸不到那张图纸，也摸不到"5 吨"三个字。但正因为有图纸，房子才不会塌。

你住进房子后（= 程序运行时），图纸（= 类型）已经完成使命了。**它保护的是"施工过程"，不是"居住过程"。**

另一个更贴切的类比：**体检报告**。报告上写着"血糖 5.6"，医生据此给你建议。但"血糖 5.6"这几个字不是长在你身体里的，它是一份**关于你**的文档，不是**你**的一部分。

### 证据一：用 `tsc` 编译，看产物

先给你一段"五脏俱全"的 TS：

```ts
// 输入：demo.ts
interface User {
  name: string;
  age: number;
}

type Id = string | number;

function greet(user: User): string {
  return `你好, ${user.name}`;
}

const u: User = { name: 'Ada', age: 36 };
console.log(greet(u));

class Counter {
  private count = 0;
  constructor(private step: number) {}
  inc(): number {
    this.count += this.step;
    return this.count;
  }
}

const c = new Counter(2);
console.log(c.inc());
```

编译：

```bash
npx tsc --target ES2022 --module ES2022 demo.ts --outDir out
```

打开 `out/demo.js`：

```js
// 输出：out/demo.js
function greet(user) {
    return `你好, ${user.name}`;
}
const u = { name: 'Ada', age: 36 };
console.log(greet(u));
class Counter {
    step;
    count = 0;
    constructor(step) {
        this.step = step;
    }
    inc() {
        this.count += this.step;
        return this.count;
    }
}
const c = new Counter(2);
console.log(c.inc());
```

请你**慢慢对照着看**，这是全章最重要的一次对照：

| TS 里写的 | JS 产物里 | 发生了什么 |
| --- | --- | --- |
| `interface User { ... }` | **整块不见了** | 接口不是值，擦掉 |
| `type Id = string \| number` | **整块不见了** | 类型别名不是值，擦掉 |
| `function greet(user: User): string` | `function greet(user)` | 参数和返回值的注解擦掉 |
| `const u: User = ...` | `const u = ...` | 变量注解擦掉 |
| `private count = 0` | `count = 0` | `private` 是纯类型概念，擦掉 |
| `constructor(private step: number)` | `step;` + `constructor(step) { this.step = step }` | 参数属性**不是纯擦除**，被翻译成了赋值语句 |
| `inc(): number` | `inc()` | 返回类型擦掉 |

注意倒数第二行：`constructor(private step: number)` **被真的翻译了**，因为它同时干了三件事（声明字段、接收参数、赋值）。这就是它属于"不可擦除语法"、Node 直跑会拒绝的原因——**Node 只剪裁，不翻译**。

但注意那个 `private`：**它被干净地擦掉了**。这是关键伏笔，记住它，第 07 章（类、模块与声明文件）会讲后果。

### 证据二：用 Node 的类型剥离验证同一件事

`node x.ts` 走的是另一条路（剥离而不是编译），但结果一样。本章配套文件里：

```ts
interface User {
  readonly id: UserId;
  name: string;
  age: number;
  email?: string;
}

type UserId = string | number;

const ada: User = { id: 1, name: 'Ada', age: 36 };

console.log('运行时 typeof ada =', typeof ada);
console.log('运行时 Object.keys(ada) =', Object.keys(ada).join(', '));
```

跑出来是：

```text
[1] 运行时 typeof ada = object
[1] 运行时 Object.keys(ada) = id, name, age
```

请你盯着这两行看：

- `typeof ada` 是 `object`，**不是** `User`。运行时根本没有"User"这个概念。
- `Object.keys(ada)` 只列出 `id, name, age`。**`readonly` 不见了，`email?:` 也不见了**（它本来就没赋值）。
- 也就是说，**类型在运行时连"存在过"的痕迹都没有**。

### 证据三：你可以在运行时"证明"类型不存在

最能让你"原来如此"的实验。看这段：

```ts
interface Animal {
  name: string;
}

const a: Animal = { name: 'dog' };

// 想在运行时判断：a 是不是 Animal？
console.log(a instanceof Animal);
```

你猜 `tsc` 会说什么？

```text
error TS2693: 'Animal' only refers to a type, but is being used as a value here.
```

翻译成人话："**'Animal' 只是一个类型，你却把它当成一个值来用。**"

`instanceof` 是**运行时**操作符，它右边必须是**运行时真实存在的东西**。而 `Animal` 是 `interface`，编译那一刻就被擦除了，运行时它**压根不存在**。所以这行代码不是"运行结果不对"，是**根本编译不过**。

这个 `TS2693` 你以后会经常见到，它出现的**唯一原因**就是类型擦除。只要你在运行时想"碰"一个类型，都会撞上它。它的变体还有：

```ts
type Id = string;
const x = Id;
```

```text
error TS2693: 'Id' only refers to a type, but is being used as a value here.
```

```ts
interface Channel { id: string }
function f(ch: Channel) {}
f(typeof c);
```

```text
error TS2749: 'Channel' refers to a value, but is being used as a type here. Did you mean 'typeof Channel'?
```

（`TS2749` 是反过来：你把一个**值**当**类型**用了。）

### 并排对照：擦除前 vs 擦除后

把最容易搞混的东西放一起，你一眼就能看出界限在哪。

**擦除前（你写的 .ts）：**

```ts
interface Todo {                    // ← 类型，会消失
  id: number;
  title: string;
  done: boolean;
}

type Filter = 'all' | 'open';       // ← 类型，会消失

const FILTERS = ['all', 'open'] as const;   // ← 值，会保留

function isDone(todo: Todo): boolean {      // ← 注解消失，函数保留
  return todo.done;
}

class Store {                                // ← 值（类是真实的函数），保留
  private items: Todo[] = [];                // ← private 和 Todo[] 都会消失

  add(todo: Todo): void {                    // ← 注解消失，方法保留
    this.items.push(todo);
  }
}
```

**擦除后（Node 眼里的样子）：**

```js
const FILTERS = ['all', 'open'];

function isDone(todo) {
  return todo.done;
}

class Store {
  items = [];

  add(todo) {
    this.items.push(todo);
  }
}
```

**判断标准只有一条**：

> 问自己一句：**这个东西"运行时需要它才能跑"吗？**
> 需要 → 是**值**，保留。
> 不需要 → 是**类型**，擦掉。

`class` 是值，因为你要 `new` 它。`interface` 是类型，因为你从不 `new` 它。`as const` 的数组是值，因为你要遍历它。

### 为什么 TS 要这么设计

你可能会想："为什么不留着类型？运行时检查一下多安全。"

三个原因，一个比一个实际：

**一、零运行时开销。** 类型信息如果保留，每个对象都要带一份"我是啥类型"的元数据，JS 引擎的整套优化体系（隐藏类、内联缓存）都要被拖累。TS 的承诺是：**擦除后的 JS，和手写的 JS 性能完全一致。**

**二、100% 兼容 JavaScript 生态。** 擦除完就是普通 JS，任何环境都能跑，人类也能读。没有"TS 专属运行时"这种东西。

**三、不改变语义。** 如果类型能当运行时判断用，那"加类型"就会**改变程序行为**，迁移会变成噩梦。TS 保证：**同一份代码加类型和去掉类型，运行结果必须一样。**

第三条是 TypeScript 的**最高设计原则**，叫 **"类型不改变运行时行为"（no runtime semantics）**。你以后遇到任何"TS 为什么不帮我做 X"的抱怨，八成答案都是这一条。

**一句话记住它：类型只活在写代码的时候，编译一结束全部消失，运行时一个字节都没有。**

## 1.5　编译期 vs 运行期：一堵看不见的墙

类型擦除带来一个必然后果：**你的程序其实活在两个完全不同的世界里。**

| | 编译期（写代码时） | 运行期（跑起来时） |
| --- | --- | --- |
| 谁在看 | TypeScript 编译器 | Node / V8 / 浏览器 |
| 能看到什么 | 类型、注解、interface | 只有值：数字、字符串、对象、函数 |
| 出错的后果 | 报个错，你改代码 | **程序崩溃 / 数据错了** |
| 能拦住什么 | 类型不匹配 | 什么都拦不住，只会如实执行 |
| 典型证据 | `error TS2322` | `TypeError: Cannot read properties of undefined` |

画成一道墙：

```text
        ┌───────────────────────────────┐
        │        编译期（写作时）          │
        │   interface / type / 注解      │   ← 只有这个世界有
        │   tsc 报的红色波浪线           │
        └───────────────┬───────────────┘
                        │
                   ═════╪═════  ← 类型擦除就发生在这条线上
                        │
        ┌───────────────┴───────────────┐
        │        运行期（跑起来时）        │
        │   只有值：1, 'a', {}, [], fn   │   ← 类型信息一个都没有
        │   TypeError / 崩溃             │
        └───────────────────────────────┘
```

**这堵墙是单向的**：编译期能"看到"运行期的意图（因为你写了类型），运行期**完全看不到**编译期的东西。

理解了这堵墙，一大堆"TS 的怪毛病"立刻就不怪了。下面三个是新手最容易栽的坑。

### 5.1　为什么 `interface` 不能 `instanceof`

上一节讲过报错，这里补一句**为什么会有人这么写**：因为你写 JS 时是这么干的：

```js
class Dog {}
const d = new Dog();
console.log(d instanceof Dog);   // true
```

`class` 在运行时**是真实存在的函数**（看前面的编译产物，`class Counter` 原样保留），所以 `instanceof` 能工作。`interface` 不是。

你想用 `instanceof` 判断"这个对象符不符合某个形状"，本质上是在**运行时读取类型**——这堵墙不允许。

```text
error TS2693: 'Animal' only refers to a type, but is being used as a value here.
```

**那我想在运行时判断对象形状怎么办？** 只有一个办法：**自己写判断逻辑，看真实的属性**。

```ts
interface Animal { name: string }

// 运行时真检查：看它有没有 name，且是不是字符串
function isAnimal(value: unknown): value is Animal {
  return (
    typeof value === 'object' &&
    value !== null &&
    'name' in value &&
    typeof (value as { name: unknown }).name === 'string'
  );
}

const data: unknown = JSON.parse('{"name":"dog"}');
console.log(isAnimal(data));   // true
console.log(isAnimal({}));     // false
```

那个 `value is Animal` 叫**类型谓词**（type predicate），第 04 章（联合类型与类型收窄）细讲。现在你只要看懂一件事：**函数体里全是 `typeof`、`in`、`!== null` 这种运行时检查——因为只有这些在运行时真实存在。**

### 5.2　为什么不能用类型判断分支

新手会写出这种代码：

```ts
interface Admin { level: number }
interface Guest { level: number }

function isAdmin(user: Admin | Guest): boolean {
  return user instanceof Admin;   // 报错 TS2693
}
```

这个例子特别值得看：**`Admin` 和 `Guest` 的形状完全一样（都只有 `level: number`）。** 就算 `Admin` 是 `class` 能通过编译，`instanceof` 也判断不出什么有用的东西——因为在结构化类型系统里，**这俩本来就是同一个类型**（1.6 节讲）。

**类型不能当运行时条件用。** 要判断分支，就必须有一个**运行时真实存在的标记**：

```ts
// 用一个真实存在的字段来区分（这叫「可辨识联合」的雏形）
interface Admin { kind: 'admin'; level: number }
interface Guest { kind: 'guest'; level: number }

function describe(user: Admin | Guest): string {
  if (user.kind === 'admin') {     // kind 是真实存在的字符串
    return `管理员，等级 ${user.level}`;
  }
  return `访客，等级 ${user.level}`;
}
```

`kind` **运行时真的在对象里**，所以 `user.kind === 'admin'` 合法。这是 TS 里做分支的标准做法，第 04 章（联合类型与类型收窄）会讲透。

### 5.3　完整案例：类型写着 `string`，运行时是 `undefined`，然后崩溃

**这是本章最需要你亲手跑一遍的例子。**

```ts
interface User {
  name: string;      // 我向编译器"保证"：一定有 name，且是字符串
}

// 服务器返回的数据：只有 id，没有 name
const raw = '{ "id": 2 }';

// 我把 JSON.parse 的结果"断言"成 User
const fakeUser = JSON.parse(raw) as User;

// 编译器完全信任我，放行：
console.log(fakeUser.name.toUpperCase());
```

**`tsc` 一声不吭，检查完全通过。** 因为 `User` 上写着 `name: string`，而 `fakeUser` 是 `User`，所以 `fakeUser.name` 是 `string`，`string` 当然能调 `.toUpperCase()`。

但真跑起来：

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
    at file:///.../01-心智模型.ts:20:63
```

**为什么？** `JSON.parse` 返回的类型是 `any`，`as User` 只是**你说服了编译器**，没有**改变数据**。数据里真的没有 `name`，所以 `fakeUser.name` 是 `undefined`，`undefined.toUpperCase()` 就炸了。

这就是最致命的组合：**`any` + `as` + 外部数据**。类型系统在这里完全失效，因为它拿到的是一个"被污染的"输入。

配套文件里我把这个崩溃包在 `try/catch` 里了，所以脚本不会真的挂掉，但报错原样打印。你运行 `node 01-心智模型.ts` 会看到：

```text
[2] 崩了 -> Cannot read properties of undefined (reading 'toUpperCase')
[2] 类型写着 string，运行时其实是 undefined
```

**正确的做法**是这样（注意检查逻辑全是在真的读属性）：

```ts
// 外部数据的类型，老老实实标成 unknown —— "我还不知道它是什么"
const data: unknown = JSON.parse(raw);

// 手动检查，把 unknown 收窄成 User
function toUser(value: unknown): User | null {
  if (typeof value !== 'object' || value === null) return null;
  const v = value as Record<string, unknown>;
  if (typeof v.name !== 'string') return null;    // 关键：运行时真的检查
  return { name: v.name };
}

const user = toUser(data);
if (user === null) {
  console.log('数据格式不对，拒绝使用');
} else {
  console.log(user.name.toUpperCase());   // 到这里才安全
}
```

**请记住这个画面。** 以后面试官问"TS 能保证运行时安全吗"，你就有话说了。

### 5.4　哪些数据不受类型保护

**凡是"从 TS 管不到的地方进来"的数据，类型都只是在骗你。** 常见入口：

| 入口 | 为什么危险 |
| --- | --- |
| `JSON.parse(...)` | 返回 `any`，数据结构完全不受控 |
| `localStorage.getItem(...)` | 返回 `string \| null`，存进去的可能是任何东西 |
| `fetch(...)` 后 `.json()` | 同样返回 `any`，服务器说变就变 |
| `postMessage` / WebSocket 消息 | 跨进程传的裸数据 |
| `process.env.XXX` | 运行时是 `string \| undefined`，可能根本没配 |
| 表单输入、URL 参数、命令行参数 | 用户想输什么就输什么 |
| `document.querySelector(...)` | 返回 `T \| null`，那个元素可能不存在 |
| 第三方库的 `any` 返回值 | 库作者没写类型，你无从判断 |

有个**极重要的推论**：外部数据进来时必须做运行时验证。要么手写（像上面那样），要么用专门的库（Zod、Valibot 这类"运行时校验 + 类型推导"的工具）。这个话题在第 11 章（面试速查表）里有一份可以直接背的问答。

`process.env` 特别典型，提前看一眼：

```ts
const port = process.env.PORT;    // 类型是 string | undefined
```

注意是 `string | undefined`——**TypeScript 明确告诉你"它可能不存在"**。这不是在给你添麻烦，是在**替你记住一个你一定会忘的事实**。

**一句话记住它：类型只在编译期存在，运行时世界对类型一无所知——所以从外部进来的数据，类型管不了，必须自己验。**

## 1.6　注解 vs 推断：第一哲学是"能推断就不手写"

### 先用大白话说清楚

有时候你写类型，有时候不用写，TypeScript 自己就能算出来。

- **注解（annotation）**：你手写类型。`const n: number = 1;`
- **推断（inference）**：TypeScript 自己看出来的类型。`const n = 1;` ← 它知道这是 `number`

**类比**：你跟同事说"把这袋米搬到 3 楼"。你不必再说"用两只手搬、走楼梯、别走电梯"。**该说的说，能自己看出来的别说。** 一开口就把所有细节念一遍的人，沟通效率极低。

TypeScript 的第一哲学就是这条：**能推断出来的类型，绝不要手写。**

### 坏品味 vs 好品味

```ts
// 坏品味：右边写得明明白白，左边再抄一遍
const badName: string = 'Ada';
const badList: string[] = ['a', 'b'];
const badCount: number = 0;
const badFn = (x: number): number => x * 2;
```

```ts
// 好品味：让编译器干活
const goodName = 'Ada';        // 推断为 "Ada"（注意是字面量类型！）
const goodList = ['a', 'b'];   // 推断为 string[]
const goodCount = 0;           // 推断为 0（字面量类型）
const goodFn = (x: number) => x * 2;   // 返回类型推断为 number
```

看出问题了吗？坏品味那版不只是"多打字"，它还**丢掉了信息**：

```ts
const a = 'Ada';         // 类型是 "Ada" —— 编译器知道它只能是这个字符串
const b: string = 'Ada'; // 类型是 string —— 编译器忘了它具体是啥
```

`a` 比 `b` 更**精确**。以后你写 `switch (a)` 时，TypeScript 能帮你检查每个 `case` 是否覆盖全；而 `b` 只能当普通字符串，什么忙都帮不上。

**手写注解往往是把一个精确类型"稀释"成模糊类型。**

再看一个函数场景，差别更明显：

```ts
// 手写返回类型，写错了编译器也发现不了
function double(n: number): string {
  return n * 2;      // error TS2322: Type 'number' is not assignable to type 'string'.
}
```

```ts
// 不写返回类型，编译器从函数体推出 number
function double(n: number) {
  return n * 2;      // 推断返回类型：number
}
```

上面那个报错说明一件事——**手写返回类型反而是"引狼入室"**：你在函数头和函数体之间人为制造了矛盾。不写就没这个矛盾。

### 什么时候必须手写

**规则一：函数参数。**

```ts
function add(a, b) { return a + b }
```

```text
error TS7006: Parameter 'a' implicitly has an 'any' type.
error TS7006: Parameter 'b' implicitly has an 'any' type.
```

**为什么参数不能推断？** 因为参数类型**只能来自调用者**，而编译器在定义函数时还没看到调用者。它没有任何线索，只能投降给 `any`。而 `strict: true` 里包含 `noImplicitAny`，就是"不许悄悄用 `any`"，所以这个错一定会报。

正确写法：

```ts
function add(a: number, b: number) {   // 参数必须手写
  return a + b;                        // 返回类型不用写，推断为 number
}
```

所以好品味的完整版是：**参数手写，返回值交给推断。**

**规则二：先声明后赋值的变量。**

```ts
let x;        // 类型是 any —— 编译器没有任何线索
x = 1;
x = 'abc';    // 不报错，因为 any 什么都接受
```

```ts
let x: number;   // 正确写法
x = 1;
```

**规则三：空数组。**

```ts
const list = [];      // 推断为 any[] —— 空的，没线索
list.push(1);
list.push('a');       // 不报错，因为 any[] 什么都收
```

```ts
const list: number[] = [];   // 正确写法
```

**规则四：你想"收窄"推断结果时。** 比如你希望一个值就是那两个字符串之一，而不是任意字符串：

```ts
let status = 'pending';                          // 推断为 string
let status2: 'pending' | 'done' = 'pending';     // 你主动收窄
```

（这种场景更地道的写法是 `satisfies` 或 `as const`，第 02 章会碰到。）

**验证方法：把鼠标悬停在变量上**（VS Code 里），你会看到 TypeScript 显示的推断类型。这是你以后最常用的学习手段——**看它推断出什么，你就知道它理解了什么。**

**一句话记住它：参数手写、返回值靠推断、能推断就不手写——写得多不等于写得好。**

## 1.7　TypeScript 的三个定位标签

这节回答："TypeScript 到底是个什么样的类型系统？"三个标签，每个我都先给大白话，再给正式名字。**这三个面试必问**，我标了重点。

### 标签一：渐进式（gradual typing）

**大白话**：你可以**慢慢地**从 JavaScript 迁移到 TypeScript，不用推倒重来。

**类比**：装修房子。你可以先只刷一间卧室的墙，其他房间保持原样，照样住人。

**具体是什么样**：

- 一个 `.js` 文件和一个 `.ts` 文件可以共存于同一项目，互相导入。
- 一个 `.ts` 文件里，你可以只给**一部分**东西加类型，剩下的不管。
- 你可以用 `any` 临时"关掉"某个值的检查，回头再补。
- 你甚至能打开 `allowJs`，让 `tsc` 连 `.js` 文件一起检查，检查强度随你调。

**为什么这么设计？** 因为 TypeScript 的真正对手不是"没有类型"，而是"**已经有一千万行 JavaScript 要维护**"。如果它要求你必须先把整个项目改完才能用，那就没人用了。**渐进式是 TypeScript 能活下来的根本原因。**

**对你的实际影响**：你接手的项目很可能一半 JS 一半 TS。看到 `any` 别急着骂，那可能就是别人标记的"待办事项"。

### 标签二：结构化类型（structural typing）★ 面试必考

**大白话**：**判断两个类型合不合得来，看它们的"形状"像不像，不看它们叫什么名字。**

**类比（这个要记住）**：机场安检。安检员看的是**你包里有没有违禁品**，不是**你的包是什么牌子**。你拿一个 LV 的包和一个地摊的包，只要里面装的都是"一件衣服 + 一台电脑"，安检结论完全一样。

另一个类比：**USB 接口**。任何插头，只要形状是 USB-A，就能插进 USB-A 的口。它不关心插头是罗技产的还是杂牌产的。

正式说法：TypeScript 用的是**结构化类型系统**（structural typing），也叫**鸭子类型**（duck typing）的静态版本。

> **鸭子类型**来自一句话："如果它走起来像鸭子，叫起来像鸭子，那它就是鸭子。"

**生动例子（配套文件里跑过）：**

```ts
interface Point {
  x: number;
  y: number;
}

const loose = { x: 1, y: 2 };   // 这个对象从没说过自己是 Point
const asPoint: Point = loose;    // 但形状对得上，就放行
```

在**名义类型系统**（nominal typing，比如 Java、C#）里，这行代码**会报错**——因为 `loose` 没声明"我 implements Point"。但 TypeScript 放它过，**因为它只看形状**。

**更震撼的例子是类实例之间：**

```ts
class Dog {
  name = 'dog';
  speak(): string { return 'woof'; }
}

class Robot {          // Robot 没有继承 Dog，也没实现任何 Dog 的接口
  name = 'robot';
  speak(): string { return 'beep'; }
}

const pretendDog: Dog = new Robot();     // 编译通过！
console.log(pretendDog.speak());          // 输出：beep
```

`Robot` **完全不知道 `Dog` 的存在**，但它有 `name` 和 `speak`，形状对上了，TS 就认为它"是一个 Dog"。

**反过来的例子更能说明问题：**

```ts
class Dog {
  name = 'dog';
  bark() { return 'woof'; }
}

class Cat {
  name = 'cat';
  meow() { return 'meow'; }
}

const d: Dog = new Cat();
```

```text
error TS2741: Property 'bark' is missing in type 'Cat' but required in type 'Dog'.
```

注意报错的措辞："**类型 'Cat' 里缺少属性 'bark'**"。它抱怨的是**缺了个方法**，不是"Cat 不是 Dog"。这就是结构化类型的思维方式。

**面试必考的一个经典问题**，先给你埋个种子：

```ts
class A { private secret = 1 }
class B { private secret = 1 }

const a: A = new B();
```

```text
error TS2322: Type 'B' is not assignable to type 'A'.
  Types have separate declarations of a private property 'secret'.
```

有意思吧？**两个形状一模一样的类，却互相不兼容**，因为 `private` 成员要求"必须是同一个声明"。这是结构化类型系统里唯一的"名义"例外。（第 07 章类、模块与声明文件有完整解释。）

**面试为什么考这个？** 因为它直接影响你写代码的方式：你不必为了让一个对象"符合某个接口"去写 `implements`，只要形状对就行。这跟 Java 的思维完全不同，是考察你"是不是真的理解 TS"的试金石。

**顺带说"多余属性检查"**，这是新手最困惑的地方：

```ts
interface Point { x: number; y: number }

const p: Point = { x: 1, y: 2, z: 3 };
```

```text
error TS2353: Object literal may only specify known properties, and 'z' does not exist in type 'Point'.
```

但前面那个 `const loose = { x: 1, y: 2 }; const asPoint: Point = loose;` 却过了。

**为什么？** 因为 TS 对**直接写在赋值位置的对象字面量**额外加了一层检查（excess property check，多余属性检查），目的是**抓拼写错误**：

```ts
const c: { apiUrl: string } = { apiURL: 'http://x' };
```

```text
error TS2561: Object literal may only specify known properties,
but 'apiURL' does not exist in type '{ apiUrl: string; }'.
Did you mean to write 'apiUrl'?
```

看那个 "Did you mean to write 'apiUrl'?" —— **这就是它的全部意义：帮你在写的时候抓到拼错的属性名。** 一旦你先把对象赋给一个变量再传进去，这层检查就不生效了。这是结构化类型的一个"人为加严"，第 04 章（联合类型与类型收窄）细讲。

### 标签三：类型层面图灵完备（所以有"类型体操"）

**大白话**：TypeScript 的类型系统**强到可以写出真正的程序**——只不过这个程序的输入输出都是"类型"而不是数据。

**类比**：你在 Excel 里能用公式算出各种东西。而 TS 的类型系统，相当于一个**完整的编程语言**，运行在"类型"这个维度上。

**什么是"图灵完备"？** 简单说就是"只要给足够的时间和内存，它能计算出任何可计算的东西"。TypeScript 的类型系统满足这个条件（有递归、有条件、有映射）。

**证据**：你在网上搜 TS，一定会看到这种吓人的东西：

```ts
// 在类型层面做数学运算（这不是在算数字，而是在"推导类型"）
type BuildTuple<L extends number, T extends unknown[] = []> =
  T['length'] extends L ? T : BuildTuple<L, [...T, unknown]>;

type Add<A extends number, B extends number> =
  [...BuildTuple<A>, ...BuildTuple<B>]['length'];

type Result = Add<3, 4>;      // 类型就是 7
```

这段代码在**类型层面**算出了 3 + 4 = 7，能通过 `tsc` 检查，`Result` 的类型真的是 `7`。而它**跑起来什么都不做**——类型全被擦除了。

**为什么 TS 要把类型系统做这么强？** 因为它要能**描述真实 JavaScript 的形状**。JS 极其动态，库的 API 五花八门。一个弱的类型系统根本描述不了 `Promise.all`、`Array.map`、`Object.keys` 的行为。TS 是被现实逼着变强的。

**代价是什么？** 就是**类型体操**——为了表达复杂类型关系，写出一坨人类看不懂的类型代码。编写成本极高、报错信息极差、可读性极低。

**给你的实用建议**：

1. **知道有这回事就够了**，面试被问"TS 类型系统强到什么程度"你能答上来。
2. **别主动写类型体操**。99% 的业务代码用不上。看到别人写的复杂类型，能读懂大意即可。
3. **别怕看到它**。它的存在是语言能力强的证明，不是你必须要掌握的全部。

**一句话记住它：渐进式（可以慢慢迁）、结构化（只看形状不看名字）、图灵完备（强到能写类型体操）——三点里，结构化是面试最爱考的。**

## 1.8　"TypeScript 是 JavaScript that scales"

**如果你只记住本章一节，就记这一节。**

### 常见的错误理解

大多数人（包括一年前的我）以为 TypeScript 的目的是：

> "帮我提前发现 bug。"

这句话**不能说错，但它不是重点**。如果只是"防 bug"，那测试、lint、code review 都能干，为什么非要发明一门语言？

### 真正的答案

> **让 100 个人改同一份代码的时候，不互相踩踏。**

### 类比：从"小作坊"到"大工厂"

**小作坊（3 个人的 JS 项目）**：只有你和小王。你把 `getUser` 返回的 `user.name` 改成了 `user.fullName`，在群里喊一句"我把 name 改成 fullName 了啊"，小王回个"OK"。**完事。口头约定就够用。**

**大工厂（300 人的 JS 项目）**：

- 40 个团队在改同一个仓库。
- 跨时区：你改代码时，西雅图的同事在睡觉。
- 你在 A 文件第 12 行删了一个字段，用到它的是另外 8 个团队的 47 个文件。
- 其中 2 处会在测试里被发现，1 处会在 code review 里被发现，**剩下 44 处会在上线三天后的凌晨 2 点被用户发现**。

**问题不在"会不会写错"，而在"错了之后要多久才发现，以及谁去发现"。**

口头约定在大工厂里彻底失效。你需要一个东西：**把"接口约定"变成代码的一部分，让机器去检查。**

这就是类型系统在大项目里的真正价值：**它是一份永远自动同步的、机器可验证的接口契约。**

### 三个具体的"踩踏"场景

**场景一：改了别人的东西，但不知道别人在用。**

```ts
// 你（在 order.ts 里）：
export interface Order {
  id: number;
  total: number;          // 你把 amount 改名成了 total
}
```

```ts
// 同事（在 report.ts 里，你俩从没说过话）：
import type { Order } from './order.ts';

function print(o: Order) {
  console.log(o.amount);    // 他不知道你改了名
}
```

在 JS 里这行代码**现在不报错**，会在运行时打印 `undefined`，报表一片空白，然后有人来问"这报表为什么是空的"。

在 TS 里，你改完名字的**那一刻**，`tsc` 就会说：

```text
error TS2339: Property 'amount' does not exist on type 'Order'.
```

**注意时间点：不是运行时，是你改完之后立刻。** 这就是类型系统的真正价值——它把"发现错误的时间"从"上线后"提前到了"写代码时"。

**场景二：接手别人的代码，不知道某个字段是什么。**

```js
function calcFee(order) {   // 纯 JS，没有类型
  return order.amount * order.rate;
}
```

你必须去翻 `order` 从哪来、`amount` 是数字还是字符串、`rate` 是 0.1 还是 10。

```ts
function calcFee(order: Order, rate: number): number {
  return order.total * rate;
}
```

**你不需要翻任何其他文件。** 类型就是那份"文档"，而且是一份**不会过期的**文档（过期了 `tsc` 会报错，逼人更新）。

**场景三：重构的时候不敢动。** 纯 JS 里你想把函数的参数从 `(a, b)` 改成 `({a, b})`，你会**非常怂**——不知道有多少人调用了它。有类型的项目里，你直接改，然后跑 `tsc --noEmit`，等它把所有调用点列出来，一个一个改完。**重构从"艺术"变成了"工程"。**

### 为什么是 Google 和 Microsoft

TypeScript 是 Microsoft 造的（Anders Hejlsberg 主导，他也是 C# 和 Delphi 的作者）。它出生时面对的世界是这样的：

- **Google**：Gmail、Google Maps 这种级别的 JS 应用，代码量到了几十万行。他们当时专门搞了一门叫 **Closure Compiler** 带注解的 JS 方言，又搞了 **AtScript**（后来并入 TypeScript）。
- **Microsoft**：Office Web、VS Code、Azure Portal——全是巨型 JS 项目。
- **Facebook**：搞了 **Flow**（另一个 JS 类型检查器），React 早期代码都用它。

**三家巨头在同一个时间段，各自独立地做同一件事：给 JavaScript 加类型。** 这不是巧合。它说明一个事实：**当 JavaScript 项目大到一定程度，"没有类型"从"灵活"变成了"失控"。** 而且是**必然**会失控——不是水平问题，是规模问题。

最后 TypeScript 赢了 Flow，赢的原因之一就是它的**渐进式**策略（标签一）：不要求你重写，可以一点点加。

### 所以"防 bug"只是副产品

- 类型确实能防 bug，但**防的是特定类型**的 bug——主要是"接口不匹配"这类。
- 它防不了逻辑 bug（你算错了公式，类型帮不了你）。
- 它防不了运行时 bug（5.3 节那个 `undefined` 崩溃，类型一点没拦住）。
- 它**真正**防的，是"**团队协作中的信息丢失**"。

配套工程 `tsconfig.json` 里那个 `strict: true`，你现在应该能理解它的意义了：**这不是在给自己找麻烦，这是在给未来的每一个同事省事。**

**一句话记住它：TypeScript 的价值不在于"帮你少写 bug"，而在于"让 100 个人改同一份代码时，约定由机器守着，而不是靠喊话"。**

## 1.9　新手最常有的 5 个误解

这五条，你只要中过一条，学 TS 的路就会走得很难受。逐条破。

### 误解一："TS 能验证运行时数据"

**症状**：以为给变量标了类型，那个数据就"安全"了。

**真相**：类型是**编译期的事**，运行时数据从哪来就是什么样，类型一点都管不着。

```ts
interface Config { port: number }

const cfg = JSON.parse(process.env.CONFIG!) as Config;   // 编译器完全信任
console.log(cfg.port + 1);   // 如果环境变量里没配 port，这里是 NaN
```

**关键认知**：`as Config` 不是"验证"，是"**你说服了编译器闭嘴**"。它一个字节的数据都没检查。

**正确的姿势**：外部数据一律先标成 `unknown`，然后**手写运行时检查**（或用 Zod 这类库）。第 11 章（面试速查表）里有一整块专门讲这个误解。

### 误解二："类型是强制的"

**症状**：以为写了 `name: string`，运行时把数字塞进去，TS 就会拦住。

**真相**：类型检查**只发生在编译期**，而且是**静态的**——它只读你的代码文本，不读你的数据。

```ts
interface User { name: string }

const u = { name: 'Ada' } as User;

// 想删掉 name。直接删会被编译器拦下来：
//     delete (u as Record<string, unknown>).name;
//     error TS2352: Conversion of type 'User' to type 'Record<string, unknown>'
//     may be a mistake because neither type sufficiently overlaps with the other.
//
// 那就再骗它一次（双重断言，第 02 章会讲这个"逃生舱"）：
delete (u as unknown as Record<string, unknown>).name;   // 编译通过
console.log(u.name.toUpperCase());                       // 编译通过，运行时崩
```

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

**注意 `TS2352` 这个报错本身也很有意思**：它在说"`User` 和 `Record<string, unknown>` 形状差太远，我不相信你是认真的"。这是结构化类型系统在做"合理性检查"——**它拦的不是错误，是"看起来像手滑"的转换**。真想做，就得先 `as unknown` 过一道，等于签字画押。

**所以类型的本质是什么？** 是**开发时的一份合约**，不是**运行时的护栏**。它约束的是**你自己和你的同事**，不是**用户和数据**。

### 误解三："类型写得越多越好"

**症状**：每个变量都写注解，每个返回值都写类型。

**真相**：多余的类型注解是**噪音**——它降低可读性，还可能丢掉精度。

```ts
// 噪音版：右边已经写得明明白白
const name: string = 'Ada';
const list: string[] = ['a', 'b'];
const fn = (x: number): number => x * 2;
```

```ts
// 清爽版：编译器都能推出来
const name = 'Ada';
const list = ['a', 'b'];
const fn = (x: number) => x * 2;
```

而且前面说过，手写注解还可能**把精确类型稀释掉**（`"Ada"` → `string`）。

**判断标准**：

- **该写**：函数参数、公共 API 的返回值、你要"收窄"或"约束"的地方、`Object.keys` 之类推太宽的地方。
- **别写**：一眼能看出来的局部变量、能推断的返回类型。

**好品味是写"恰好的"类型，不是写"最多的"类型。**

### 误解四："TS 会让程序变慢"

**症状**：担心加了类型，运行时性能下降。

**真相**：**运行时零开销。** 类型在代码执行前就被完全擦除了，1.4 节的编译产物已经证明了。

- **运行时**：擦除后的 JS 和手写的 JS 性能一模一样。不存在"因为加了类型所以慢"。
- **开发时**：`tsc` 检查确实要花时间（小项目几百毫秒，大项目几秒到几十秒）。
- **`node x.ts` 直跑**：Node 的类型剥离非常快，接近普通 JS 的加载速度。

**唯一真实的代价在"开发流程"上**：编辑器要跑类型检查（吃 CPU 和内存），CI 里多一步 `tsc --noEmit`。**这些是开发成本，不是运行成本。**

顺便说一句：**能"变慢"的反而是编辑器体验**。项目大到一定程度时，VS Code 的类型检查会吃掉几个 G 内存。这也是 TypeScript 7（Go 重写版）要解决的问题——加快的正是**编译和检查速度**。

### 误解五："`any` 是万能的"

**症状**：报错烦了就写 `any`，因为 `any` 什么都能过。

**真相**：`any` 确实能让报错消失，**但它同时会让类型检查在这一点上彻底失效，而且会传染**。

```ts
function parseData(input: any) {
  return JSON.parse(input);
}
```

一旦参数是 `any`：

- 函数体内**任何**属性访问都不检查（`input.foo.bar.baz` 也不报错）。
- 返回值也是 `any`。
- 调用这个函数的人拿到 `any`，他的检查也失效了。
- **传染链一路扩散下去，整个项目的类型安全被这个 `any` 开了个大洞。**

`any` 最恶劣的一点是：**它让"类型检查通过"变成一个假的绿灯。**

**那 `any` 什么时候能用？**

- **迁移期**：把巨型 JS 文件改成 TS，先用 `any` 开路，标记 `// TODO`，后面逐个收紧。
- **类型定义确实有 bug 的第三方库**：临时绕开。
- **测试代码里的 mock**：影响范围可控。

**更好的替代品是 `unknown`**：

| | `any` | `unknown` |
| --- | --- | --- |
| 能赋给任何变量 | 可以 | 不行，必须先收窄 |
| 能读任意属性 | 可以（危险） | 不行，必须先收窄 |
| 能调用 | 可以（危险） | 不行 |
| 安全性 | 关掉了检查 | 保留了检查 |

```ts
function f(a: any) {
  a.foo.bar();          // 编译通过（运行时可能炸）
}

function g(u: unknown) {
  u.foo.bar();          // error TS18046: 'u' is of type 'unknown'.
}
```

**记住这个口诀**：**`any` 是"我不想管"，`unknown` 是"我还不知道"。** 你需要的是后者，不是前者。

**一句话记住它：TS 管不了运行时的数据、类型不是强制的、类型不是越多越好、类型不拖慢程序、`any` 不是解药而是麻药。**

## 1.10　动手练习

别只看，**把下面 5 个都敲一遍**。每个 5 分钟内能完成，而且都会让你"啊，原来是这样"。

### 练习 1：制造一次真实的类型崩溃

写一个文件 `ex01.ts`：

1. 定义 `interface Book { title: string; pages: number }`。
2. 用 `JSON.parse('{"pages":100}')` 造一个**只有 pages 没有 title** 的数据。
3. 用 `as Book` 断言它。
4. 打印 `book.title.length`。
5. 先跑 `npx tsc --noEmit`——**确认它一声不吭**。
6. 再跑 `node ex01.ts`——**看它怎么崩的**。

**要你体会的**：编译器为什么被骗过去了？改成 `unknown` + 手写检查，让它不崩。

### 练习 2：用编译产物证明类型擦除

写一个 `ex02.ts`，塞进这五种东西：

1. 一个 `interface`
2. 一个 `type` 别名
3. 一个带完整注解的函数（参数和返回值都写类型）
4. 一个 `class`（带 `private` 字段）
5. 一行 `as const` 的数组

然后：

```bash
npx tsc --target ES2022 --module ES2022 ex02.ts --outDir out
```

打开 `out/ex02.js`，**逐行对照**，把"哪些消失了、哪些原样保留、哪些被翻译成了别的代码"写成注释。

**要你体会的**：`class` 留下了，`interface` 消失了，`private` 消失了——**为什么？**

### 练习 3：验证 Node 的 strip-only 限制

新建 `ex03.ts`：

```ts
enum Level { Low, High }
console.log(Level.High);
```

1. 跑 `node ex03.ts`，**记下完整报错**（应该包含 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`）。
2. 加开关再跑：`node --experimental-transform-types ex03.ts`。
3. **改成不用 `enum` 的写法**（`as const` 对象 + 联合类型），确认不加开关也能跑。

**要你体会的**：Node 只剪裁不翻译。顺便学会 `enum` 的现代替代写法。

### 练习 4：结构化类型的"惊悚实验"

写 `ex04.ts`：

```ts
class Cat { name = 'cat'; meow() { return 'meow'; } }
class Lion { name = 'lion'; roar() { return 'roar'; } }

const x: Cat = new Lion();     // 会报什么错？
```

1. 跑 `npx tsc --noEmit`，**抄下报错**。
2. 给 `Lion` 加上 `meow()` 方法（返回任意字符串），再检查一次——**这次过了吗？**
3. 把 `Cat` 和 `Lion` 都改成 `interface`，再试一次。
4. 最后给两个类都加一个 `private secret = 1`，再试一次，看报错变成了什么。

**要你体会的**：TS 看的是形状，不是名字。第 4 步那个 `private` 是个例外，想想为什么。

### 练习 5：坏品味改好品味

下面是一段"手写狂"的代码，改成"能推断就不手写"的版本，**同时保证类型不变精也不变粗**：

```ts
const title: string = 'TS 教程';
const version: number = 1;
const tags: string[] = ['typescript', 'tutorial'];
const enabled: boolean = true;

function format(title: string, version: number): string {
  return `${title} v${version}`;
}

const doubled: number[] = tags.map((t: string): string => t.toUpperCase());
```

改完后，**把鼠标悬停在每个变量上**，看 TypeScript 推断出的类型是什么。

**要你体会的**：哪几个注解删了之后类型完全一样？哪几个位置**必须**保留注解？（提示：`tags.map` 里面的箭头函数参数。）

## 本章小结

一句话串起来：

> TypeScript 是 JavaScript 加上一层**写的时候在、跑的时候没**的类型说明。它靠**渐进式**让你慢慢迁移，靠**结构化类型**看形状不看名字，强到能在类型层面算数学。它真正的目标不是防 bug，而是**让大团队改同一份代码时不互相踩踏**。所以记住：运行时数据它管不了，`any` 不是解药，类型不是越多越好，程序不会因为它变慢。

下一章我们开始动真格：把 `tsconfig.json` 那二十几个配置项逐行拆开，让你知道每一个开关在干什么、什么时候该打开。

（本教程每一章的文件名都带章号，正文里提到"第 N 章"时我会带一句主题说明——比如第 02 章是类型基础与推断，第 04 章是联合类型与类型收窄，第 07 章是类、模块与声明文件，第 11 章是面试速查表。如果你手上的目录和这里的章号对不上，按**主题**去索引，不要按编号死记。）
