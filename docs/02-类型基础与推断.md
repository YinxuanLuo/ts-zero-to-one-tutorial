# 第 02 章 · 类型基础与类型推断

> 本章对应代码：`examples/02-类型基础.ts`（可运行）

## 2.1 那个冒号到底是什么？

看这行代码：

```ts
let age: number = 18;
```

`age` 后面的 `: number`，读作：

> "**我把 `age` 这个名字，登记成一个只能装数字的盒子。**"

这是一个**声明**，不是**命令**。

区别在哪？

- 如果是**命令**（比如 Java 的 `int age`），语言必须真的造一个"整数盒子"。
- 它是**声明**——你在告诉编译器"我打算这么用"，编译器帮你记着，谁违反了这个约定就报错。

而这行代码编译出来是：

```js
let age = 18;
```

`number` 消失了。这正是第 00 章说的**可擦除**。

> **一句话记住它：类型注解是你对编译器的一句承诺，不是一条运行时的规则。**

## 2.2 七个原始类型

JS 里本来就有原始类型，TS 把它们照抄过来。

```ts
let s: string = '你好';
let n: number = 42;
let b: boolean = true;
let big: bigint = 100n;
let sym: symbol = Symbol('id');
let u: undefined = undefined;
let nul: null = null;
```

注意这几点，都是新手必踩的：

### 坑 1：`Number` / `String` / `Boolean` 是大写开头的包装对象，**别用**

```ts
const s: string = new String('hi');
```

```text
error TS2322: Type 'String' is not assignable to type 'string'.
  'string' is a primitive, but 'String' is a wrapper object.
  Prefer using 'string' when possible.
```

**规则：永远用小写的 `string` / `number` / `boolean`。**
大写的是 JS 里的包装对象（`new String('x')` 造出来的东西），你几乎永远不需要它。
（有趣的是：`new String('x')` 在 JS 里是个对象，`typeof` 返回 `"object"`，它是真值但 `new Boolean(false)` 也是真值……总之，躲开它。）

### 坑 2：`number` 同时表示整数和小数

TS 没有 `int` / `float` 之分。因为 JS 只有一种数字（IEEE 754 双精度浮点数）。

```ts
let a: number = 1;
let b: number = 1.5;
let c: number = NaN;
let d: number = Infinity;
// 全是合法的 number
```

这意味着 **`number` 类型不能帮你防住"这个字段应该是整数却传了小数"**。
真要区分，得用**品牌类型（Branded Type）**，第 09 章会讲。

### 坑 3：`null` 和 `undefined` 是"单独的类型"

它们是独立的类型，不只是"没有值"。这一点在 `strictNullChecks` 开启后变得极其重要（第 08 章细讲）：

```ts
let name: string = null;
```

```text
error TS2322: Type 'null' is not assignable to type 'string'.
```

**这就是 TS 最值钱的开关之一。**
在 JS 里 `null` 和 `undefined` 能悄悄流进任何变量，然后在某个深夜炸掉你的线上服务。
开了 `strictNullChecks`，编译器会在你写下的那一刻就拦住。

```ts
let name: string | null = null;   // 你得显式承认它可能是 null
```

> **一句话记住它：小写 `string`/`number`/`boolean`；`null` 和 `undefined` 是独立类型，不是"万能兼容"。**

## 2.3 数组与元组：两种"一串东西"

### 数组 `T[]`

```ts
let names: string[] = ['Tom', 'Jerry'];
let scores: Array<number> = [90, 85];   // 另一种写法，完全等价
```

`string[]` 和 `Array<string>` 是同一个东西。**用哪个都行，团队统一就好**（前端圈更流行 `string[]`，因为它短）。

数组的关键性质：**所有元素的类型必须一样。**

```ts
const mixed = [1, 'a'];
//    ^? 类型是 (string | number)[]
```

TS 推断出的是"这个数组里可能装 string 也可能装 number"（联合类型，第 04 章细讲）。

```ts
const onlyNums: number[] = mixed;
```

```text
error TS2322: Type '(string | number)[]' is not assignable to type 'number[]'.
  Type 'string | number' is not assignable to type 'number'.
    Type 'string' is not assignable to type 'number'.
```

**读错误信息的技巧**：从最后一行往上读。最后一行才是最具体的原因：
`Type 'string' is not assignable to type 'number'` —— 哦，原来是有个 string 混进来了。

### 只读数组 `readonly T[]`

```ts
const ro: readonly number[] = [1, 2];
ro.push(3);
```

```text
error TS2339: Property 'push' does not exist on type 'readonly number[]'.
```

注意错误不是"你不能改它"，而是 "**`readonly number[]` 上根本没有 `push` 这个方法**"。

这个措辞很 TS：**它不禁止你，它直接让"改"这个动作在类型上不存在。**

`readonly T[]` 是给函数参数用的神器——你告诉调用者"我保证不动你的数组"：

```ts
function sum(nums: readonly number[]): number {
  // nums.push(1);   // 想写也写不了
  return nums.reduce((a, b) => a + b, 0);
}

const myNums = [1, 2, 3];
sum(myNums);        // 普通数组能传给 readonly 参数
// 反过来不行，这是好事
```

> **一句话记住它：`readonly T[]` 用在函数参数上，是对调用者的承诺——"我不改你的数据"。**

### 元组 `[T1, T2]`：定长、定类型的"一串东西"

数组是"一堆同类东西"，元组是"**固定几个、每个位置类型不同**"。

```ts
let pair: [string, number] = ['Tom', 18];
const name = pair[0];    // string
const age = pair[1];     // number
```

**元组按位置记住类型**，这是它和数组的本质区别。

```ts
pair[0] = 1;
```

```text
error TS2322: Type 'number' is not assignable to type 'string'.
```

越界访问也会被拦：

```ts
let t: [number, number] = [1, 2];
const oob = t[5];
```

```text
error TS2493: Tuple type '[number, number]' of length '2' has no element at index '5'.
```

**这是 TS 里唯一能防数组越界的地方。** 普通数组 `arr[999]` 不报错（因为类型是 `number`，不是 `number | undefined`——除非你开了 `noUncheckedIndexedAccess`，第 08 章讲）。

**元组最常见的实战场景：`useState` 和 `Promise.all`**

```ts
// React 的 useState 返回的就是元组
const [count, setCount] = useState(0);
//     ^? number      ^? (v: number) => void

// Promise.all 返回的也是元组，位置对得上
const [user, posts] = await Promise.all([fetchUser(), fetchPosts()]);
//     ^? User        ^? Post[]
```

> **一句话记住它：数组是"一堆"，元组是"几个"——元组记住了每个位置该放什么。**

## 2.4 对象类型：描述"形状"

```ts
let user: { name: string; age: number } = { name: 'Tom', age: 18 };
```

`{ name: string; age: number }` 就是"**形状描述**"：
"这东西有两个属性，`name` 是字符串，`age` 是数字"。

分隔符用 `;` 或 `,` 都行，**惯例是 `;`**。

### 对象字面量的"多余属性检查"

这是个新手一定会撞上的行为：

```ts
type Point = { x: number; y: number };

const p: Point = { x: 1, y: 2, z: 3 };
```

```text
error TS2353: Object literal may only specify known properties,
  and 'z' does not exist in type 'Point'.
```

但奇怪的是，这样写就不报错：

```ts
const tmp = { x: 1, y: 2, z: 3 };
const p2: Point = tmp;      // ✅ 通过！
```

**为什么同样是多一个 `z`，一个报错一个不报？**

因为 TS 有个专门的机制叫**多余属性检查（excess property check）**，
它**只在你直接写对象字面量**的时候生效。

设计理由：写 `{ x: 1, y: 2, z: 3 }` 这种字面量时，你心里想的就是"造一个 Point"。
多写的 `z` 极大概率是**拼写错误**（比如 `naem` 而不是 `name`），所以 TS 要帮你抓。

而 `tmp` 是一个**已经存在的变量**，TS 走的是普通的"结构兼容"判断：
`tmp` 的形状包含 `Point` 需要的所有东西，那就兼容。

> 这是**面试高频题**："为什么对象字面量会触发多余属性检查？"
> 答：因为字面量是"当场构造"，多出的属性几乎必然是笔误；而变量赋值是"结构兼容"，宽一点是合理的。

### 对象属性的可选与只读

```ts
type Config = {
  readonly apiUrl: string;    // 只读：初始化后不能改
  timeout?: number;           // 可选：可以没有
};

const cfg: Config = { apiUrl: 'https://x.com' };
cfg.apiUrl = 'https://y.com';
```

```text
error TS2540: Cannot assign to 'apiUrl' because it is a read-only property.
```

`?` 的意思是 `number | undefined`，所以用它之前要处理 `undefined`：

```ts
const t = cfg.timeout ?? 3000;   // OK
const bad = cfg.timeout + 1;
```

```text
error TS18048: 'cfg.timeout' is possibly 'undefined'.
```

> **一句话记住它：对象类型描述"形状"；字面量赋值会被额外检查多余属性，这是为了抓拼写错误。**

## 2.5 四个特殊类型：any / unknown / never / void

这四个是 TS 里最容易被误解的。我按"该不该用"的顺序讲。

### 2.5.1 `unknown`：安全的"我不知道"

想象你从外面收到一个包裹，你不知道里面是什么。

```ts
function handle(input: unknown) {
  input.toUpperCase();
}
```

```text
error TS18046: 'input' is of type 'unknown'.
```

`unknown` 的意思是："**这东西是什么我完全不知道，所以在你证明它是什么之前，你什么都不能对它做。**"

想用它？先**收窄**（narrowing，第 04 章的主角）：

```ts
function handle(input: unknown) {
  if (typeof input === 'string') {
    // 这里 TS 已经知道 input 是 string 了
    return input.toUpperCase();
  }
  if (typeof input === 'number') {
    return input.toFixed(2);
  }
  return String(input);
}
```

**`unknown` 是"有纪律的 any"。** 它把所有不确定性都逼到明面上，而你只需要用 `if` 把这个不确定性消掉。

**实战场景**：所有从外部来的东西都应该标成 `unknown`。

```ts
// ✅ 好品味
async function loadUser(id: string): Promise<unknown> {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
}

// ❌ 坏品味：假装知道
async function loadUserBad(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return res.json();   // 编译器信你，但它不该信你
}
```

### 2.5.2 `never`：不可能发生

`never` 是"一个值都不包含的类型"。

**它只出现在两种地方：**

**场景 A：永远不返回的函数**

```ts
function fail(msg: string): never {
  throw new Error(msg);
}
```

为什么不是 `void`？因为 `void` 是"返回了，但没返回值"，而 `never` 是"**根本回不来**"。

**场景 B：被穷尽后的分支**（这个更有用）

```ts
type Status = 'loading' | 'success' | 'error';

function assertNever(x: never): never {
  throw new Error(`未处理的状态: ${x}`);
}

function render(s: Status): string {
  switch (s) {
    case 'loading': return '加载中';
    case 'success': return '成功';
    case 'error':   return '失败';
    default: return assertNever(s);   // 走到这里 s 只能是 never
  }
}
```

**好处**：以后你给 `Status` 加了 `'cancelled'`，这个函数**立刻编译报错**，提醒你漏了一个分支。

**这是整份教程里最值得养成的一个习惯。** 它把"忘记处理新分支"这种运行时事故，变成了编译期的红灯。

试试看，`never` 不能被赋值：

```ts
const x: never = 1;
```

```text
error TS2322: Type '1' is not assignable to type 'never'.
```

因为 `never` 里一个值都没有，你当然放不进去任何东西。

### 2.5.3 `void`：函数"不返回值"

```ts
function logIt(): void {
  console.log('hi');
}
```

```ts
function bad(): void {
  return 1;
}
```

```text
error TS2322: Type 'number' is not assignable to type 'void'.
```

`void` 有个**反直觉但很有用的特性**：它容忍"返回值被忽略"。

```ts
const nums = [1, 2, 3];

// forEach 的回调签名是 (v: number) => void
nums.forEach((n) => {
  return n * 2;       // 你返回了东西，但没人要，TS 不报错
});
```

为什么允许？因为 `forEach` 的设计意图就是"我不关心你的返回值"。
这个特性叫 "**返回值的位置不参与检查**"，是刻意设计的，让 `() => void` 能接受任何函数。

### 2.5.4 `any`：逃生舱，会传染

```ts
const data: any = JSON.parse('{}');

data.foo.bar.baz();          // 通过
const n: number = data;      // 通过
const s: string = data;      // 通过
const x: 这个类型不存在 = data; // 还是通过
```

`any` 是**双向黑洞**：任何东西都能变成 `any`，`any` 也能变成任何东西。

**`any` 最可怕的不是它自己，是它会传染：**

```ts
type User = { name: string };

function getUser(id: string): any {
  return { name: 'Tom' };
}

const u: User = getUser('1');
//    ^? 类型是 User（你以为的）
//       实际上 u 的真实类型是 any
u.name.toUpperCase();    // 编译通过
u.nmae.toUpperCase();    // 编译也通过！拼错了也不报错
```

**一个 `any` 让下游所有类型检查全部失效。**

所以：

| 类型 | 什么时候用 | 危险程度 |
|---|---|---|
| `unknown` | **外部数据**（API、JSON、localStorage、catch 变量） | 安全 |
| `any` | 迁移旧 JS 时的临时逃生舱 | 危险，会传染 |
| `never` | 穷尽检查、永不返回的函数 | 安全 |
| `void` | 不关心返回值的回调 | 安全 |

**记住一句话：能用 `unknown` 就不要用 `any`。**

如果你在 code review 看到 `any`，正确反应是问一句："这里为什么不能是 `unknown`？"

> **一句话记住它：`unknown` 是"我不知道，你别乱动"；`any` 是"我不知道，你随便动"——后者是灾难的开始。**

## 2.6 类型推断：TS 的第一哲学

现在讲这一章真正的重点。

### 核心原则

> **能推断出来的类型，就不要手写。**

TS 官方文档的第一句话级别的建议就是这句。原因有两个：

1. **手写的类型会过期。** 你把函数改了，忘记改类型注解，就会出现"注解和实现不一致"，而且编译器不一定能发现。
2. **手写的类型会骗人。** 你以为你写的是准确描述，实际上你只是给编译器下了一个断言。

### 推断的三种场景

**场景 1：变量初始化推断**

```ts
let a = 1;              // number
const b = 1;            // 字面量类型 1（const 不能改，所以范围就锁死了）
let c = 'hello';        // string
const d = 'hello';      // 字面量类型 "hello"
let e = [1, 2, 3];      // number[]
const f = { x: 1 };     // { x: number }
let g = null;           // any（strictNullChecks 下是 null）
```

注意 `let` 和 `const` 的区别：
`let b = 1` 推断成 `number` 而不是 `1`，因为 `let` 后面可能改成 2。
`const d = 'hello'` 推断成 `"hello"`，因为它永远是这个值。

**这个差异非常重要**，第 04 章的字面量类型全靠它。

**场景 2：函数返回值推断**

```ts
function add(a: number, b: number) {
  return a + b;
}
// 返回类型被推断为 number，你不用写
```

**那函数返回值到底该不该手写？**

我的建议（也是社区主流）：

- **导出的公共函数：写。** 因为它是你的 API 契约，改动应该是显式的。
- **内部的小函数：不写。** 让它推断，省事。

```ts
// 公共 API：显式写，改动时你会意识到这是破坏性变更
export function parseDate(input: string): Date { /* ... */ }

// 内部工具：让它推断
const double = (n: number) => n * 2;
```

**场景 3：上下文推断（Contextual Typing）—— 最有意思的一种**

这是新手最容易"感觉 TS 有魔法"的地方：

```ts
const nums = [1, 2, 3];

nums.map((n) => n * 2);
//        ^? n 自动是 number，你没写任何类型
```

`n` 的类型是从哪来的？**是从 `map` 的签名"倒推"回来的。**

```ts
// Array<number>.map 的签名大致是：
// map<U>(callback: (value: number, index: number, array: number[]) => U): U[]
```

因为 `nums` 是 `number[]`，所以 `map` 知道回调的第一个参数一定是 `number`。
**它把这个类型"灌"进了你写的箭头函数里。**

再看一个更明显的：

```ts
window.addEventListener('click', (e) => {
  //                        ^? e 自动是 MouseEvent
});

window.addEventListener('keydown', (e) => {
  //                        ^? e 自动是 KeyboardEvent
});
```

**你一个字都没写，但 `e` 的类型随事件名变化。** 这就是上下文推断。

**理解上下文推断的价值**：它解释了你为什么"大部分时候不用写类型"。
TS 不是靠你标注，而是靠它自己**顺藤摸瓜**。

### 推断的极限：什么时候必须手写

**函数参数几乎总是要写**（除非有上下文）：

```ts
function f(a, b) { return a + b; }
```

```text
error TS7006: Parameter 'a' implicitly has an 'any' type.
error TS7006: Parameter 'b' implicitly has an 'any' type.
```

因为函数可能被任何人、用任何方式调用，TS **无从推断**参数会是什么。
所以 `noImplicitAny` 会强制你写出来——**这是好意，它在防止你的函数变成一个 `any` 黑洞。**

**空数组 / 空对象**：

```ts
const arr = [];        // any[]
arr.push(1);
arr.push('a');         // 都不报错，因为元素类型是 any
```

这时候用**类型断言**或**显式注解**：

```ts
const arr: string[] = [];     // ✅ 推荐
```

> **一句话记住它：TS 的第一哲学是"能推断就不写"。上下文推断是它最聪明的地方——你写的箭头函数参数类型，往往是它从调用点倒推给你的。**

## 2.7 写类型的品味：一张对照表

这部分没有绝对对错，但照着做不会错。

| 场景 | 建议 | 例子 |
|---|---|---|
| `const` / `let` 局部变量 | **不写**，让它推断 | `const n = 1` ✅ / `const n: number = 1` ❌ |
| 函数参数 | **必须写** | `function f(a: string)` |
| 导出的函数返回值 | **写**（API 契约） | `export function f(): User` |
| 内部函数返回值 | 不写 | `const f = () => 1` |
| 空数组 / 空对象 | **写** | `const a: User[] = []` |
| 对象字面量 | **不写**（用 `satisfies`，见第 06 章） | `const c = { x: 1 }` |
| 从外部来的数据 | 标成 `unknown` | `res.json(): Promise<unknown>` |
| 复杂的泛型类型 | **抽成 `type` 起个名字** | `type Result<T> = ...` |

**最后一个特别重要**：

```ts
// ❌ 一眼看不懂
function f(cb: (e: Error | null, data: Record<string, string[] | number>) => void) {}

// ✅ 起个名字，代码立刻能读
type Handler = (e: Error | null, data: Record<string, string[] | number>) => void;
function f(cb: Handler) {}
```

> **一句话记住它：类型的价值在于"让人看懂"，不在于"让编译器满意"。起名字是最高性价比的类型技巧。**

## 2.8 `type` 别名：给类型起名字

```ts
type ID = string | number;
type Point = { x: number; y: number };
type Callback = (err: Error | null) => void;

let userId: ID = 1;
userId = 'abc';    // 也合法，因为 ID 是联合类型
```

`type` 只是**起别名**，它不创建新类型。

`type` 能表达的东西很多，包括下一章要讲的联合、交叉，以及第 06 章的函数类型、条件类型。

**`type` 和 `interface` 的区别是个超高频面试题**，我们在第 03 章详细对比。这里先记住：

- 描述**对象形状**：两个都能用，社区习惯用 `interface`。
- 描述**联合类型、元组、函数、工具类型**：只能用 `type`。

---

## 2.9 本章常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 用了大写 `String`/`Number` | `Type 'String' is not assignable to type 'string'` | 改小写 |
| 空数组推断成 `any[]` | 塞什么进去都不报错 | 显式写 `const a: T[] = []` |
| 函数参数没写类型 | `TS7006: implicitly has an 'any' type` | 补上类型 |
| 对象字面量多个字段 | `TS2353` | 检查拼写，或去掉多余字段 |
| 忘了处理 `undefined` | `TS18048: possibly 'undefined'` | 用 `??` 或先收窄 |
| `any` 传染 | 拼写错误也不报错 | 换成 `unknown` |
| 用了 `readonly` 数组还想 push | `TS2339: Property 'push' does not exist` | 复制一份再改，或改签名 |

## 2.10 本章小结

```
七个原始类型 ──── string / number / boolean / bigint / symbol / null / undefined
     │            用小写；null 和 undefined 是独立类型
     │
数组 vs 元组 ──── string[] 是"一堆"；[string, number] 是"几个"
     │            readonly T[] 用在参数上，是对调用者的承诺
     │
对象类型 ──────── 描述"形状"；字面量赋值会做多余属性检查
     │
四个特殊类型 ──── unknown（安全）/ any（危险且传染）/ never（穷尽检查）/ void
     │
类型推断 ──────── 能推断就不写；上下文推断是它最聪明的地方
```

**三句话带走：**

1. **能推断就不写。** 手写类型是负债，不是资产。
2. **外部数据一律 `unknown`。** 把 `any` 当成 bug 来看待。
3. **`never` 穷尽检查**是你最该养成的习惯，它把运行时事故变成编译期红灯。
