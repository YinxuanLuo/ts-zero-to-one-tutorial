# 第 07 章　类与面向对象 + 模块系统 + 声明文件
> 本章对应代码：`examples/07-类与模块.ts`（可运行）

这一章有三块内容：**类**、**模块**、**声明文件**。它们看起来没关系，其实是同一条线索上的三站：

- 你在写**类**的时候，会发现 TS 给 `class` 加了一堆 JS 没有的修饰符（`private`、`readonly`、`abstract`……）。这些东西**全是编译期的**，运行时不存在。理解这一点，就理解了整个 TS 的世界观。
- 既然大部分东西运行时都不存在，那**哪些 import 会真的被加载、哪些会凭空消失**，就变成了必须搞清楚的事。这就是**模块**那一节。
- 而那些"凭空消失"的类型，TS 是从哪知道它们的？别人写的 JS 库没有类型，TS 怎么知道怎么补？这就是**声明文件**。

一句话串起来：**类让你看到"类型是编译期的"，模块让你看到"类型会被擦除"，声明文件让你看到"类型从哪来"。**

# A. 类

## A.0 先搞清楚：类声明其实同时造了两个东西
`class Foo {}` 这一行代码，同时创造了两样东西：

- **一个值**：运行时真实存在的构造函数 `Foo`，`new Foo()` 和 `instanceof Foo` 用它。
- **一个类型**：只在编译期存在的类型 `Foo`，`const x: Foo` 用它。

用大白话说：**类是"工厂"和"图纸"的同名双胞胎。** 工厂是实体的（能造东西），图纸是纸上的（只能对着检查）。
**生活类比：一家餐馆的招牌。** 招牌挂在那儿（值），你指着招牌说"我要一份招牌菜的规格"（类型）。你可以 `new` 这个招牌指向的餐馆，但不能 `new` "规格"。
正因为这层双胞胎关系，后面很多"为什么这么写"才有答案：`implements` 后面只能跟**类型那一半**，`instanceof` 后面只能跟**值那一半**。
**一句话记住它：`class` 同时产出一个值和一个类型，前者运行时在，后者编译后消失。**


## A.1 四种可见性修饰符：public / private / protected / readonly
### 它解决什么问题
JS 里的对象字段是"裸奔"的：任何拿到对象的人都能随便读写任何字段。项目一大，你就没法表达"这个字段是内部实现，别从外面改"。TS 给了四种修饰符来表达这件事。
注意：**这四种都是"类型层面的门禁"**，不是运行时的大门。后面 A.2 会专门讲这个落差。
### 逐个讲
**`public`（公开）**：谁都能访问。**这是默认值**，你不写就是它。写出来只是为了"显式表达意图"，很多团队要求必须写全。
**`private`（私有）**：只有**声明它的这个类自己的方法内部**能访问。子类不行，外部不行。
**`protected`（受保护）**：这个类自己 + 它的**子类**能访问。外部不行。它比 `private` 松一档，专门给"想给子类用，但不想给外人用"的东西。
**`readonly`（只读）**：注意，它和上面三个**不是同一类东西**。上面三个管的是"谁能看见"，`readonly` 管的是"能不能改"。一个字段可以同时是 `public readonly`。
`readonly` 的规则很干脆：**只能在两个地方赋值——声明的时候、或者构造函数里**。出了构造函数，任何赋值都是编译错误。
### 可运行代码

```ts
class Employee {
  public name: string;         // 默认就是 public，写出来是给同事看的
  private salary: number;      // 只有类内部能碰
  protected department: string; // 自己 + 子类能碰
  readonly id: string;         // 只能在声明处或构造函数里赋值
  constructor(name: string, salary: number, department: string, id: string) {
    this.name = name;
    this.salary = salary;
    this.department = department;
    this.id = id;              // ✅ 构造函数里可以给 readonly 赋值
  }
  public giveRaise(percent: number): number {
    this.salary = Math.round(this.salary * (1 + percent / 100)); // ✅ 类内部能改 private
    return this.salary;
  }
}
class Manager extends Employee {
  public leadTeam(): string {
    return `${this.name} 管理 ${this.department}`; // ✅ 子类能读 protected
    // return this.salary;  // ❌ private 连子类都不给
  }
}
```

### 真实报错
❌ 你可能这么写（在类外面改 `readonly`）：

```ts
const alice = new Employee('Alice', 20000, '研发部', 'E-001');
alice.id = 'E-999';
```
```text
error TS2540: Cannot assign to 'id' because it is a read-only property.
```
❌ 你可能这么写（在类外面读 `private`，或者子类里读父类的 `private`，报错一样）：

```ts
console.log(alice.salary);
class Manager extends Employee {
  show(): number {
    return this.salary;
  }
}
```
```text
error TS2341: Property 'salary' is private and only accessible within class 'Employee'.
```
**防坑提示**：这个码是 **TS2341**，不是你常见的 TS2339（"属性不存在"）。因为 `private` 成员**是存在的**，只是"你无权访问"，TS 特意用不同的码区分这两种情况——面试说出来很加分。
❌ 你可能这么写（类外面读 `protected`）：

```ts
console.log(new Employee('A', 1, 'B', 'C').department);
```
```text
error TS2445: Property 'department' is protected and only accessible within class 'Employee' and its subclasses.
```

### `readonly` 和 JS 的 `Object.freeze` 有什么区别
三层差别。
**第一层：深度。** `readonly` 是**浅的、按属性来的**，而且只锁"重新赋值"这个动作：

```ts
type User = { readonly id: string; tags: string[] };
const u: User = { id: '1', tags: [] };
u.id = '2';        // ❌ 编译报错
u.tags.push('a');  // ✅ 合法！数组内容改了，但没"重新赋值"
```
想连数组内容也锁住，得写 `readonly string[]`（只读数组类型）——这是**两个不同的 `readonly`**：一个在属性上，一个在类型构造器上。`Object.freeze` 也是浅的（只冻结第一层，嵌套对象不冻结，这是 JS 最经典的坑之一）。
**第二层：时间。** `readonly` 在**编译期**，编译完就消失，运行时的对象上根本没有"只读"这回事。`Object.freeze` 在**运行时**真切地改了对象行为（注意：**严格模式下**写冻结属性抛 `TypeError`，**非严格模式下静默失败**——另一个经典坑）。
**第三层：能不能绕过。** `readonly` 用一个 `as` 断言就能绕过；`Object.freeze` 靠类型系统绕不过去，因为它真的是运行时行为。示例文件里真的跑了一遍：

```ts
(alice as { id: string }).id = 'E-HACKED'; // 编译通过，运行时真的改掉了
```
```text
readonly 被类型断言绕过后的 id: E-HACKED
```
**这就是本章要你反复体会的那件事：TS 的类型是"护栏"，不是"牢笼"。它能拦下无意的错误，拦不下故意的绕过。**
**一句话记住它：`public/private/protected` 管"谁能看见"，`readonly` 管"能不能改"，四个都是编译期的门禁，运行时不设防。**


## A.2 关键哲学：TS 的 private 是"约定"，`#` 才是"法律"
**这一节是本章最重要的地方。如果你只记住一节，就记这节。**
### 为什么会有这个落差
回到最根本的事实：**TS 编译完，类型全部被擦掉，剩下的就是普通 JS。** 那 `private` 这个词编译后去哪儿了？答案是：**哪儿也没去，它消失了。** 所以运行时怎么"拦"你？答案是：**拦不住，它压根没打算拦。**
TS 的 `private` 本质上是**一句写在代码里的承诺**——"我（作者）声明这是内部实现，请你（使用者）别碰"。编译器帮你监督（你碰了就报错），但编译一结束，监督就下班了。
而 JS 后来（ES2022）加了真私有字段，语法是 `#` 开头。它不是"约定"，是**语言层面的硬规则**：`#secret` 这个标识符在词法分析阶段就不允许出现在类外面。
**生活类比**：
- TS 的 `private` = **办公室门上贴的"闲人免进"**。门没锁，贴纸只是提醒，你不看贴纸推门就进去了。
- JS 的 `#` = **保险柜**。门上没把手，你手都不知道往哪放。
### 并排对照代码

```ts
// 左边：TS 的 private —— 编译期的约定
class SecretBox {
  private secret = 'TS 的 private 秘密';
  read(): string {
    return this.secret;
  }
}
const box = new SecretBox();
console.log(box.read());              // ✅ 'TS 的 private 秘密'
// console.log(box.secret);           // ❌ 编译报错
console.log((box as any).secret);     // ✅ 编译通过，运行时也真的读到了！
console.log(Object.keys(box));        // ['secret'] ← 它是个真属性，只是类型层藏了名字
```
```ts
// 右边：JS 的 # —— 运行时的真私有
class RealPrivateBox {
  #secret = '真·私有秘密';
  read(): string {
    return this.#secret;
  }
}
const realBox = new RealPrivateBox();
console.log(realBox.read());                      // ✅ '真·私有秘密'
// console.log(realBox.#secret);                  // ❌ 编译报错
// console.log((realBox as any).#secret);         // ❌ 连这样写都不行，见下文
console.log(Object.getOwnPropertyNames(realBox)); // [] ← 反射 API 完全看不见它
```

### 真实报错
❌ 你可能这么写（用 `#` 但想在类外面读）：

```ts
const realBox = new RealPrivateBox();
console.log(realBox.#secret);
```
```text
error TS18013: Property '#secret' is not accessible outside class 'RealPrivateBox' because it has a private identifier.
```
关键差别：**`#secret` 不是"属性名"，而是语法上被限制的标识符**，所以 `(realBox as any).#secret` 连语法关都过不去：

```text
error TS18016: Private identifiers are not allowed outside class bodies.
```
那 `#secret` 就绝对安全了吗？也不是。`#` 防的是"从外面按名字拿"，防不了"把类里的方法偷出来换掉它的 `this`"。示例文件里我特意演示了这一点：

```ts
// 把原型上的方法偷出来当普通函数，this 换成一个空对象
const stolen = (RealPrivateBox.prototype as any).read as () => string;
try {
  stolen.call({});
} catch (error) {
  console.log('运行时真的抛错了:', (error as Error).message);
}
```
```text
运行时真的抛错了: Cannot read private member #secret from an object whose class did not declare it
```
再看反射上的对比，差别非常直观：

```text
实例自有属性名（#）： []                 ← 完全看不见
TS private 的自有属性名： ["secret"]     ← 明明白白摆在那儿
```

### 那到底该用哪个
给你一条能直接落地的规则：

- **想要真正的封装（存密码、存内部校验状态）→ 用 `#`。** 它是硬的，不可能被 `as any` 绕过。
- **只是想让团队别乱用内部细节 → 用 `private`。** 子类/测试里实在需要时一个 `as any` 还能救急，而且它出现在 `Object.keys` 里，序列化、调试更顺手。
- **不要混着用来表达同一件事**，一个类里两套风格会让同事困惑。
- **一个实际影响**：`#` 字段在 `JSON.stringify` 里**永远不出现**，`private` 字段**会**。对象要 `JSON.stringify` 发到后端时，用 `private` 可能反而"灾难性地方便"——这正是数据泄露的经典来源。

**一句话记住它：TS 的 `private` 是门上贴的纸条，JS 的 `#` 是保险柜；纸条挡君子，保险柜挡所有人。**


## A.3 构造函数参数属性（`constructor(public name: string)`）
### 它解决什么问题
写一个类，你可能要重复三遍同一件事：声明属性、声明参数、赋值。

```ts
class User {
  public name: string;      // 第 1 遍：声明属性
  private age: number;
  constructor(name: string, age: number) {  // 第 2 遍：声明参数
    this.name = name;       // 第 3 遍：赋值
    this.age = age;
  }
}
```
TS 觉得太啰嗦，于是给了一个简写：**在构造函数参数前面直接写修饰符**，这个简写叫**参数属性（parameter properties）**。一行干三件事。

```ts
class User {
  constructor(
    public name: string,   // 同时声明了 public name: string 属性
    private age: number,   // 同时声明了 private age 属性
    readonly id: string,   // readonly 也能这么用
  ) {}
}
const u = new User('小明', 18, 'U-1');
console.log(u.name);       // '小明'
// console.log(u.age);     // ❌ 编译报错：private
// u.id = 'U-2';           // ❌ 编译报错：readonly
```
**好处**：少写 60% 的样板代码。NestJS、TypeORM 里到处都是它，因为那些框架的构造函数就是"依赖注入清单"。
**代价**：可读性差一点（`constructor(private readonly a: A, private readonly b: B) {}` 里塞了 6 个信息），以及下面这个硬事实。
### 关键事实：Node 直接跑 `.ts` 时，参数属性会报错
Node.js v24 可以直接 `node xxx.ts`，靠的是**类型擦除（type stripping）**：把类型标注当空气删掉，剩下的当 JS 跑。这个做法有个硬限制：**它只能"删"，不能"改"。**
参数属性正好踩线：`constructor(public name: string) {}` 如果只删掉 `public name: string`，就变成 `constructor() {}`——**赋值那一步没了**。要保持语义必须"生成"新代码（`this.name = name`），这就超出擦除的能力范围。
❌ 你可能这么写：

```ts
class User {
  constructor(public name: string, private age: number) {}
  info(): string {
    return `${this.name}/${this.age}`;
  }
}
console.log(new User('A', 1).info());
```
```text
node:internal/modules/typescript:68
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript parameter property is not supported in strip-only mode
    at parseTypeScript (node:internal/modules/typescript:68:40)
    ...
```
注意关键词：**`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`** 和 **`strip-only mode`**。
### 同类语法一共三个：enum、namespace、参数属性
Node 的 strip-only 模式明确不支持这三种"带运行时语义"的 TS 语法。enum 也一样（下面是我真跑出来的）：
❌ 你可能这么写：

```ts
enum Color {
  Red,
  Green,
}
console.log(Color.Red);
```
```text
node:internal/modules/typescript:68
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
    at parseTypeScript (node:internal/modules/typescript:68:40)
    ...
```
第三种是 `namespace`（同样报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`）。
### 正确写法（两种）
**方案一：加 `--experimental-transform-types`**，让 Node 从"只删"升级到"真的转换"。

```bash
node --experimental-transform-types some-file.ts
```
能跑通，但会打一条 `ExperimentalWarning: Transform Types is an experimental feature`，生产环境慎用。
**方案二（推荐）：干脆不用这三种语法。**

- `enum` → 用 `as const` 对象 + `typeof`（第 06 章讲过，本章示例文件也用了）：
  ```ts
  const Channel = { Wechat: 'wechat', Alipay: 'alipay' } as const;
  type Channel = (typeof Channel)[keyof typeof Channel]; // 'wechat' | 'alipay'
  ```
- 参数属性 → 老老实实"显式声明 + 构造函数赋值"（本章示例文件就是这么写的）。
- `namespace` → 基本不用了，ESM 模块已取代它，你只会在老代码和声明文件里见到。
### 为什么这么设计
这不是 bug，是**刻意划的线**：能擦除的语法 = 零成本跑 = 放心用；不能擦除的语法 = 需要真正的转换器 = 你得清楚自己付了什么代价。换句话说，**Node 的 strip-only 限制其实在帮你区分"类型层面的 TS"和"会改变运行时代码的 TS"**——这个区分能力，是判断一个人是不是真懂 TS 的分水岭。
顺带说一句：`pnpm exec tsc` 编译这三种语法完全没问题（它就是"真转换器"）。这是 Node 的运行时限制，不是 TS 的限制。
**一句话记住它：参数属性能省三遍字，但它是"会生成代码"的 TS 语法，Node 直接跑 `.ts` 时不认——和 `enum`、`namespace` 一样。**
## A.4 `abstract` 抽象类：为什么需要它
### 它解决什么问题
假设你要写几种支付渠道，它们都有"支付"这个动作，但每一种的支付步骤完全不同。你希望：

1. 调用方只写一句 `channel.pay(199)`，不用管是哪个渠道（**统一入口**）。
2. 有些步骤所有渠道都一样（比如"金额必须大于 0"的校验），不想每个子类抄一遍（**复用**）。
3. 有些步骤只有子类知道，但你必须强迫每个子类都实现，漏一个都不行（**强制契约**）。

`interface` 能满足 3，能满足 1 的"形状"，但它满足不了 2——**接口不能带实现**。这时候就需要**抽象类**：它是一份**半成品**，一部分写好了（具体方法），一部分留着给子类填（抽象方法）。
**生活类比：公司的报销单模板。** 模板上印好了抬头、部门、日期（具体部分，你直接用），但"金额"和"事由"是空的（抽象部分，必须你自己填）。而且公司明确规定：**不许交一张空模板上来**——所以你不能 `new` 抽象类。
### 三个关键规则

```ts
abstract class Shape {
  readonly name: string;
  constructor(name: string) {
    this.name = name;
  }
  abstract area(): number;   // 抽象方法：只有签名，没有函数体
  describe(): string {       // 具体方法：所有子类继承
    return `${this.name} 的面积是 ${this.area().toFixed(2)}`;
  }
}
```
1. **抽象方法没有 `{}`**，只有签名，而且**必须以 `;` 结尾**（不能写 `= 0` 之类的默认值）。
2. **抽象类不能 `new`**。
3. **子类必须实现所有抽象方法**，否则子类也必须是抽象的。
### 真实报错
❌ 你可能这么写（直接 `new` 抽象类）：

```ts
abstract class Shape {
  abstract area(): number;
}
new Shape();
```
```text
error TS2511: Cannot create an instance of an abstract class.
```
❌ 你可能这么写（子类忘了实现抽象方法）：

```ts
class Circle extends Shape {
  // 忘了写 area()
}
```
```text
error TS2515: Non-abstract class 'Circle' does not implement inherited abstract member 'area' from class 'Shape'.
```
这两条错误就是抽象类的全部价值：**把"忘了写"从运行时崩溃，提前到编译时报错。**
### 模板方法模式与钩子方法
注意上面 `describe()` 里调用了 `this.area()`：`describe` 在父类里定义，`area` 在子类里实现——**父类用"未来的子类实现"来组织自己的逻辑**。这个套路叫**模板方法模式（Template Method）**，是抽象类存在的最大理由。本章示例里的支付渠道就是这么写的：

```ts
abstract class PayChannel {
  abstract readonly kind: Channel;
  abstract readonly displayName: string;
  /** 模板方法：定义流程骨架 */
  async pay(amount: number): Promise<PayResult> {
    if (amount <= 0) {
      return { ok: false, tradeNo: '', message: '金额必须大于 0' };
    }
    const tradeNo = await this.doPay(amount); // ← 这一步交给子类
    return { ok: true, tradeNo, message: `${this.displayName} · 支付成功` };
  }
  /** 只有子类知道怎么扣钱 */
  protected abstract doPay(amount: number): Promise<string>;
}
```
子类只需要关心 `doPay` 一件事（"怎么扣钱"），"金额校验、包装结果"这些流程骨架白送。**这就是"框架调用你，而不是你调用框架"（好莱坞原则）。**
抽象类里还可以放"**有默认实现、子类可选覆盖**"的方法，它介于"抽象方法"和"具体方法"之间，叫**钩子方法（hook）**：

```ts
protected detail(): string {
  return '通用形状'; // 默认实现，子类想改就改
}
```
本章示例里 `Circle` 和 `Rect` 都覆盖了 `detail()`，于是 `describe()` 的输出自动带上了各自的细节。**这是"可选扩展点"的标准做法**：抽象方法是"必须做"，钩子是"可以做"。
### 抽象类 vs 接口：面试高频题
| 维度 | 抽象类 `abstract class` | 接口 `interface` |
| --- | --- | --- |
| 能不能带实现 | 能（具体方法、字段初始化） | 不能（只有签名） |
| 能不能有构造函数 | 能 | 不能 |
| 能不能有访问修饰符 | 能（`protected abstract` 很常用） | 不能（接口成员天然公开） |
| 能不能多继承 | **不能，只能 `extends` 一个** | **能，可以 `implements A, B, C`** |
| 编译后是否存在 | **存在**（它是一个真实的类） | **不存在**（完全擦除） |
| 能不能描述"任意对象的形状" | 不能（必须是这个类的子类） | **能**（结构化类型，鸭子类型） |
| 运行时能不能 `instanceof` | **能** | 不能 |

选择规则三句话：① **需要复用实现 → 抽象类**（接口给不了实现，这是硬限制）；② **只需要描述形状 → 接口**（更轻、能多实现）；③ **两者都要 → 抽象类 + 接口组合**（本章示例里的 `Square extends Shape implements Printable` 就是这个套路）。
还有一条容易被忽略的：**接口更"轻"**。接口编译后完全消失，抽象类编译后是一个真实的函数（有 prototype、有构造逻辑）。库的公开 API 如果只需要描述形状，用接口不会给使用者增加运行时体积。
**一句话记住它：抽象类是"半成品模板"，接口是"纯合同"；要复用代码用抽象类，要描述形状用接口。**
### `implements` vs `extends`：本质区别
这两个词在 TS 里的差别，比大多数人以为的大得多。一句话概括：**`extends` 是"继承"，`implements` 是"承诺"。**

```ts
class Square extends Shape implements Printable {
  //                    ↑ 承诺：我一定有 print()
  //   ↑ 继承：我拿到了 name、describe()、还有"我是 Shape 的子类"这个身份
}
```

| | `extends`（继承） | `implements`（实现） |
| --- | --- | --- |
| 后面跟的是什么 | 类（或抽象类），**是值也是类型** | 只能是类型（接口、type 别名、类也行） |
| 继承什么 | **实现 + 类型**（方法体会被继承） | **只有类型**（不继承任何实现） |
| 数量 | 只能一个 | 可以多个 |
| 运行时影响 | **有**：原型链真的接上了 | **没有**：完全擦除 |
| `instanceof` | 能用 | 不能用 |
| 必须 override 吗 | 覆盖父类成员时，开了 `noImplicitOverride` 就要写 `override` | **不需要**（接口没有实现可覆盖） |

最容易踩坑的两点：**第一，`implements` 不继承任何实现**——接口里的方法只是被要求存在，你还是要自己写全部函数体。**第二，`implements` 一个类也是合法的，但它只检查形状，不建立原型链**：

```ts
class Animal {
  legCount = 4;
  move(): void {
    console.log('走');
  }
}
class Robot implements Animal {   // ✅ 语法合法
  legCount = 0;
  move(): void {
    console.log('滚');
  }
}
new Robot() instanceof Animal;    // false！它根本不是 Animal 的子类
```
这就是"承诺"和"继承"的差别：`Robot` **承诺自己有 Animal 的形状**，但它跟 `Animal` 没有血缘关系。
**一句话记住它：`extends` 接上原型链（实现 + 类型一起继承），`implements` 只是签字画押（只承诺形状）。**

## A.5 `override` 与 `noImplicitOverride`
### 它解决什么问题
有个经典的翻车现场：父类有个方法 `save()`，子类覆盖了它。后来有人重构父类，把 `save()` 改名成 `persist()`——**子类的 `save()` 不会报错，它会变成一个新方法，永远不会被调用。** 而且没有任何编译错误，直到线上数据丢了才发现。
这个 bug 有个名字叫"**静默失联**"。`override` 关键字就是为了解决它：**让你每次覆盖父类成员时显式声明"我知道我在覆盖"。**
### 怎么用

```ts
class Animal {
  move(): void {
    console.log('动物在移动');
  }
}
class Dog extends Animal {
  override move(): void {     // override 明确表示："我在覆盖父类的 move"
    console.log('狗在跑');
  }
}
```
`override` 是**可选的**，除非你开了 `noImplicitOverride: true`（本章的配套工程就开了）。
开了之后，好处是双向的：

- **覆盖而不写 `override` → 报错。** 逼你显式承认，别人 review 时一眼能看见。
- **写了 `override` 但父类没这个成员 → 报错。** 这就是"父类改名"时的救星。
### 真实报错
❌ 你可能这么写（覆盖了但没写 `override`，且开了 `noImplicitOverride`）：

```ts
class Animal {
  move(): void {}
}
class Dog extends Animal {
  move(): void {}   // 少写了 override
}
```
```text
error TS4114: This member must have an 'override' modifier because it overrides a member in the base class 'Animal'.
```
❌ 你可能这么写（写了 `override`，但父类根本没有这个方法）：

```ts
class Animal {
  move(): void {}
}
class Dog extends Animal {
  override fly(): void {}   // 父类没有 fly
}
```
```text
error TS4113: This member cannot have an 'override' modifier because it is not declared in the base class 'Animal'.
```
**TS4113 就是那个"静默失联"的探针。** 父类一改名，所有子类的 `override` 立刻变红，你在编译期就知道哪里要跟着改。这是 `noImplicitOverride` 最实在的价值。
### 两个细节
**细节一：实现抽象方法时，可以写 `override` 也可以不写。** 抽象方法没有"实现"可以覆盖，所以两种写法都合法。本章示例里我统一写了 `override`（风格一致性更好）。
**细节二：`implements` 接口的方法不需要 `override`。** 接口没有实现可覆盖，写了反而可能报错。
**一句话记住它：`override` 是"我知情"的签名，开了 `noImplicitOverride` 后，它把"父类改名导致的静默失效"变成编译错误。**


## A.6 getter / setter / 静态成员 / static 块 / 访问器签名
这一节讲类的"零件"，都是 JS 本来就有、TS 只是补了类型的能力。
### getter / setter
getter/setter 让你**用属性语法调用方法**，从而在"读"和"写"的时候插入逻辑。

```ts
class Temperature {
  #celsius = 0;
  get celsius(): number {
    return this.#celsius;
  }
  set celsius(value: number) {
    if (value < -273.15) {
      throw new RangeError(`温度不能低于绝对零度`);
    }
    this.#celsius = value;
  }
  get fahrenheit(): number {
    return this.#celsius * 1.8 + 32;
  }
}
const t = new Temperature();
t.celsius = 25;                     // 走 setter（校验）
console.log(t.celsius, t.fahrenheit); // 走 getter
```
三个类型层面的规矩：

1. **setter 不能写返回类型标注。** 只能写参数类型。`set x(v: number): void {}` 是错的。
2. **setter 的参数类型必须能接收 getter 的返回类型**，否则 TS 会报错（想想为什么：`t.x = t.x` 得说得通）。
3. **只要 getter 不要 setter，就是"只读属性"。** 这是 TS 里做"计算属性只读"的标准做法：
   ```ts
   get fahrenheit(): number { ... }  // 没有 set fahrenheit
   ```
   此后 `t.fahrenheit = 100` 会报 TS2540（只读）。
**为什么 setter 不能标返回类型？** 因为 setter 是通过赋值语法使用的，赋值表达式的值永远是"被赋的值"，不是 setter 的返回值。TS 干脆禁止你声明一个没人会用的返回类型——**这是"不让 API 表达不存在的语义"的设计**。
### 静态成员
`static` 成员属于**类本身**，不属于实例。

```ts
class Temperature {
  static readonly ABSOLUTE_ZERO = -273.15;
  static fromFahrenheit(f: number): Temperature {
    const t = new Temperature();
    t.celsius = ((f - 32) * 5) / 9;
    return t;
  }
}
Temperature.ABSOLUTE_ZERO;          // ✅ 从类上访问
Temperature.fromFahrenheit(212);    // ✅ 静态工厂
// new Temperature().ABSOLUTE_ZERO; // ❌ 实例上没有它
```
两个实用点：

- **静态常量**：`static readonly XXX = ...`，比在模块顶层写 `const` 更适合"这个概念属于这个类"的场景。
- **静态工厂方法**：`fromXxx()` 命名是业界惯例。它比构造函数好用的地方是——**可以有多个、名字能表达意图、可以返回子类**。
### `static` 块
`static` 块是 ES2022 的语法，在类第一次被求值的时候执行一次，用来做"复杂初始化"。

```ts
class Temperature {
  static readonly ABSOLUTE_ZERO = -273.15;
  static {
    console.log('[static 块] 类被加载了');
    // 这里可以写多行逻辑、try/catch、访问 # 私有静态字段
  }
}
```
它比"静态属性初始化"强在哪？

- 能写**多条语句**（属性初始化只能是一个表达式）。
- 能用 **`try/catch`**。
- 能访问**私有静态字段**。
- **多个 static 块会按顺序执行**，且和静态属性的初始化按书写顺序交错执行。

本章示例里真的跑了一次，输出是：

```text
[static 块] Temperature 类被加载了，this 就是类本身: -273.15
```
注意一个细节：**static 块里的 `this` 指向类本身**（不是实例），所以 `Temperature.ABSOLUTE_ZERO` 和 `this.ABSOLUTE_ZERO` 在 static 块里是同一个东西。
### 访问器签名（在接口/类型里描述 getter）
有时候你只想描述"这个对象有个 `length` 属性"，不关心它是字段还是 getter。这很正常——**对使用者来说，`obj.length` 就是 `obj.length`，谁管它背后是字段还是计算出来的**。
但如果要显式声明"这是个访问器"，TS 给了 `get`/`set` 签名：

```ts
interface Box {
  get size(): number;
  set size(value: number);
}
```
**实际上 99% 的情况你不需要它。** 直接写 `size: number` 就够了，因为结构化类型不区分"字段"和"访问器"。它的存在主要是为了兼容一些极端场景（比如同名 getter/setter 类型不一致时，或者声明文件里要精确描述）。
**一句话记住它：getter/setter 让属性语法带上逻辑（setter 不能标返回类型），static 属于类本身，static 块是"类加载时跑一次的初始化区"。**


## A.7 泛型类
泛型在前面章节已经讲透了，这里只补"它在类上长什么样"，两点差异：

```ts
class Box<T> {
  #items: T[] = [];
  add(item: T): this {     // ← 注意返回类型是 this，不是 Box<T>
    this.#items.push(item);
    return this;
  }
  first(): T | undefined {
    return this.#items[0];
  }
}
const nums = new Box<number>().add(1).add(2).add(3);
const strs = new Box<string>().add('a');
// strs.add(1);  // ❌ 类型不对
```
**差异一：泛型参数写在类名后面，整个类内部都能用。** 这和泛型函数一样，只是作用范围是整个类体。
**差异二：返回 `this` 而不是 `Box<T>`。** 这是个很实用的小技巧。假设有个子类：

```ts
class NumberBox extends Box<number> {
  sum(): number { return 0; }
}
new NumberBox().add(1).sum();  // 返回 this 时 ✅ 能链式调用 sum()
new NumberBox().add(1).sum();  // 返回 Box<number> 时 ❌ sum 不存在
```
`this` 类型（叫"多态 this 类型"）会跟着**实际调用者**变，而 `Box<T>` 是写死的。做链式 API（builder 模式）时这是必备技巧。
**一句话记住它：泛型类就是把类型参数放在类名上，返回 `this` 而不是类名，链式调用时子类的类型才不会丢。**


## A.8 完整实战：抽象类 + 多态写一个支付渠道
把上面所有点串起来。完整可运行代码在 `examples/07-类与模块.ts` 第 8 段，这里给核心结构。

```ts
// 用 as const 对象代替 enum —— 擦除友好，运行时还真实存在
const Channel = {
  Wechat: 'wechat',
  Alipay: 'alipay',
  Balance: 'balance',
} as const;
type Channel = (typeof Channel)[keyof typeof Channel]; // 'wechat' | 'alipay' | 'balance'
interface PayResult {
  ok: boolean;
  tradeNo: string;
  message: string;
}
abstract class PayChannel {
  abstract readonly kind: Channel;       // 每个渠道自报家门
  abstract readonly displayName: string;
  async pay(amount: number): Promise<PayResult> {   // 模板方法
    if (amount <= 0) {
      return { ok: false, tradeNo: '', message: '金额必须大于 0' };
    }
    const tradeNo = await this.doPay(amount);       // 交给子类
    return { ok: true, tradeNo, message: `${this.displayName} · 支付成功` };
  }
  protected abstract doPay(amount: number): Promise<string>;
}
class WechatPay extends PayChannel {
  readonly kind = Channel.Wechat;
  readonly displayName = '微信支付';
  protected override async doPay(amount: number): Promise<string> {
    console.log(`  [扫码] 唤起微信收银台，金额 ${amount}`);
    return `WX${Date.now()}`;
  }
}
class BalancePay extends PayChannel {
  readonly kind = Channel.Balance;
  readonly displayName = '余额';
  #balance: number;
  constructor(balance: number) {
    super();                 // 子类构造函数必须先 super()
    this.#balance = balance;
  }
  protected override async doPay(amount: number): Promise<string> {
    if (amount > this.#balance) {
      throw new Error(`余额不足，当前 ${this.#balance}`);
    }
    this.#balance -= amount;  // # 私有字段，外部改不动
    return `BAL${Date.now()}`;
  }
}
```
调用方只依赖抽象：

```ts
const checkout = async (channel: PayChannel, amount: number): Promise<void> => {
  const result = await channel.pay(amount);   // 完全不知道具体是哪个渠道
  console.log(result.ok ? `✅ ${result.message}` : `❌ ${result.message}`);
};
await checkout(new WechatPay(), 199);
await checkout(new BalancePay(500), 100);
await checkout(new BalancePay(10), 100);   // 余额不足
await checkout(new WechatPay(), -5);       // 金额非法
```
真实运行输出：

```text
===== 8. 实战：抽象类 + 多态写一个支付渠道 =====
  [扫码] 唤起微信收银台，金额 199
✅ 微信支付 · 支付成功 ¥199.00，单号 WX17911889201111
  [扣减] 余额扣款 100，剩余 400
✅ 余额 · 支付成功 ¥100.00，单号 BAL17911889201113
❌ 余额 · 支付失败: 余额不足，当前 10
❌ 金额必须大于 0
```
这个结构为什么好？**要加一个新渠道（比如银联），你只需要写一个新的子类，`checkout` 一个字都不用改。** 这就是设计模式里的**开闭原则**（对扩展开放，对修改关闭）。类型系统在这里的作用是：**如果你新写的子类漏了 `doPay` 或者参数类型不对，`pnpm exec tsc --noEmit` 立刻拦下。**
一个实战细节：`kind` 字段在本例中没被用到，它的真正用途是**类型收窄（discriminated union）**——在 `switch (channel.kind)` 里，TS 能根据 `kind` 精确推断出具体类型，`case Channel.Balance:` 分支里 `channel` 就自动变成 `BalancePay`。这就是"给联合类型一个判别字段"的经典用法。
**一句话记住它：抽象类定义流程骨架，子类只填差异部分，调用方只认抽象——加需求时只加子类，不改调用方。**


# B. 模块

## B.1 TS 的模块就是 JS 的模块
先破一个常见的幻想：**TS 没有自己的模块系统。** `import` / `export` 是 JS 的东西（ESM），或者 CommonJS 的 `require`。TS 只是"理解"它们，然后额外加了两件事。
**生活类比：TS 是 JS 的"校对员"。** 校对员不改文章结构（模块系统是作者——JS——定的），他只做两件事：

1. **搞清楚哪些是"文字"（类型），哪些是"实物"（值）。**
2. **在实物清单上签字，保证清单和正文对得上。**（类型检查）

TS 额外加的两件事，就是**类型导入**和**类型导出**。
为什么需要？因为模块有两种"东西"要传：

- **值（value）**：函数、对象、类、常量。运行时真实存在，`import` 会真的去加载那个文件。
- **类型（type）**：接口、类型别名、泛型参数。编译后就没了，`import` 不应该产生任何运行时行为。

问题是：`import { Foo } from './x.ts'` 这一行里，`Foo` 到底是值还是类型？**JS 引擎不知道，它也不关心——它会把这一行原样保留，真的去加载 `./x.ts`。**
这就出问题了。看下面这个场景。

## B.2 `import type` 为什么存在：一个"运行时炸了"的例子
### 场景：循环依赖 + 纯类型
假设你有两个文件：

```ts
// user.ts
import { Order } from './order.ts';   // ← 只是想用 Order 这个"类型"
export interface User {
  id: string;
  orders: Order[];   // 类型位置
}
```
```ts
// order.ts
import { User } from './user.ts';     // ← 只是想用 User 这个"类型"
export interface Order {
  id: string;
  owner: User;        // 类型位置
}
```
**两个文件里的 `import` 都只用在类型位置**（`Order[]`、`owner: User`）。按理说，编译后这两个 `import` 都应该消失。
但如果你不开 `verbatimModuleSyntax`，TS 会做**导入省略（import elision）**：它自己判断"这个导入只用在类型位置，那我把它删掉"。听起来挺好？**问题在于这个判断偶尔会错，而且不透明。** 典型翻车有三种：
**翻车一：副作用丢失。** `import './polyfill.ts'` 这种导入就是为了执行副作用（注册全局、patch 原型）。如果 TS 觉得"你没用它的任何导出"，有可能把它整个删掉，**运行时行为就变了**。
**翻车二：`isolatedModules` / Babel / esbuild 场景下判断失灵。** 这些工具**一次只看一个文件**，不知道 `Order` 是类型还是值，于是只能"保守地保留这个 import"，结果运行时真的去加载 → `order.ts` 又去加载 `user.ts` → `user.ts` 还没执行完，你拿到的是 `undefined`。
**翻车三：循环依赖被这个"多余的 import"激活了。** 上面 `user.ts ↔ order.ts` 本来就是循环依赖，如果两个纯类型的 import 都被保留，循环就真的建立起来了：

```text
ReferenceError: Cannot access 'User' before initialization
```
或者更隐蔽：不报错，但你拿到 `undefined`，然后在别的地方炸。
### 解决方式：显式告诉它"这只是类型"

```ts
// user.ts
import type { Order } from './order.ts';   // ← 明确：纯类型，编译后删掉
export interface User {
  id: string;
  orders: Order[];
}
```
`import type` 的**语义是硬承诺**：这一行里导入的东西**只能当类型用**，编译后**一定**被完整删除。TS 不再需要"猜"，打包器也不需要"保守保留"。**这就是它存在的全部理由**，可以总结成三条好处：

1. **保证被擦除。** 不会有"看起来只用了类型，结果运行时加载了一个模块"的意外。
2. **打断运行时循环依赖。** 纯类型导入不进模块图，循环链就断了——这是排查循环依赖时最有效的第一招。
3. **让打包器安全摇树（tree shaking）。** esbuild / SWC / Rollup 逐文件处理时，看到 `import type` 就知道可以无条件删掉，不用做跨文件的类型分析。
### 真实报错
❌ 你可能这么写（把值当类型导入，或者反过来，且开了 `verbatimModuleSyntax`）：

```ts
import { Product } from './07-lib.ts';   // Product 是 interface
const p: Product = { id: '1', name: 'a', price: 1, currency: 'CNY' };
```
```text
error TS1484: 'Product' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```
❌ 你可能这么写（用 `import type` 导入了值，然后当值用）：

```ts
import type { add } from './07-lib.ts';
console.log(add(1, 2));
```
```text
error TS1361: 'add' cannot be used as a value because it was imported using 'import type'.
```
这两个错误码要记住：**TS1484 = 该写 `import type` 却没写；TS1361 = 写了 `import type` 却当值用了。**

## B.3 三种写法：`export type`、`import type`、`import { type X }`

```ts
// 1) 整个导入语句都是类型
import type { Currency, Product } from './07-lib.ts';
// 2) 混着导：值用普通写法，类型用行内 type 修饰符
import { formatPrice, Counter, type Currency, type Product } from './07-lib.ts';
// 3) 导出侧同理
export type { Currency } from './07-lib.ts';        // 纯类型再导出
export { Counter, type Product } from './07-lib.ts'; // 混合再导出
```
**推荐哪一种？** 我的建议：

- **纯类型**（比如工具类型文件）→ 用 `import type`，最清晰。
- **值和类型混着** → 用行内 `type` 修饰符（写法 2）。好处是"哪些是类型"一眼可见，不用翻到文件另一头对照两个 import 语句。
- **不要**写两个分离的 import 语句（一个 `import type` 一个 `import`）指向同一个文件——那是没必要的啰嗦。

## B.4 `verbatimModuleSyntax` 是什么
`verbatim` 是"逐字照抄"的意思。这个选项打开之后，TS 对 import/export 语句的态度变成：**你写什么，我就原样保留什么。**
具体行为：

1. **不做导入省略（import elision）。** 你在代码里写的每一个 `import`，只要不是 `import type`，编译后都原样保留。
2. **因此，只导入类型时必须显式写 `import type`。** 否则 TS 会报 TS1484——因为如果它原样保留这个 import，运行时就会真的去加载一个"只有类型"的模块，而那个模块编译后可能是个空文件，或者根本不存在（比如有些包只提供类型）。
3. **`import x = require()` 和 `export =` 只能在 CJS 语境下用。**

**为什么这个选项值得开？** 因为它把"TS 猜你的意图"变成了"你明确表达意图"。一旦开了它：

- 你的 TS 源码和编译产物**一一对应**，不会出现"我明明没写这个 import，产物里却有"。
- 给 Babel / esbuild / SWC 用的时候**行为完全一致**（因为它们本来就是逐字处理的）。
- **循环依赖的成因变得可见**：看一眼还有哪些非 `import type` 的 import，就知道哪些是真的运行时依赖。

代价是**啰嗦一点**（每次导类型都要写 `type`），但这点啰嗦换来的是确定性，很值。本章的配套工程（`examples/tsconfig.json`）就开了它。
**一句话记住它：`verbatimModuleSyntax` 让 TS 不再猜你的 import 意图，代价是你必须亲手标注 `import type`。**

## B.5 `export =` / `import x = require()`（了解即可）
这两种写法是 **CommonJS 时代的遗产**，你在现代 ESM 项目里基本不会写，但**读老代码和 `.d.ts` 时一定会见到**。

```ts
// CommonJS 风格的类型声明（老库的 .d.ts 里常见）
declare function myLib(x: number): string;
declare namespace myLib {
  const VERSION: string;
}
export = myLib;          // 等价于 module.exports = myLib
```
```ts
// 消费方要这样导入
import myLib = require('my-lib');   // 不是 ES 的 import，是 TS 的特殊语法
```
三个要点：

1. **`export =` 不能被 ES 的 `import { x } from` 正常消费**（除非开 `esModuleInterop`，那是另一个话题）。
2. **`export =` 和 `export default` 不能同时出现在一个文件里。**
3. **你现在写新代码，一律用 ESM 的 `export` / `import`。** 见到 `export =` 就知道"这是个老库"，心里有数就行。

## B.6 循环依赖：成因与排查
### 成因
模块 A `import` 了 B，B 又 `import` 了 A（直接循环），或者 A→B→C→A（间接循环）。
这不是"错误"，**是合法代码**。问题在于 ESM 的加载顺序：模块是**深度优先、先加载后执行**的。循环形成后，**至少有一个模块会在自己的依赖还没执行完时就开始执行**，这时候它拿到的是 `undefined` 或者一个还没初始化的绑定。
### 典型症状

```text
ReferenceError: Cannot access 'X' before initialization
```
```text
TypeError: Cannot read properties of undefined (reading 'something')
```
最恶心的一种是：**它有时报错有时不报**（取决于从哪个入口文件启动）。因为加载顺序和入口有关。
### 排查思路（按顺序做）
**第一步：把纯类型的 import 改成 `import type`。**
这是最有效的一招，而且能省掉一大半问题。因为**纯类型 import 根本不应该参与运行时循环**。如果你的循环依赖里有相当一部分是"为了类型而 import"，改完循环链就断了。
**第二步：看真实报错的堆栈，定位"谁先执行了"。** 报 `Cannot access 'X' before initialization` 的那个模块，就是那个"在自己依赖没准备好时就执行"的倒霉蛋。
**第三步：可视化依赖图。** 用 `madge` 这类工具直接画出来：

```bash
npx madge --circular --extensions ts src/
```
它会打印出所有循环链，比你在代码里翻快 100 倍。
**第四步（重构）：把共享的东西提到第三个模块。**
```
// 之前：A ↔ B（互相依赖）
// 之后：A → C ← B（双方都依赖 C，循环消失）
```
把两边都要用的**类型**、**常量**、**接口**抽到 `types.ts` / `constants.ts`。这是最标准、最一劳永逸的解法。
**第五步（应急）：改成延迟导入。** 把顶层的 `import` 改成函数内部的 `await import('./b.ts')`。这能让加载时机变晚，绕开"初始化顺序"问题。但这是**治标**，代码会变难看，只适合临时救火。
**一句话记住它：循环依赖大部分是因为"为类型而 import"造成的，先全改 `import type`，再把共享类型提到第三个文件。**


# C. 声明文件（.d.ts）

## C.1 什么是 `.d.ts`，为什么不写实现
**先解决"它是什么"。**
`.d.ts` 文件里**只有类型，没有实现**。它回答的问题是："这个模块对外长什么样？"
**生活类比：餐厅菜单。** 菜单上写着"宫保鸡丁，38 元，微辣"（= 签名：函数名、参数类型、返回类型），但菜单上**没有菜谱**（= 没有实现）。你不需要知道厨房怎么做的，你只需要知道"我点这个，会得到那个"。`.d.ts` 就是菜单——**它描述能力，不提供能力**。
**为什么要有这种东西？** 三个真实场景：

1. **JS 库想支持 TS。** 库是用 JS 写的（可能是十年前写的，也可能作者就是不想用 TS）。它没有类型源码。怎么办？**单独写一份 `.d.ts` 描述自己的 API**，和 JS 文件放到一起。TS 就能用上类型了。
2. **`tsc` 编译产物。** 你写 TS 库发给别人用，别人不想看你源码。`tsc --declaration` 会为每个 `.ts` 生成一个 `.d.ts`——**只包含类型的那一半**。别人拿到 `.d.ts` + 编译后的 `.js` 就够用了。（这也是为什么 `.d.ts` 不能有实现：**它就是"从源码里抽出来的类型部分"**。）
3. **手写补类型。** 一个老库没类型，社区也没人写，你自己写一份——这是本章 C.4 的实战。

**它和同名 `.js`/`.ts` 的关系：** 一份 `.d.ts` 旁边通常有一个同名 `.js`（比如 `lodash.js` + `lodash.d.ts`）。运行时用 `.js`，类型检查用 `.d.ts`。两个文件描述同一个东西的两个面。
**一个关键规则：`.d.ts` 里不能有实现代码。** 因为它是"类型描述"，不是"程序"。写了 `console.log` 也不会执行——`.d.ts` 会被编译器完全忽略掉运行相关内容。

## C.2 `declare` 关键字
`declare` 的读法是："**我保证运行时这个东西存在，你（编译器）别问它从哪来。**"
**生活类比：记账时的"暂估"。** 你知道有这笔钱，但单据还没到，先记一笔"暂估 XXX"。`declare` 就是"暂估"。
### `declare const` / `declare let` / `declare function`

```ts
declare const VERSION: string;                          // 运行时有个 VERSION 常量
declare function formatPrice(num: number, currency: string): string;  // 运行时有个这个函数
```
注意：**只能写签名，不能写实现**（不能有函数体）。因为 `declare` 的意思就是"实现不在这里"。
### `declare class`

```ts
declare class LegacyDate {
  constructor(timestamp: number);
  getTime(): number;
  static now(): number;
}
```
`declare class` 描述"运行时有个这样的类"。注意它的成员也**不能有函数体**。
### `declare module`
这是最常用的一个，用来"给一个模块起名字并描述它"：

```ts
declare module 'my-legacy-lib' {
  export function formatPrice(num: number, currency: string): string;
  export const VERSION: string;
}
```
**注意一个容易踩的坑：** `declare module 'xxx'` 写在 `.d.ts` 文件里叫"环境模块声明"（ambient module declaration），是**声明一个新模块**；但如果你把它写在 `.ts` 文件里，它会变成"**模块增强**"（module augmentation），此时 `xxx` **必须已经存在**，否则报错：

```text
error TS2664: Invalid module name in augmentation, module 'my-legacy-lib' cannot be found.
```
**为什么？** 因为 TS 的规则是：**在模块文件（有 import/export 的 `.ts`）里，`declare module 'xxx'` 只可能是"增强一个已存在的模块"。** 想凭空造一个模块，你得在**非模块的 `.d.ts`** 里写。
### `declare global`
在模块文件里给全局作用域加东西：

```ts
declare global {
  interface Window {
    __myAppVersion: string;
  }
}
export {};   // 保证这是模块
```
这个后面 C.5 会详细讲，它是本章最容易出错的点之一。
### 一个常见误解
很多人以为 `declare` 会"生成"东西。**不会。** `declare` 是纯类型的、零运行时输出的。你 `declare const VERSION: string;` 之后，运行时并没有 `VERSION` 这个变量——**是"运行时本来就有，我只是告诉你"**。所以你 declare 了但运行时没有，一用就是 `ReferenceError: VERSION is not defined`。
**一句话记住它：`declare` = "我保证运行时存在这个东西，编译器你信我，别要实现"。**

## C.3 TS 怎么找到类型
这是实操里最常卡住的地方。TS 找类型的顺序，你可以理解成"**找一本书的目录**"：先看内页有没有目录（包自带的 types），没有就去公共图书馆索引里找（`@types/xxx`）。
### 第一步：包自己的 `types` / `typings` 字段
TS 去 `node_modules/xxx/package.json` 里找：

```json
{
  "name": "axios",
  "main": "./dist/node/axios.cjs",
  "types": "./index.d.ts",        // ← 这里！
  "exports": {
    ".": {
      "types": "./index.d.ts",    // ← 现代包用 exports 里的 types 条件
      "import": "./index.js"
    }
  }
}
```
有 `types` 字段 → 直接用。**这就是"包自带类型"**。现在越来越多的库直接用 TS 写源码然后把 `.d.ts` 一起发布，这类库你**什么都不用装**。
两个细节：

- `types` 和 `typings` 是等价的（历史原因两个都支持）。
- 现代包用 `exports` 字段控制导出，那时类型要写在 `exports` 的 `types` 条件里。**顺序很重要**：`types` 条件必须放在最前面，否则 Node 会先匹配到 `import`/`require` 而忽略类型。
### 第二步：`@types/xxx`
包自己没类型怎么办？TS 会去 `node_modules/@types/` 下面找同名包：

```text
node_modules/@types/lodash/index.d.ts   ← 对应 import ... from 'lodash'
node_modules/@types/express/index.d.ts  ← 对应 import ... from 'express'
```
`@types/` 下的包从哪来？来自 **DefinitelyTyped**——这是社区维护的"类型定义仓库"，是 TS 生态最伟大的基础设施之一。你装它就行：

```bash
npm i -D @types/lodash @types/express
```
**什么时候需要装 `@types/xxx`？** 判断口诀：

- **包自带 `.d.ts`（package.json 里有 `types` 字段）→ 不用装。** 比如 axios、zod、vue、react（React 18+ 自带类型）。
- **包是纯 JS、没写类型 → 要装。** 比如 lodash、express、node 本体（`@types/node`）。
- **怎么快速知道要不要装？** 直接 `import` 一下，TS 报 TS2307 就是缺类型：
  ```text
  error TS2307: Cannot find module 'lodash' or its corresponding type declarations.
  ```
  然后去 [npmjs.com](https://www.npmjs.com/) 搜 `@types/lodash`，**搜得到就装，搜不到就自己写**（C.4 的内容）。
### 第三步：`typeRoots` 和 `types` 配置项
这两个选项控制"`@types` 从哪些目录找"和"默认加载哪些"。

```jsonc
{
  "compilerOptions": {
    // typeRoots：去哪里找 @types 包。默认就是 ["./node_modules/@types"]
    "typeRoots": ["./node_modules/@types", "./types"],
    // types：只自动加载列出来的这几个，其他 @types 包一律不自动加载
    "types": ["node"]
  }
}
```
**`types` 这个选项特别容易踩坑，值得单独说。** 它的行为是"**白名单**"：

- **不写 `types`** → `node_modules/@types/` 下的**所有**包都被自动加载到全局。方便，但可能慢，而且可能引入你不想要的全局类型。
- **写了 `types: ["node"]`** → **只有 `@types/node` 被自动加载**，其他 `@types/*` 只在你**显式 `import`** 时才生效。

**为什么这是个坑？** 因为很多人配了 `types: ["node"]` 之后发现 `@types/jest` 的全局 `describe`/`it` 没了、`@types/mocha` 的全局 `before` 没了——因为它们被白名单挡在外面了。解决办法是把它们也列进去：

```jsonc
"types": ["node", "jest"]
```
还有个常见误区：**`typeRoots` 不是"我的自定义类型放哪"的选项。** 它是"`@types` 这种**包**放哪"的选项。你自己的 `.d.ts` 应该通过 `include` 让 TS 扫到：

```jsonc
{
  "include": ["src/**/*.ts", "types/**/*.d.ts"]
}
```
**一句话记住它：找类型三步走——包自带 `types` 字段 → `node_modules/@types/` → 自己写；`types` 选项是白名单，配了它别的 `@types` 就不自动加载了。**

## C.4 实战：给没有类型的第三方库手写 `.d.ts`
假设有个老库 `my-legacy-lib`，它是纯 JS，没有类型，导出：

- 一个函数 `formatPrice(num, currency)`
- 一个常量 `VERSION`
### 第一步：确认它真的没类型

```ts
import { formatPrice } from 'my-legacy-lib';
```
```text
error TS2307: Cannot find module 'my-legacy-lib' or its corresponding type declarations.
```

### 第二步：写 `.d.ts`
新建 `types/my-legacy-lib.d.ts`：

```ts
// types/my-legacy-lib.d.ts
declare module 'my-legacy-lib' {
  /** 把数字格式化成带货币符号的字符串 */
  export function formatPrice(num: number, currency: string): string;
  /** 库的版本号 */
  export const VERSION: string;
}
```
**三个要点：**

1. **`declare module 'xxx'` 里的字符串必须和 `import` 里写的完全一致**（包括大小写、`@scope/` 前缀）。**文件名不重要**——叫 `my-legacy-lib.d.ts` 只是习惯，叫 `whatever.d.ts` 效果一样。
2. **`export` 关键字别忘。** 有了 `export`，这个模块里的东西才是"从模块导出的"；忘了写，它们会变成全局的。
3. **我故意把 `currency` 写成 `string` 而不是联合类型**，因为老库大概率不校验货币值——**声明文件要忠实地描述现实，不要描述你希望的样子**。如果你写成 `'CNY' | 'USD'`，而库其实接受任意字符串，那你就给使用者造了一个假的安全感，运行时照样炸。
### 第三步：让 TS 扫到它
如果 `tsconfig.json` 的 `include` 里没有 `types/**/*.d.ts`，加上：

```jsonc
{
  "include": ["**/*.ts", "types/**/*.d.ts"]
}
```
或者用三斜线指令显式引入（少见但有用）：

```ts
/// <reference path="./types/my-legacy-lib.d.ts" />
```

### 第四步：验证

```ts
import { formatPrice, VERSION } from 'my-legacy-lib';
const text: string = formatPrice(12.5, 'CNY');   // ✅ 有补全、有类型
const ver: string = VERSION;                     // ✅
```
传错类型会被抓住：
❌ 你可能这么写：

```ts
formatPrice('12.5', 'CNY');
```
```text
error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```
**到这里你就完成了一次"给 JS 库补类型"的完整流程**——这也是在真实项目里非常有用的能力（很多公司内部的老库就靠这一步续命）。
### 进阶：用 `import` 在声明文件里复用类型
声明文件里也可以 import：

```ts
// types/my-legacy-lib.d.ts
import type { Currency } from '../src/money.ts';
declare module 'my-legacy-lib' {
  export function formatPrice(num: number, currency: Currency): string;
}
```
但要注意：**一旦 `.d.ts` 里出现了顶层 `import`，它就成了"模块"**，里面的 `declare module` 语义会变成"模块增强"——上面那个坑又来了。稳妥做法是把 `declare module` 和 `import` 的关系理清楚，或者干脆在 `declare module` 内部用 `import type`：

```ts
declare module 'my-legacy-lib' {
  import type { Currency } from '../src/money.ts';
  export function formatPrice(num: number, currency: Currency): string;
}
```

## C.5 给全局扩展类型：`declare global`
### 需求
你想在 `window` 上挂一个自己定义的字段，但 TS 不认识它（浏览器只定义了 `window` 的标准字段）。

```ts
window.__myAppVersion = '1.2.3';
console.log(window.__myAppVersion);
```
注意：本章配套工程的 `lib` 里**没有 DOM**，所以这里讨论 `window` 时请理解成"你在浏览器项目里的场景"。
### 错误写法一：直接写 `interface Window`

```ts
import type { Currency } from './07-lib.ts';   // ← 有 import = 这是个"模块"
interface Window {   // ❌ 在模块里，这只是"本模块的局部接口"
  appVer: string;
}
```
在**另一个模块**里读它：

```ts
// other.ts
console.log(window.appVer);
```
```text
error TS2339: Property 'appVer' does not exist on type 'Window & typeof globalThis'.
```
**为什么？** 因为**一旦文件有顶层 `import` 或 `export`，它就是"模块"，模块里的声明默认是"模块作用域"，不会跑到全局去**。上面那段 `interface Window` 只是在本文件里**遮蔽（shadow）** 了全局的 `Window`，对外面毫无影响。
### 错误写法二：文件里没有 `import`/`export`（"脚本"模式）
反过来说，**没有任何顶层 import/export** 的文件叫**脚本（script）**，它的顶层声明**全都会跑到全局作用域**，这时候 `interface Window { ... }` 确实会全局生效。
**但这很危险**：一个文件本来没有 import，后来加了一个 import，**它的全局声明就突然失效了**。这种"改一行 import 就坏掉"的行为是 bug 的温床，所以别依赖它。
### 正确写法：`declare global`

```ts
// env.d.ts（或任意 .ts 文件）
import type { Currency } from './07-lib.ts';   // 有 import，是模块
declare global {
  interface Window {
    appVer: string;
  }
}
export {};   // 双保险：明确告诉 TS "这是个模块"
```
现在任何模块里都能用 `window.appVer`。（实测：加上 `declare global` 之后，上面那个 TS2339 就消失了。）
### 为什么必须写在 `declare global` 里
> **`declare global` 的意思是"我虽然在一个模块里，但我要往全局作用域里塞东西"。它是一个显式的、跨出模块边界的出口。**

**生活类比：部门小群 vs 公司门口公告栏。** 在模块里写声明，等于在部门小群里发消息，只有本部门看得到；要全员都知道，必须贴到公司门口（`declare global`）。这个默认很合理——ESM 的设计哲学就是"一切皆模块，别污染全局"。
而 `declare global` 只能出现在**模块**或**环境模块声明**里。在**脚本模式的 `.d.ts`** 里写它，TS 会报：

```text
error TS2669: Augmentations for the global scope can only be directly nested in external modules or ambient module declarations.
```
这就是为什么**必须有 `export {}`**：它是把文件"变成模块"的最轻量方式（你已经有 import 了，加 `export {}` 是双保险，也常见于只有类型声明的 `.d.ts` 里）。

> **一个实测出来的细节（网上很多文章写错了）：**
> 触发 TS2669 的准确条件是 **`.d.ts` 文件没有 `import` / `export`**，
> 而不是"任何没有 import/export 的文件"。
>
> | 场景 | 结果 |
> |---|---|
> | `.d.ts` 脚本模式 + `declare global` | ❌ TS2669 |
> | `.ts` 脚本模式 + `declare global` | ✅ 不报错（但此时声明本来就已经是全局的，`declare global` 是多余的） |
> | `declare global` 被嵌套在 `namespace` 里 | ❌ TS2669，另外还报 TS1038 |
>
> **实践结论不变**：全局扩展一律写成 `.d.ts` + `export {}` + `declare global`，
> 这样意图最明确，也不会因为文件里加了一行 import 就突然坏掉。
### `.d.ts` 里的实践约定
真实项目里全局扩展通常单独放一个 `env.d.ts` 或 `global.d.ts`：

```ts
// src/types/global.d.ts
export {};    // 只为了让它是模块
declare global {
  interface Window {
    __APP_VERSION__: string;
  }
  interface ProcessEnv {
    NODE_ENV: 'development' | 'production' | 'test';
  }
  function log(...args: unknown[]): void;   // 全局工具函数
}
```
**`declare global` 里面不需要再写 `declare`**——里面的每条声明自动就是"全局的、环境（ambient）的"，写 `declare interface Window` 反而多余。
**一句话记住它：模块里的声明不会自动全局，往全局塞东西必须包在 `declare global {}` 里，而 `declare global` 只能出现在模块文件里（所以要有 `import` 或 `export {}`）。**

## C.6 声明合并（declaration merging）
### 它是什么
**同名声明会自动合并成一份。** 这是 TS 里一个非常独特、面试非常爱问的特性。
最简单的例子：**两个同名 `interface` 自动合并**。

```ts
interface User {
  id: string;
  name: string;
}
interface User {     // 又声明了一次，不报错！
  age: number;
}
// 合并后：User 必须同时拥有 id、name、age
const u: User = { id: '1', name: 'a', age: 18 };   // ✅ 三者缺一不可
```
**这和别的语言完全相反**（Java/C# 里同名类型会直接冲突）。TS 为什么要这样？
### 为什么 TS 要保留这个特性
两个原因，一个是历史，一个是真实需求。
**原因一：历史包袱（也是生态基础）。** TS 早期的一个核心任务是"给已有的 JS 生态补类型"，而 JS 生态里到处是**同一份东西分散在多个文件里描述**的情况（jQuery 插件给 jQuery 加方法、Node 的各种模块互相扩展）。声明合并让"分散描述"成为可能，**DefinitelyTyped 整个仓库的运作方式都建立在它之上**，所以即使有争议也一直保留着。
**原因二：可扩展性——这才是你现在真正会用到的部分。**最经典的例子是**给 Express 的 `Request` 加 `user` 字段**：你用 JWT 中间件把用户信息挂到 `req.user` 上，但类型不认识它。

```ts
app.use((req, res, next) => {
  req.user = verifyToken(req.headers.authorization);   // ❌ 类型报错
  next();
});
```
```text
error TS2339: Property 'user' does not exist on type 'Request<ParamsDictionary, any, any, ParsedQs, Record<string, any>>'.
```
**标准解法：声明合并（模块增强）**——不用 `declare global`、直接增强模块，作用域更干净：

```ts
// src/types/express.d.ts
import type { User } from '../models/user.ts';
declare module 'express-serve-static-core' {
  interface Request {
    user?: User;              // 合并进 Request
  }
}
```
现在 `req.user` 就有类型了，而且**你一个字节的 express 源码都没改**。这就是声明合并的威力：**它是"从外部给已有类型打补丁"的官方机制。**同样的套路还能用于给 `Window` 加字段（C.5）、给 jQuery 插件加方法、给 `process.env` 加强类型字段。
### 合并的规则
不同种类的声明，合并行为不同。这张表要大致记住：
| 声明 A | 声明 B | 结果 |
| --- | --- | --- |
| `interface` | `interface` | **合并成员**（同名属性类型必须完全一致） |
| `namespace` | `namespace` | **合并成员** |
| `namespace` | `class` / `function` / `enum` | **合并**（namespace 的成员变成静态成员） |
| `interface` | `class` | **不合并**（会报重复标识符） |
| `type` | 任意同名 | **不合并，直接报错** |
**最后一行是重点**：**`type` 别名不能合并**，两个同名 `type` 会直接报"重复标识符"（TS2300）。这也是"什么时候用 `interface` 而不是 `type`"的一条实际理由——**需要被扩展/合并的时候用 `interface`**。
同名 interface 的成员冲突也会报错：
❌ 你可能这么写：

```ts
interface User { id: string; }
interface User { id: number; }   // 冲突
```
```text
error TS2717: Subsequent property declarations must have the same type.  Property 'id' must be of type 'string', but here has type 'number'.
```
**注意：同名属性必须类型完全一致，但同名方法会被重载合并**（`foo(x: string)` 和 `foo(x: number)` 会变成重载列表）。这个细节反直觉，但很实用。
### namespace 合并

```ts
namespace Money {
  export const symbol = '¥';
}
namespace Money {
  export function format(n: number): string {
    return `${symbol}${n}`;   // ← 能访问到另一个 namespace 块里的 symbol
  }
}
```
**为什么这个有用？** 它是"把一个大模块拆成多个文件"的 CJS 时代做法（现在被 ESM 取代了），你只会在老代码里见到它。
**一个警告：不要用声明合并去改标准库的原型。** `declare global { interface Array<T> { last(): T | undefined } }` 这种写法语法上能过，但**运行时极其危险**：① 你得自己给 `Array.prototype` 挂方法，改全局原型是著名反模式（会和其他库打架）；② 一旦某个依赖也加了同名但不同实现的 `last()`，你们互相覆盖且**没有任何编译错误**。**这个特性留给"给第三方库的接口打补丁"用，不要用来改语言内建类型。**
**一句话记住它：声明合并 = 同名声明自动合体，`interface` 和 `namespace` 能合、`type` 不能合；它的主战场是从外部给第三方库的类型打补丁（比如 Express 的 `req.user`）。**


# D. 面试高频 8 问
正文已经讲透的地方，这里只给"能直接说出口的答案"，细节回看对应小节。
### 问 1：`interface` 和 `type` 有什么区别？类能 `implements` 谁？
**答**：大部分场景可互换，硬差别有六条：
| 维度 | `interface` | `type` |
| --- | --- | --- |
| 能声明的东西 | 对象 / 函数 / 类的形状 | 上面全部 **+ 联合、元组、条件类型、映射类型、原始类型别名** |
| 同名声明 | **自动声明合并** | 直接报重复标识符 TS2300 |
| 被 `class implements` | 能 | **也能**（联合类型也行，条件是每个成员都被实现） |
| 被扩展 | `interface extends A, B` 多继承 | 靠交叉类型 `A & B`，语义和报错可读性差一些 |
| 编译性能 | 有缓存，大型项目更好 | 每次求值 |
| 报错可读性 | 名字会出现在报错里 | 匿名展开，常报出一大坨 |
**注意一个流传很广的错误说法："类只能 implements interface。"这是错的**——`type` 别名、甚至联合类型都能被 `implements`。
**实操建议**：能写 `interface` 就写它（对象形状、公开 API、可能要扩展的东西）；联合类型、`Omit`/`Pick` 这类工具类型组合、函数类型别名、原始类型别名用 `type`。
### 问 2：抽象类和接口的区别？什么时候用哪个？
**答**：完整对照表见 A.4，一句话版本：**抽象类能带实现、编译后真实存在、能 `instanceof`，但只能 `extends` 一个；接口只有签名、编译后完全擦除、不能 `instanceof`，但能 `implements` 多个。**
**选择**：要**共享实现**用抽象类（接口给不了）；只要**描述契约**用接口（更轻、能多实现）；两者都要 → 抽象类 + `implements` 接口组合。
**举场景**：支付渠道用抽象类（"金额校验"这段逻辑要共享）；"可序列化"能力用接口（不需要共享实现，还要允许一堆不相关的类都具备）。
### 问 3：TS 的 `private` 和 JS 的 `#` 有什么区别？
**答**：三条。

1. **层面不同。** `private` 是编译期的访问控制，编译后属性名照旧存在。`#` 是 JS 语言级的硬私有字段，运行时由引擎保证。
2. **能不能绕过。** `private` 能被 `(obj as any).secret` 绕过；`#` 绕不过——`obj.#secret` 在语法层面就不允许出现在类外（TS18016）。
3. **反射可见性。** `private` 字段会出现在 `Object.keys` / `JSON.stringify` 里，`#` 字段永远不会。对象要 `JSON.stringify` 发到后端时，这个差别很关键——可能是便利，也可能是数据泄露。

**选型**：真正要封装（密码、内部状态）用 `#`；想让团队别乱用、又保留调试便利用 `private`。（详细对照见 A.2。）
### 问 4：`.d.ts` 是干嘛用的？
**答**：`.d.ts` 是**只含类型、不含实现的声明文件**，描述"一个模块长什么样"。三个用途：

1. **给纯 JS 库提供类型**（库自己写，或社区在 DefinitelyTyped 里写 `@types/xxx`）。
2. **`tsc --declaration` 的产物**——`src/a.ts` → `dist/a.js` + `dist/a.d.ts`，使用者拿 `.d.ts` 做类型检查、拿 `.js` 运行。
3. **手写补类型**：没类型的第三方库或内部老库，自己写一份 `declare module 'xxx' { ... }`。

**关键特征**：运行时完全不加载它，里面不能写实现。所以同名的 `.js` + `.d.ts` 才构成完整的一个模块。
### 问 5：什么是声明合并？
**答**：**同名的多次声明会被 TS 自动合并成一份**，规则见 C.6（`interface` 和 `namespace` 能合，`type` 不能合）。
**为什么保留它？** ① 历史：要给"同一份东西分散描述"的 JS 生态补类型，DefinitelyTyped 靠它运作；② 真实需求：**从外部给第三方库的类型打补丁**（Express 的 `req.user`、`Window` 自定义字段），不改库源码就能扩展。
### 问 6：`import type` 有什么用？
**答**：三个作用，本质都是**明确告诉编译器"这个导入只用于类型，编译后请删掉"**：

1. **保证被完全擦除**——不会有"看起来只导入了类型，运行时却真加载了那个模块"的意外。
2. **打断运行时循环依赖**——纯类型导入不进模块图，这是排查循环依赖的第一招。
3. **让打包器安全摇树**——esbuild / SWC / Rollup 逐文件处理时，看到 `import type` 就能无条件删掉，不用跨文件分析。

**和 `verbatimModuleSyntax` 的关系**：开了它之后 `import` 一律原样保留，所以**只导类型时必须写 `import type`**，否则报 TS1484；反过来，用 `import type` 导入了值再当值用，报 TS1361。
**一个反例**：`import './polyfill.ts'` 这种纯副作用导入**不要**加 `type`——它就是要执行的。
### 问 7：`implements` 和 `extends` 的区别？
**答**：一句话——**`extends` 是"继承"（认亲，实现 + 类型一起接上原型链），`implements` 是"承诺"（签字，只承诺形状）。**
关键差别只有三条：`extends` 只能跟一个、**运行时有影响、能 `instanceof`**；`implements` 能跟多个、**运行时零影响、不能 `instanceof`**、覆盖方法也不需要 `override`。（完整表格见 A.4。）
**最容易踩的坑**：`implements` **不会**给你任何实现，函数体还得自己写全。而且 **`implements` 一个类也是合法的，但不建立继承关系**——`new Robot() instanceof Animal` 会是 `false`，哪怕写了 `Robot implements Animal`。
### 问 8：为什么类型不能 `instanceof`？
**答**：因为 **`instanceof` 是运行时运算符，而类型在运行时已经被擦除了**。它的语义是"查对象的原型链上有没有 `Foo.prototype`"，需要右边是一个运行时的构造函数——接口和类型别名只有"类型"那一半，没有"值"那一半（回想 A.0 的双胞胎）。
❌ 你可能这么写：

```ts
interface Printable { print(): string; }
const x = new Square(6);
console.log(x instanceof Printable);
```
```text
error TS2693: 'Printable' only refers to a type, but is being used as a value here.
```
**那想按类型分支怎么办？** 三招：

```ts
// ① 用类当判别依据（类有"值"那一半）
if (x instanceof Square) { /* ... */ }
// ② 用可辨识联合的判别字段 —— TS 里最正统的做法
type Shape = { kind: 'circle'; r: number } | { kind: 'rect'; w: number; h: number };
if (shape.kind === 'circle') { shape.r; }   // ✅ TS 自动收窄
// ③ 用类型谓词函数 —— 需要检查"形状像不像某个接口"时
function isPrintable(x: unknown): x is Printable {
  return typeof (x as Printable).print === 'function';
}
if (isPrintable(x)) { x.print(); }   // ✅
```
**这三招必须记住，"怎么在运行时判断接口类型"是非常高频的追问。**

**练习 3：制造并修复一个循环依赖。** 建 `a.ts` 和 `b.ts` 互相 `import`，且**都在模块顶层立即使用对方的值**（比如 `export const x = fromB();`）。用 `node a.ts` 跑，观察 `ReferenceError: Cannot access ... before initialization`；然后把其中一个 import 改成 `import type` 看循环是否消失；还没消失就把共享部分抽到 `shared.ts`。记录每一步报错的变化。
**练习 4：给一个库手写 `.d.ts`。** 假设 `date-helper` 暴露 `parseDate(input: string): Date`、`formatDate(date: Date, pattern?: string): string`，还有一个含这两个函数的 `default` 导出。用 `types/date-helper.d.ts` 写出声明（包括 `default` 导出），写 `test.ts` 消费它并故意传错一次参数确认能拿到 TS2345。回答：`declare module 'date-helper'` 里如果不写 `export`，会发生什么？
**练习 5：给 `process.env` 加强类型。** 在 `types/env.d.ts` 里写 `declare global { namespace NodeJS { interface ProcessEnv { APP_ENV: 'dev' | 'prod'; PORT: string; } } }`，写一个文件把 `process.env.APP_ENV` 赋给 `'dev' | 'prod'` 类型的变量确认编译通过；再故意写 `process.env.APP_ENV = 'staging'` 确认报错。最后把 `declare global` 去掉（只留 `namespace NodeJS`），验证报错并解释为什么。
**收尾提醒**：`tsconfig.json` 的 `include: ["**/*.ts"]` 是**通配的**，你在 `examples/` 下随手建的临时探针文件也会被扫进类型检查，然后以别人的报错干扰你排查。**调试完就把探针文件删掉**，这是个很小但很省时间的好习惯。

## 本章小结
- **类**：`public/private/protected/readonly` 全是编译期门禁，`#` 才是运行时真私有；抽象类是"半成品模板"，接口是"纯合同"；`extends` 继承实现，`implements` 只承诺形状。
- **模块**：TS 的模块就是 JS 的模块，TS 只多做了一件事——把"类型导入"和"值导入"分开；`import type` 保证被擦除，是打断循环依赖和让打包器安全摇树的关键。
- **声明文件**：`.d.ts` 是菜单不是菜谱；`declare` 意思是"我保证运行时存在"；给第三方库补类型靠 `declare module`，给已有类型打补丁靠声明合并 + `declare global`。
