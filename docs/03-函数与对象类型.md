## 3.0 先看一个真实的报错

带新人改类型时，几乎都会撞上这个：

```text
error TS2353: Object literal may only specify known properties,
and 'nickname' does not exist in type 'User'.
```

新人第一反应是："我没写错啊，后端返回的就是 `nickname`。"

对，后端返回的是 `nickname`，但**你给这个数据登记的名字是 `name`**。
编译器只是个记账员：你登记了 `name`，它就在你写 `nickname` 的地方收你一笔。
这一章给你的就是这本账的写法：**怎么给函数和对象登记类型**。

> 产品说"`name` 改成 `nickname`"，你把类型定义改一行，
> 编辑器立刻列出所有要改的调用点。**不用全局搜索，不会漏。**

# A 部分 · 函数类型

## 3.1 函数类型怎么写：两种写法，一个意思

JS 里函数是值，可以传来传去。问题是：`fn` 这个盒子里装的是什么形状的东西？
**在 JS 里你只能读代码或者猜。在 TS 里，你可以在盒子上贴一张标签。**
这就是"函数类型"存在的唯一理由。

```ts
// 写法 1：类型别名（最常用）。读作：一个函数，接收 number，返回 string
type Formatter = (value: number) => string;
const toYuan: Formatter = (value) => `¥${value.toFixed(2)}`;   // value 被推断为 number
// 写法 2：对象类型里的「调用签名」，跟写法 1 完全等价
interface Formatter2 { (value: number): string }
const toDollar: Formatter2 = (value) => `$${value.toFixed(2)}`;
```

`{ (参数): 返回值 }` 叫**调用签名（call signature）**。
**类比**：写法 1 像给盒子贴一张便签"这里装着一个函数"；
写法 2 像给盒子做一张正式清单"这个盒子可以被这样调用"。装的东西一模一样。

**到底用哪个？** 单纯一个函数 → 用 `type` 别名（短、好读）；
这个函数身上还挂着属性 → 用调用签名（属性写在同一层）。
第二种的真实例子是带缓存的记忆化函数：

```ts
interface MemoizedFn {
  (n: number): number;         // 能当函数调用
  cache: Map<number, number>;  // 还带着一个属性
}
const fib: MemoizedFn = Object.assign(
  (n: number): number => (n <= 1 ? n : fib(n - 1) + fib(n - 2)),
  { cache: new Map<number, number>() },
);
fib(10);         // 当函数用
fib.cache.size;  // 当对象用
```

`type F = (a: A) => B` 做不到——它描述的是纯粹的"可调用物"，
你没法在别名上再挂属性（只能写 `& { cache: ... }`，可读性差）。

**最容易懵的点：类型位置的 `=>` 是什么意思。** 看这三行，`=>` 出现三次，**三种身份**：

```ts
type A = (n: number) => string;      // ① 类型位置：读作「一个函数」
const b = (n: number) => String(n);  // ② 值位置：真的创建了一个函数
const c: (n: number) => string = (n: number) => String(n);
//        ^^^^^^^^^^^^^^^^^^^^ 类型        ^^^^^^^^^^^^^^^^^^^^ 值
```

> **类型位置的 `=>` 里没有"箭头函数"这回事。它只是一个符号，
> 读作"它是一个函数，参数是这些，返回是那个"。
> 之所以长得像 `=>`，纯粹是 TS 设计师图省事，从箭头函数抄了个符号。**

新手会懵，是因为下意识觉得"`=>` 就是箭头函数"，
于是把 `type A = (n: number) => string` 理解成"把箭头函数赋给 A"，那 A 就成了值。
**但它是类型，运行时一个字都不存在：**

```ts
type A = (n: number) => string;
console.log(typeof A);
```

```text
error TS2693: 'A' only refers to a type, but is being used as a value here.
```

> **一句话记住它：类型位置的 `=>` 只表示"函数"，跟箭头函数没关系；左边是标签，右边才是值。**

## 3.2 参数：可选、默认值、剩余、解构

**可选参数 `?`：**

```ts
function greet(name: string, title?: string): string {
  return title ? `${title} ${name}` : name;
}
greet('Ada');          // ✅
greet('Ada', 'Dr.');   // ✅
```

`title?` 在类型上等价于 `title: string | undefined`。
**立刻可见的后果**：函数体里不能直接 `title.toUpperCase()`，
TS 会说 `'title' is possibly 'undefined'`。你得先判断——那正是运行时的真相。
`?` 必须放在参数列表最后：

```ts
function bad(a?: number, b: string): void {}
```

```text
error TS1016: A required parameter cannot follow an optional parameter.
```

**为什么这么设计？** 调用时参数位置是固定的。
`bad(undefined, 'x')` 和 `bad('x')`——第二个 `'x'` 是给 `a` 还是给 `b`？编译器没法猜，
所以语言干脆禁止这种歧义。（跟 Python 的"默认参数放最后"同理。）

**默认参数：自动变成可选。**

```ts
function retry(times = 3, delay = 100): string {
  return `重试 ${times} 次，每次间隔 ${delay}ms`;
}
retry();     // ✅ 都用默认值
retry(5);    // ✅ 只覆盖第一个
```

两点：**有默认值的参数不要写 `?`**（写了反而让类型变宽）；
**默认值让参数从必需变成可选**，所以它同样不能出现在必需参数前面。
（小彩蛋：`times = 3` 会让 TS 推出 `times: number`；只有默认值是 `undefined` 时才退化成 `any`。）

**剩余参数 `...rest`：**

```ts
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}
sum(1, 2, 3, 4);   // 10

function logAll(level: 'info' | 'warn', ...msgs: string[]): string {
  return `[${level}] ${msgs.join(' | ')}`;
}
```

三个要点：**类型必须是数组**（`number[]`，因为函数体里它就是真数组）；
**必须放最后**、一个函数只能有一个；**可以和必需参数搭配**（见 `logAll`）。
`...rest` 是 ES6 就有的语法，TS 只是帮你写清楚"这个数组里装什么"。
对比 `arguments`：类数组、没有类型信息、箭头函数里还不存在。**新代码一律用 `...rest`。**

**解构参数：类型写在"整个对象"上。** 新手必踩的坑：

```ts
// ❌ 你可能这么写
function connect({ host: string, port: number }) {
  return [host, port];
}
```

```text
error TS7031: Binding element 'string' implicitly has an 'any' type.
error TS7031: Binding element 'number' implicitly has an 'any' type.
error TS2304: Cannot find name 'host'.
error TS2304: Cannot find name 'port'.
```

**为什么错？** 因为在 JS 里 `{ host: string }` 已经是**合法的解构语法**：
"把 `host` 属性取出来，赋值给一个叫 `string` 的变量"。
关键在于 **`string` 在这里是"变量名"不是"类型名"，
所以根本没产生任何类型信息**（报 `TS7031` 隐式 `any`），
而 `host` 只被当成属性路径、没被声明成变量（报 `TS2304`）。
**记住这个现象**：在解构里写类型，编译器**不会**提醒你"类型不能写在这里"，
而是给你一堆看起来毫无关系的报错。
**看到 `TS7031` + `TS2304` 一起出现，八成就是把类型写进解构里了。**

正确写法是**把类型写在解构模式外面，描述整个参数对象**：

```ts
type ConnectOpts = { host: string; port?: number };

function connect({ host, port = 80 }: ConnectOpts): string {
  return `${host}:${port}`;
}
connect({ host: 'db' });              // 'db:80'，port 用默认值
connect({ host: 'db', port: 5432 });  // 'db:5432'

// 整个参数对象也想可选（允许 connect2() 不传），就给解构一个默认值
function connect2({ host, port = 80 }: ConnectOpts = { host: 'localhost' }): string {
  return `${host}:${port}`;
}
```

> **一句话记住它：参数类型永远写在"整个参数"上——解构不是类型的容器；`?` 和 `...rest` 都不能违反"必需在前"的顺序。**

## 3.3 返回值类型：`void` / `Promise<T>` / `this`

**`void`：我不关心你的返回值。**

```ts
function printBanner(text: string): void {
  console.log(text);
  // return 123;   -> TS2322: Type 'number' is not assignable to type 'void'.
}
```

`void` 字面意思是"空"：**函数干完活就完了，没有东西交给你。**
但它有一个特别容易被误解的性质：**它是个"漏勺"。**

```ts
type Notify = (msg: string) => void;
const notify: Notify = (msg) => msg.toUpperCase();   // ✅ 不报错！
notify('x');   // 但调用处拿不到返回值，类型是 void
```

`toUpperCase()` 明明返回了 `string`，为什么能赋给返回 `void` 的类型？
**因为"回调"这个场景太常见了：**

```ts
[1, 2, 3].forEach((n) => list.push(n));   // push 返回 number，但我们根本不要它
```

如果严格检查，全世界的 `forEach`、`map` 回调都得加一堆 `{}` 包起来。
TS 选择了务实规则：**只要接收方声明"我不要返回值"，
你返回什么都行，反正会被丢掉。** 调用者拿到的东西类型仍是 `void`，用不了。
**这是"返回值协变"的特例，是 TS 里少数几个"故意不健全"的地方，面试爱考。**
反向不允许：

```ts
declare function logIt(msg: string): void;
const bad: () => number = logIt;
```

```text
error TS2322: Type '(msg: string) => void' is not assignable to type '() => number'.
  Target signature provides too few arguments. Expected 1 or more, but got 0.
```

（注意报的是"参数太少"，不是"void 不能赋给 number"——编译器先撞上了参数个数问题。）

**`async` 函数的返回类型必须写 `Promise<T>`。**

```ts
async function loadUser(id: number): Promise<{ id: number; name: string }> {
  return { id, name: 'Ada' };   // 函数体里 return 的是 T
}
```

**关键理解**：`async` 只是"给返回值套一层 Promise"的语法糖。
函数体里 `return x`，实际返回 `Promise.resolve(x)`。
所以类型注解要描述**它真正返回的那个东西**。写错的报错很友好：

```ts
async function load(): number { return 1; }
```

```text
error TS1064: The return type of an async function or method must be the global
Promise<T> type. Did you mean to write 'Promise<number>'?
```

**要不要手写返回类型？** 内部小函数不写，让 TS 推断；
**导出的函数、API 层一定要写**（那是给同事和未来的你看的契约）。

**返回 `this` 实现链式调用：**

```ts
class QueryBuilder {
  #parts: string[] = [];
  select(...cols: string[]): this {          // 返回 this 而不是 QueryBuilder
    this.#parts.push(`SELECT ${cols.join(', ')}`);
    return this;
  }
  from(table: string): this { this.#parts.push(`FROM ${table}`); return this; }
  build(): string { return this.#parts.join(' '); }
}
new QueryBuilder().select('id', 'name').from('users').build();
// 'SELECT id, name FROM users'
```

**为什么返回 `this` 而不是 `QueryBuilder`？** 因为子类继承时，
`this` 会自动变成子类类型，链式调用不会"退回父类"。
写死 `QueryBuilder` 的话，子类调完一个方法类型就断了。

> **一句话记住它：`void` 表示"没返回值"，而且它是漏勺（返回什么都行）；`async` 函数的返回类型必须写成 `Promise<T>`，因为 async 本质就是给返回值套一层 Promise。**

## 3.4 函数重载：一个函数，多种输入输出

**它解决什么问题？**

```ts
function pick(flag: boolean): string | number {
  return flag ? 'yes' : 0;
}
const x = pick(true);
//    ^? x: string | number     ← 问题在这
x.toUpperCase();
// error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
```

**我明明传了 `true`，返回值一定是 `string`，但编译器只肯给我 `string | number`。**
联合类型在这里"糊"掉了信息：它描述"所有可能"，而不是"这一次的结果"。
**函数重载就是用来把这个信息找回来的。**

```ts
// ① 重载签名：只有类型，没有函数体
function pick(flag: true): string;
function pick(flag: false): number;
// ② 实现签名：有函数体，对调用者不可见
function pick(flag: boolean): string | number {
  return flag ? 'yes' : 0;
}
const a = pick(true);    // a: string  ✅
const b = pick(false);   // b: number  ✅
```

三条铁律：**重载签名在前、实现签名在后，实现必须紧挨着最后一个签名**；
**实现签名对调用者不可见**（调用 `pick(true)` 时只匹配前面两个签名，匹配不上就报 `TS2769`，
所以实现签名不能用来"兜底"）；**重载只能写在函数声明上**，
`const pick = (flag: boolean) => ...` 加不了重载签名。

**真实场景：`createElement` 风格。**

```ts
function createElement(tag: 'div'): HTMLDivElement;
function createElement(tag: 'span'): HTMLSpanElement;
function createElement(tag: string): HTMLElement {
  return document.createElement(tag);
}
const div = createElement('div');   // HTMLDivElement
div.style.color = 'red';            // ✅ div 才有 style
```

如果只写 `createElement(tag: string): HTMLElement`，你拿到 `div` 后还得自己
`as HTMLDivElement`。**重载把这个断言内化进了类型定义：写一次，全项目受益。**
`lib.dom.d.ts` 里这类重载遍地都是，这就是它们存在的理由。

```ts
declare function make(tag: 'div'): { tag: 'div' };
declare function make(tag: 'span'): { tag: 'span' };
make('p');
```

```text
error TS2769: No overload matches this call.
  Overload 1 of 2, '(tag: "div"): { tag: "div"; }', gave the following error.
    Argument of type '"p"' is not assignable to parameter of type '"div"'.
  Overload 2 of 2, '(tag: "span"): { tag: "span"; }', gave the following error.
    Argument of type '"p"' is not assignable to parameter of type '"span"'.
```

**这个报错是宝藏**：它把每个重载为什么不匹配都列出来了。
看到 `TS2769` 不要慌，从上往下读它列的每一条。

**实现签名和声明打架：`TS2394`。**

```ts
function parseIt(input: string): number;
function parseIt(input: number): string;
function parseIt(input: string): number { return 1; }   // ❌
```

```text
error TS2394: This overload signature is not compatible with its implementation signature.
```

**为什么报错？** 第二个声明承诺"传 `number` 进来、给你 `string`"，
但实现签名只接受 `string`。**实现必须能兼容所有声明**——运行时只有这一个函数。修法：

```ts
function parseIt(input: string | number): number | string {
  return typeof input === 'string' ? input.length : String(input);
}
```

实现签名里通常得写联合类型 + 自己判断——
**这说明"重载"和"联合类型"其实是一回事的两种表达，只是重载把收窄的责任推给了调用者。**

**为什么大多数时候该用联合类型？** 重载的代价很明确：
**写得多**（`n` 个组合，代码量成倍增长）、**实现签名容易撒谎**、**可读性差**
（同事得把所有签名读一遍才知道能怎么调）。同一件事用联合 + 条件类型（第 06 章细讲）：

```ts
type Tag = 'div' | 'span' | 'input';
type ElOf<T extends Tag> =
  T extends 'div' ? HTMLDivElement :
  T extends 'span' ? HTMLSpanElement : HTMLInputElement;
function createElement<T extends Tag>(tag: T): ElOf<T> {
  return document.createElement(tag) as ElOf<T>;
}
```

> **默认用联合类型。只有当"参数和返回值的关系无法用联合+泛型简洁表达"时才上重载。
> 判断标准：重载超过 3 个，先想想是不是类型设计有问题。**

**什么时候重载确实更好？** 两个参数的**位置组合**不同
（`fn(a: string, b: number)` / `fn(a: number, b: string)`，联合类型表达不了这种"位置绑定"）；
给**已有函数**加类型（包装第三方库，不能改实现）；你希望调用者看到**清晰的候选列表**。

> **一句话记住它：重载是"多个声明 + 一个实现"，用来告诉编译器"参数决定返回类型"；但它代码量翻倍，绝大多数场景联合类型就够了。**

## 3.5 `this` 类型：一个"假参数"

TS 允许在参数列表的**第一个位置**写一个叫 `this` 的参数：

```ts
function standaloneAdd(this: Counter, n: number): number {
  return this.count + n;
}
```

三个特殊之处：**它是"假参数"**（运行时完全擦掉，调用时**不算进参数个数**，
所以是 `standaloneAdd.call(counter, 1)`）；**唯一作用是给 `this` 定类型**；**必须放第一位**。

**类比**：`this` 参数像会议室门口的"仅限本部门人员"牌子。
它不是参会人（参数），它是一张说明（约束）。没有它，谁都能进来——这就是 `this` 变成 `any` 的下场。

**`noImplicitThis`：为什么必须写。** `strict: true` 里包含它：

```ts
function broken() { return this.name; }
```

```text
error TS2683: 'this' implicitly has type 'any' because it does not have a type annotation.
```

**为什么 TS 不能自己推断 `this`？** 因为函数是"散装"的：
可以被挂在任何对象上、用 `.call` 换掉 `this`、被解构后再调用。
TS 无从知道你打算绑给谁，**所以它诚实地说"我不知道"，而不是假装知道**。
在**对象字面量**或**类**里，`this` 就能推出来：

```ts
const counter: Counter = {
  count: 0,
  add(n) {
    this.count += n;   // this 被推断为 Counter（上下文类型给的）
    return this.count;
  },
};
```

**摘下来的方法会丢 `this`：**

```ts
const extracted = realCounter.add;
extracted(1);
```

```text
error TS2684: The 'this' context of type 'void' is not assignable to
method's 'this' of type 'Counter'.
```

**"`this` context of type `void`"是什么意思？** 意思是"你没给它 `this`"。
方法摘下来之后不再属于任何对象，严格模式下 `this` 就是 undefined。
TS 在 `strictBindCallApply` 下帮你抓住了这个经典 JS 坑。修法：
`extracted.call(realCounter, 1)` 或 `realCounter.add.bind(realCounter)`。
**这个报错在 React 老代码里天天见**：`onClick={this.handleClick}` 忘了 bind，
运行时 `this` 是 undefined。TS 让你在写下的那一刻就知道。

**箭头函数为什么没有自己的 `this`。** 这是 JS 的规则，跟 TS 无关，但面试必问。
规则：**箭头函数没有自己的 `this`，它直接用外层作用域的 `this`。**
（专业说法叫"词法 `this`"——`this` 在定义的位置就定死了，跟怎么调用无关。）

```ts
const holder = {
  value: 42,
  arrow: () => { return typeof this; },     // ❌ 不是 holder！
  normal(): string { return typeof this; }, // ✅ 是 holder
};
holder.normal();   // 'object'
holder.arrow();    // 'undefined' —— ESM 顶层 this 是 undefined
```

**为什么箭头函数拿不到 `holder`？** 因为它定义在对象字面量里，
它的"外层"是模块顶层，不是这个对象。`this` 只跟"函数怎么被调用"有关，
而**对象字面量根本不是一个作用域，也不提供 `this`**。
TS 在这里的贡献是：**它知道箭头函数的 `this` 是外层的，会直接告诉你类型**，
不会给你 `any`，也不会报 `TS2683`。你在箭头函数里写 `this.xxx`，
外层没有 `xxx` 时编译器立刻报错。

**实战结论**：需要 `this` 指向自己 → 用方法简写 `normal() {}`；
当回调传出去、不想管 `this` → 用箭头函数；
数组方法回调、`setTimeout`、事件监听 → 一律箭头函数。

> **一句话记住它：`this` 参数是个只在编译期存在的"假参数"，专门给 `this` 定类型；箭头函数没有自己的 `this`，它用定义位置外层的 `this`。**

## 3.6 函数参数的可变性：回调参数是"逆变"的

**面试高频，也是本章最绕的一节。我用大白话拆，不写数学。**

> **函数类型的"参数"：你的要求只能比对方更宽松，不能更严格。**
> **函数类型的"返回值"：你的东西只能比对方更具体，不能更模糊。**

官方名词：参数**逆变**（contravariant）、返回值**协变**（covariant）。
开关叫 `strictFunctionTypes`（`strict: true` 里包含）。

**真实例子：把回调参数写窄了会出事。**

```ts
type Animal = { name: string; age: number };
type Dog = { name: string; age: number; bark(): void };

const animals: Animal[] = [{ name: 'Cat', age: 3 }];
const dogs: Dog[] = [{ name: 'Wang', age: 4, bark: () => console.log('汪') }];

// 这个函数承诺：任何 Animal 我都能处理
function eachAnimal(list: Animal[], cb: (a: Animal) => void): void {
  for (const a of list) cb(a);
}
eachAnimal(dogs, (d: Dog) => d.bark());   // ❌ 回调参数写窄了
```

```text
error TS2345: Argument of type '(d: Dog) => void' is not assignable to
parameter of type '(a: Animal) => void'.
  Types of parameters 'd' and 'a' are incompatible.
    Property 'bark' is missing in type 'Animal' but required in type 'Dog'.
```

**从最后一行往上读**："`bark` 在 `Animal` 里不存在，但在 `Dog` 里是必需的"，
也就是"你要求的东西比人家承诺的更多"。**这就是逆变的本质。**

**为什么危险？** 因为 `eachAnimal` 内部是 `for (const a of list) cb(a)`——
它会把**每一个**元素交给 `cb`。虽然你这次传的是 `dogs`，
但类型签名允许传 `animals`（里面有 Cat）。**只要签名允许，就不能依赖调用点碰巧传了什么。**
某天有人把它改成 `eachAnimal(animals, ...)`，你的 `(d: Dog) => d.bark()` 就会在 Cat 身上炸掉。
**TS 在你写的那一刻就把这个未来事故拦下来了。**
正确写法是参数保持和承诺一致，需要什么在函数体里自己收窄：

```ts
eachAnimal(animals, (a) => { console.log(a.name); });   // ✅ a 是 Animal，只用公共字段
```

**反向是合法的**（更宽松 → 塞进更严格的位置）：

```ts
function eachDog(list: Dog[], cb: (d: Dog) => void): void {
  for (const d of list) cb(d);
}
eachDog(dogs, (a: Animal) => console.log(a.name));   // ✅
```

因为 `eachDog` 承诺给我的一定是 `Dog`，我只要 `Animal` 那一小部分信息。
**我要求得比它给的少，绝不会出事。** 最直观的理解方式：

> **对方给的多、你要的少 → 安全。对方给的少、你要的多 → 危险。**

**为什么方法参数是"双变"的？** 看这个反例：

```ts
type OnlyMethod<T> = { m(x: T): void };
const dogBox: OnlyMethod<Dog> = { m: (d) => d.bark() };
const animalBox: OnlyMethod<Animal> = dogBox;   // ✅ 编译通过！
// animalBox.m({ name: 'Cat', age: 3 });        // ⚠️ 编译也过，运行时崩
```

| 函数类型的写法 | 参数检查方式 |
|---|---|
| **方法简写** `m(x: T): void` | 双变（宽松，两个方向都放行） |
| **函数属性** `m: (x: T) => void` | 严格逆变（`strictFunctionTypes` 生效） |

**为什么 TS 要开这个后门？** 官方的理由是务实的：`Array<T>`、`Map<K,V>`、`Promise<T>`
这些库类型的成员都是**方法**。如果严格做逆变检查，
`Dog[]` 就**不能**赋给 `Animal[]`（因为 `push(dog)` / `push(animal)` 冲突），
那几乎所有的日常代码都会报错。
**这是一个明确的工程权衡：牺牲"类型完全健全"，换取"实用"。**
第 00 章讲的"TS 是不健全的（unsound）"在这里体现得最清楚。
**实战建议**：回调参数尽量写成方法简写的形式；
**但不要依赖双变去写"参数写窄"的代码**——它今天放过你，明天换个写法就报错，运行时风险是真的。
面试被问"TS 为什么不健全"，**"方法参数双变"就是最好的答案之一。**

**一个必须知道的盲区：泛型参数不做逆变检查。**

```ts
declare function mapStrict<T, U>(arr: T[], f: (x: T) => U): U[];
declare const dogs: Dog[];
mapStrict(dogs, (a: Animal) => a.name);   // ⚠️ 不报错！
```

按上面的规则这里应该报 `TS2345`，但它**不报错**。
对比一下——同样的"参数写宽"，在**非泛型**函数类型上会被抓住：

```ts
declare function useCb(cb: (a: Animal) => void): void;
useCb((d: Dog) => d.bark());   // ❌ TS2345
```

```text
error TS2345: Argument of type '(d: Dog) => void' is not assignable to
parameter of type '(a: Animal) => void'.
  Types of parameters 'd' and 'a' are incompatible.
    Property 'bark' is missing in type 'Animal' but required in type 'Dog'.
```

**原因**：当目标签名里出现类型参数（`T`）时，TS 无法确定 `T` 该被推成 `Dog` 还是 `Animal`
（两个方向都说得通），于是退回"宽松比较"，不做逆变检查。
显式写 `mapStrict<Dog, string>(...)` 也一样——**这是类型参数比较的已知局限。**
**实战结论**：`Array.prototype.map`、`filter` 这类泛型方法**不会**帮你检查回调参数。
规矩得自己守：**写回调时，参数类型永远照抄来源的类型，不要自己"简化"成父类型或加宽成子类型。**

> **一句话记住它：参数逆变 = "你要求的不能比人家给的多"；返回值协变 = "你给的不能比人家要的少"；方法简写双变是官方为了 Array/Map 好用故意开的后门，泛型参数比较则是它的盲区。**

## 3.7 函数类型之间的兼容性：四条人话规则

**规则 1：参数少的可以赋给参数多的——"少要求一点没关系"。**

```ts
type Two = (a: number, b: number) => void;
const zeroArgs = () => console.log('我只要 0 个参数');
const oneArg = (a: number) => console.log('我只要 1 个参数');

const f1: Two = zeroArgs;   // ✅ 合法
const f2: Two = oneArg;     // ✅ 合法
f1(1, 2);
```

**类比**：你找人搬家，要求"来两个工人"。
来了一个说"我一个人搬得动，另一个不用来"——没毛病，**少要求一点是安全的**。反方向不行：

```ts
declare const twoParams: Two;
const f3: (a: number) => void = twoParams;
```

```text
error TS2322: Type 'Two' is not assignable to type '(a: number) => void'.
  Target signature provides too few arguments. Expected 2 or more, but got 1.
```

**为什么不行？** 你承诺"我只要一个参数"，但那个函数内部要用第二个。
调用者按你的承诺只传一个，函数内部就拿到 `undefined`。**多要求就是危险。**
**实战价值**：这条规则解释了为什么你可以这么写：

```ts
[1, 2, 3].map((n) => n * 2);                       // 回调只要 1 个，map 会传 3 个
['a'].forEach(() => console.log('我不关心元素'));    // 一个参数都不要
```

**没有这条规则，你的每个回调都得把 `(value, index, array)` 全写出来。**

**规则 2：返回值必须兼容——"给的东西不能比人家要的少"。**

```ts
const g1: () => void = () => 123;      // ✅ 返回值被丢掉（上面的 void 漏勺）
const g2: () => number = () => {};
```

```text
error TS2322: Type 'void' is not assignable to type 'number'.
```

**规则 3：可选参数 / 联合类型，只能更宽不能更窄。**

```ts
declare const maybeB: (a: number, b?: number) => void;
const needB: (a: number, b: number) => void = maybeB;
```

```text
error TS2322: Type '(a: number, b?: number) => void' is not assignable to
type '(a: number, b: number) => void'.
  Types of parameters 'b' and 'b' are incompatible.
    Type 'number | undefined' is not assignable to type 'number'.
      Type 'undefined' is not assignable to type 'number'.
```

**为什么？** `maybeB` 说"`b` 可能是 `undefined`"，但 `needB` 保证"`b` 一定有值"。
**接收方要的是"一定有"，你只保证"可能有"，这就是窄了。** 联合类型参数同理：

```ts
declare const takesUnion: (a: string | number) => void;
declare const takesString: (a: string) => void;
const u: typeof takesUnion = takesString;
```

```text
error TS2322: Type 'TakesString' is not assignable to type 'TakesUnion'.
  Types of parameters 'a' and 'a' are incompatible.
    Type 'string | number' is not assignable to type 'string'.
      Type 'number' is not assignable to type 'string'.
```

**人话版**：对方说"string 和 number 我都能吃"，你却说"我只吃 string"。
现在有人递过来一个 number，对方本来能处理，你却会吐出来——**你的能力比承诺的窄。**

**规则 4：泛型参数是个例外（见 3.6），别依赖它。**

| 方向 | 结论 | 人话 |
|---|---|---|
| 参数更**少** → 赋给参数多的 | ✅ | 少要求一点没关系 |
| 参数更**多** → 赋给参数少的 | ❌ `TS2322` | 多要求就危险 |
| 返回更**具体** → 赋给返回宽的 | ✅ | 给了就不亏 |
| 返回 `void` → 赋给任意返回类型 | ❌ | void 是"什么都没有" |
| 任意返回 → 赋给 `void` | ✅ | void 是漏勺 |
| 参数是**联合**（宽）→ 赋给单一类型（窄） | ✅ | 能力更强 |
| 参数是单一类型 → 赋给参数是联合的 | ❌ `TS2322` | 能力更弱 |
| 可选参数 → 赋给必需参数 | ❌ `TS2322` | 保证不了"一定有" |
| 必需参数 → 赋给可选参数 | ✅ | 保证更强 |
| 目标签名含泛型 `T` | ⚠️ 不检查 | 已知盲区，自己守住 |

> **一句话记住它：函数兼容性就一句话——"少要求一点没关系，多要求就不行；返回的东西只能更具体，不能更糊"。**

# B 部分 · 对象类型

## 3.8 `interface` 完整语法

如果只记一个语法，记这个：

```ts
interface User {
  readonly id: number;          // 只读属性
  name: string;                 // 必需属性
  age?: number;                 // 可选属性 -> number | undefined
  tags: readonly string[];      // 只读数组
  greet(this: User): string;    // 方法简写
  toJSON(): string;
}
```

**必需属性：漏了就报 `TS2741`。**

```ts
const u: User = { name: 'Ada', tags: [] };   // ❌ 少了 id / greet / toJSON
```

```text
error TS2741: Property 'id' is missing in type '{ name: string; tags: never[]; }'
but required in type 'User'.
```

`TS2741` 是你见得最多的错误码之一，**意思就是"少了必需的属性"**，
报错里会明确告诉你少了哪个，照着补就行。

**可选属性 `?`：读出来一定是 `| undefined`。**

```ts
interface User { id: number; age?: number }
function describeAge(u: User): string {
  return u.age.toFixed(0);
}
```

```text
error TS18048: 'u.age' is possibly 'undefined'.
```

修法：先判断，或者用 `?.` + `??`：

```ts
return u.age === undefined ? '年龄未知' : `他 ${u.age.toFixed(0)} 岁`;
return `他 ${u.age?.toFixed(0) ?? '?'} 岁`;   // 或者这样
```

**只读属性 `readonly`：**

```ts
u.id = 2;
```

```text
error TS2540: Cannot assign to 'id' because it is a read-only property.
```

**`readonly` 只在编译期起作用**——运行时它是普通属性，
`Object.getOwnPropertyDescriptor` 看不出任何区别。它的价值是**表达意图**。
什么时候用？**所有 ID**（`id`、`uuid`、`createdAt`，这些变了就是 bug）、
**配置对象**、**函数参数** `readonly T[]`（向调用者保证"我只读，不会改你的数组"）。
**不要无脑全加**：全 readonly 会让代码没法写中间状态（比如表单对象）。
**领域对象用 readonly，UI 状态对象通常不用。**

**方法：两种写法，有一个真实区别。**

```ts
interface Service {
  get1(path: string): Promise<unknown>;        // ① 方法简写
  get2: (path: string) => Promise<unknown>;    // ② 属性写函数类型
}
```

**① 和 ② 的区别就是 3.6 讲的**：方法简写的参数是**双变**的，函数属性是**逆变**的。
该用哪个？**描述对象的方法 → 方法简写 `get1()`**（社区惯例，也是 `lib.dom.d.ts` 的写法）；
**描述回调、事件处理器 → 属性写法 `onClick: (e: Event) => void`**
（参数检查更严格，能帮你抓到 3.6 里那种"参数写窄"的 bug）。
**这就是为什么 React 的 props 里到处都是 `onClick?: (e: MouseEvent) => void` 这种属性写法。**

**多余的属性会报错——但只在字面量上。**

```ts
const u2: User = { id: 1, nickname: 'Tom', tags: [] };
```

```text
error TS2353: Object literal may only specify known properties,
and 'nickname' does not exist in type 'User'.
```

但这样**不报错**：

```ts
const tmp = { id: 1, nickname: 'Tom', tags: [] };
const u3: User = tmp;    // ✅ 不报错！
```

**为什么？** 因为 `tmp` 这个变量**可能还有别的用途**，TS 只检查"它有没有 User 需要的东西"，
不检查"它有没有多余的"。而对象字面量是"一次性用完就丢"的，多写字段 99% 是拼错了。
**这条规则叫"多余属性检查（excess property checks）"，第 02 章练习 3 考过，面试也爱问。**

> **一句话记住它：`interface` 描述对象形状就四件事——必需、可选 `?`、只读 `readonly`、方法；漏属性报 `TS2741`，多属性（只在字面量上）报 `TS2353`。**

## 3.9 `interface` vs `type`：面试必考，一次讲透

**先说结论：99% 的场景下两者写出来的类型完全一样，选哪个是团队品味问题。
真正有区别的只有 4 件事。**

```ts
interface UserI { name: string; age: number }
type UserT = { name: string; age: number };   // 使用时完全等价
```

**区别 1：`type` 能表达的更多。**

```ts
type Status = 'idle' | 'loading' | 'done';   // 联合类型
type Pair = [number, string];                // 元组
type ID = string | number;                   // 原始类型别名
type Fn = (a: number) => string;             // 函数类型
// interface Status = 'idle' | 'loading';    ❌ 语法错误，interface 一个都写不了
```

**原因在底层**：`interface X { ... }` 的语法结构天生只能描述"有属性的东西"；
`type` 是"给任意类型起名字"，任何类型都能当它的右边。
**所以：只要你要描述的不是"对象形状"，就只有 `type` 一条路。**

**区别 2：`interface` 会"声明合并"，`type` 不会。**

```ts
interface Merged { a: number }
interface Merged { b: string }    // 不报错！自动合并成 { a: number; b: string }
const m: Merged = { a: 1, b: 'x' };   // ✅
const bad: Merged = { a: 1 };         // ❌ TS2741: Property 'b' is missing

type Dup = { a: number };
type Dup = { b: number };   // ❌ 同名 type 直接报错
```

```text
error TS2300: Duplicate identifier 'Dup'.
error TS2300: Duplicate identifier 'Dup'.
```

合并时**同名属性类型不一致**也会报错：

```ts
interface Clash { a: number }
interface Clash { a: string }
```

```text
error TS2717: Subsequent property declarations must have the same type.
Property 'a' must be of type 'number', but here is type 'string'.
```

**为什么要有声明合并？** 它只有一个正经用途：**给别人的类型打补丁**。
比如给 `Window` 加一个全局变量：

```ts
declare global {
  interface Window { __MY_APP__: { version: string }; }
}
```

**这种场景只能用 `interface`**，因为 `type` 没法"重新打开"一个已存在的类型。
**日常业务代码里：不要用声明合并。** 它会让"这个类型到底有几个字段"变得难以追踪
（同名 interface 可能散落在多个文件里），是维护噩梦。

**区别 3：继承写法不同，冲突时的表现更不同。**

```ts
interface BaseA { a: number }
interface BaseB { b: string }

interface ChildI extends BaseA, BaseB { c: boolean }   // 多继承
type ChildT = BaseA & BaseB & { c: boolean };           // 交叉类型
```

两者产出的类型**完全一样**。但**冲突时表现不同**：

```ts
interface ConfA { v: number }
interface ConfB { v: string }
interface ConfChild extends ConfA, ConfB {}   // ❌ 立刻报错
```

```text
error TS2320: Interface 'ConfChild' cannot simultaneously extend types
'ConfA' and 'ConfB'. Named property 'v' of types 'ConfA' and 'ConfB' are not identical.
```

而交叉类型**不报错**，它默默算出一个 `never`：

```ts
type ConfT = ConfA & ConfB;    // 定义处不报错
const bad: ConfT = { v: 'x' };
```

```text
error TS2322: Type 'string' is not assignable to type 'never'.
```

**这就是面试金句**：

> **`interface extends` 冲突会立刻报错（早发现），`type &` 冲突会静默变成 `never`（晚发现）。**

**为什么 `&` 要算成 `never`？** 因为 `number & string` 是"既是数字又是字符串的值"，
这种值不存在，所以是 `never`（第 02 章讲过 `never` 是"不可能的类型"）。
数学上对，但写代码的角度看，它让你在"赋值那一刻"才发现问题。
**小技巧**：写接口优先用 `interface extends`（冲突能早发现），需要拼装已有类型时再用 `type &`。

**区别 4：性能（知道就好，别当决策依据）。** TS 官方文档有过说明，大意是：
`interface` 之间的关系会被**缓存**（因为声明合并让它能被反复重算）；
`type` 别名（尤其交叉类型）是**惰性求值**的，在超大代码库里可能被重复计算，
甚至撑爆编译器的递归深度。
**但是**：这个差别在**你的项目里基本感觉不到**。
几百个类型、几千行代码，两种写法编译时间没区别。
只有**几十万行的巨型代码库 + 大量交叉类型**时才可能显现，而且 TS 5.x 之后优化了很多。
**所以不要拿"性能"当选 `interface` 的理由。**
面试时能说出"官方说 interface 有缓存，交叉类型是惰性的"，再补一句"**日常无感**"，
**这样回答比只背前半句要加分。**

**到底该用哪个：可以直接抄的团队规范。**

```
1. 描述「对象形状」（API 响应、组件 props、配置、领域模型） -> interface
2. 联合类型 / 元组 / 函数类型 / 原始类型别名             -> type
3. 需要 extends 复用                                   -> interface
4. 需要把几个类型拼在一起（& 交叉）                      -> type
5. 需要给别人扩展（声明合并，比如 window.xxx）             -> 必须 interface
6. 需要映射类型 / 条件类型（第 06 章）                    -> 必须 type
7. 同一个文件里两者都出现时，风格保持一致                   -> 别混着写同一件事
```

**最实用的一条**：如果你的团队没有规范，就选一个，**并且在 README 里写下来**。
"两个人用两种写法描述同一个对象"比"选错了"要糟糕得多。

> **一句话记住它：`type` 能表达的更多（联合/元组/函数），`interface` 能扩展的更多（声明合并/多继承）；对象形状用 interface，其他一律 type；冲突时 interface 早报错、type & 变 never。**

## 3.10 索引签名 `[key: string]: T`

有些对象的 key 是**运行时才知道**的：

```ts
interface Env {
  [key: string]: string;
}
const env: Env = { NODE_ENV: 'development', API_URL: 'http://localhost' };
env.DYNAMIC_KEY = 'ok';   // ✅ 任何字符串 key 都行
```

**类比**：普通属性像"编号固定的储物柜"，索引签名像"一整面墙的挂钩"——
墙上可以挂任何东西，但你得先说清楚"这面墙上只挂外套"。
**什么时候用？** 环境变量、HTTP 头、查询参数、字典 `Record<string, number>`、缓存。

**坑 1：它要求所有属性都符合它。**

```ts
interface Scores {
  [subject: string]: number;
  name: string;      // ❌ name 是 string，但索引签名要求 number
}
```

```text
error TS2411: Property 'name' of type 'string' is not assignable to
'string' index type 'number'.
```

**为什么？** 索引签名是一句**公开承诺**："任何字符串 key 拿到的都是 `number`"。
现在 `name` 是 `string`，承诺就破了——别人写 `scores['name']` 时以为拿到 `number`，
结果拿到 `string`，整个类型的意义就没了。修法是放宽索引签名类型：

```ts
interface Scores {
  [subject: string]: string | number;   // 放宽
  name: string;                          // ✅ 现在兼容了
  math: number;
}
```

**代价**：`scores['chinese']` 也变成 `string | number` 了，用之前还得收窄。
**这就是索引签名的核心权衡：越通用，越不精确。**

**坑 2：它会吞掉拼写检查。**

```ts
env.NODE_ENV     // ✅ 对
env.NODE_ENVS    // ✅ 也"对"！因为任何 key 都合法
```

**这是索引签名最大的坏处**：TS 抓不到拼写错误了。
你打错一个字母，编译器一句话都不说，运行时拿到 `undefined`。
**怎么破？** 明确区分"已知字段"和"动态字段"：

```ts
interface Config {
  nodeEnv: string;                    // 已知字段，写具体
  apiUrl: string;
  extra: Record<string, string>;      // 动态字段，关进一个明确的字段里
}
```

**我推荐这个方案**：把"动态部分"关进一个明确的字段里，
不要让整个对象都变成"什么 key 都行"。

**坑 3：点号访问未知 key 会被拦（这是好事）。**

```ts
const v = env.WHATEVER;
```

```text
error TS4111: Property 'WHATEVER' comes from an index signature,
so it must be accessed with ['WHATEVER'].
```

`env['WHATEVER']` 就没问题了。**但要注意**：它的类型是 `string`（不是 `string | undefined`），
**哪怕这个 key 根本不存在**。TS 默认假设"索引签名里什么 key 都有"
（除非开 `noUncheckedIndexedAccess`，第 08 章讲）：

```ts
console.log(env['WHATEVER']);   // undefined —— 但类型说是 string
```

**这就是"类型撒谎"的经典场景**，也是外部数据进来要先校验的原因。

**只读索引签名：**

```ts
interface FrozenDict { readonly [key: string]: number; }
```

```text
error TS2542: Index signature in type 'FrozenDict' only permits reading.
```

和 `readonly` 一样，**它只管第一层**；值如果是对象，里面照样能改。

> **一句话记住它：索引签名解决"key 不固定"的问题，代价是"所有属性都必须符合它" + "拼写错误再也查不出来"；能用具体字段就别用索引签名。**

## 3.11 交叉类型 `&`：合并，以及"冲突变 `never`"

```ts
type Named = { name: string };
type Aged = { age: number };
type Person = Named & Aged;      // { name: string; age: number }
const p: Person = { name: 'Tom', age: 18 };
```

**类比**：交叉类型像把两张购物清单叠在一起——**两边的每一项都必须买到**。
（对比联合类型 `|`：两边任一即可。第 04 章细讲联合。）

| 写法 | 读作 | 要求 |
|---|---|---|
| `A & B` | A **并且** B | 两边的属性都要有 |
| `A \| B` | A **或者** B | 满足一边就行 |

**冲突时会变成 `never`：**

```ts
type Conflict = { v: string } & { v: number };
const bad: Conflict = { v: 'x' };   // ❌ 定义处不报错，赋值时报错
```

```text
error TS2322: Type 'string' is not assignable to type 'never'.
```

读出来也是 `never`：

```ts
const c = {} as Conflict;
const s: string = c.v;
```

```text
error TS2322: Type 'never' is not assignable to type 'string'.
```

**为什么是 `never`？** 因为 `string & number` 是"既是字符串又是数字的值"。
这种值**不存在**，所以类型是 `never`（"不可能有值"的类型）。
`never` 只能赋给 `never`，所以你既构造不出来，也读不出来。
**这算好事还是坏事？** 正确性上是**好事**（客观反映了"不可能有值"）；
开发体验上是**坏事**（报错发生在"赋值那一行"，而不是"定义 `Conflict` 那一行"）。
**实战经验**：看到 `Type 'X' is not assignable to type 'never'`，
**第一反应应该是"我某处写了交叉类型，而且属性冲突了"，去搜 `&` 就行。**

**正经用途：给已有类型"打补丁"。**

```ts
type WithMeta<T> = T & { _meta: { fetchedAt: number } };
const u: WithMeta<{ id: number }> = { id: 1, _meta: { fetchedAt: Date.now() } };
```

**泛型 + 交叉 = 在不修改原类型的前提下附加信息。**
第 05 章讲泛型、第 06 章讲映射类型时会大量看到这个模式。

> **一句话记住它：`&` 是"并且"，要求两边属性都满足；属性冲突时交集是 `never`，意味着这个类型造不出值——看到 `never` 报错先去找 `&`。**

## 3.12 `readonly` 的深浅：它只防第一层

**这是 `readonly` 最大的认知误区。**

```ts
interface Config {
  readonly server: { host: string; port: number };
  readonly name: string;
}
const cfg: Config = { server: { host: 'localhost', port: 80 }, name: 'prod' };

cfg.server = { host: 'x', port: 1 };   // ❌ TS2540 不能重新赋值
cfg.server.port = 8080;                // ✅ 编译通过！！！
cfg.server.host = 'db.internal';       // ✅ 也通过
```

**为什么？** 因为 `readonly` 修饰的是**那个属性槽位**（"server 这个名字不能再指向别的对象"），
而不是"server 指向的那个对象"。那个对象本身还是普通对象。
**类比**：`readonly` 像把储物柜的柜门焊死了（你不能换一个箱子放进去），
但箱子里的东西照样能换（只要你能伸手进去）。

**`Readonly<T>` 也是浅的：**

```ts
type ReadonlyConfig = Readonly<{ server: { host: string } }>;
const rc: ReadonlyConfig = { server: { host: 'localhost' } };
rc.server = { host: 'x' };   // ❌ TS2540 不能重新赋值
rc.server.host = 'x';        // ✅ 照样能改
```

**两种深只读方案。** 方案 A：**手动写深层 `readonly`**（最直接，最推荐）：

```ts
interface Config {
  readonly server: { readonly host: string; readonly port: number };
  readonly name: string;
}
```

方案 B：**递归类型**（第 06 章会讲，先会用就行）：

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
const deepCfg: DeepReadonly<Config> = { server: { host: 'localhost', port: 80 }, name: 'prod' };
deepCfg.server.port = 1;   // ❌ TS2540: Cannot assign to 'port' because it is a read-only property.
```

**我的实战建议**：**不要**给所有东西加 `readonly` 然后期待它保护你的数据；
**要**在"领域对象"上用手动深层 `readonly`；
**要**在函数参数上用 `readonly T[]`（给调用者的承诺，不需要递归）；
**真正需要不可变**（比如 Redux state）→ 用 `DeepReadonly` 或 `as const`。
**顺带说个运行时事实**：`readonly` 和 `Object.freeze` 是两码事。
`readonly` 是纯编译期的，运行时数据完全可改；`Object.freeze` 是运行时的、而且只冻结第一层，
被冻结的对象在类型上也**不会**自动变成深只读。

> **一句话记住它：`readonly` 和 `Readonly<T>` 都只防第一层；要深只读得手写嵌套的 readonly，或者用 `DeepReadonly<T>`。**

## 3.13 `{}` / `object` / `Record<string, never>` 的区别

**面试高频，而且答案反直觉。`{}` 不是"空对象"：**

```ts
const a: {} = 'string 也能赋给 {}';   // ✅
const b: {} = 42;                      // ✅
const c: {} = () => {};                // ✅
const d: {} = { x: 1 };                // ✅
const e: {} = null;                    // ❌
const f: {} = undefined;               // ❌
```

```text
error TS2322: Type 'null' is not assignable to type '{}'.
error TS2322: Type 'undefined' is not assignable to type '{}'.
```

**`{}` 的准确含义是：除了 `null` 和 `undefined` 之外的任何值。**
**为什么？** 因为 `{}` 在类型系统里的意思是"一个没有已知属性的类型"。
而"没有已知属性"这个要求，**所有非空类型都满足**——
`string`、`number`、函数、对象，都可以被当作"一个我不打算访问任何属性的东西"。
**类比**：`{}` 像"任何东西，只要它存在"。
你把它当黑盒——反正你不会去访问它的属性。
`null` 和 `undefined` 连"存在"都算不上，所以被排除。
**所以千万别用 `{}` 表达"空对象"，它拦不住任何东西：**

```ts
function acceptsEmpty(v: {}): void {}
acceptsEmpty('我是字符串');     // ✅ 通过了，你想要的"空对象"检查形同虚设
```

**`object`：任何非原始值。**

```ts
const a: object = { x: 1 };      // ✅
const b: object = [1, 2];        // ✅ 数组也是对象
const c: object = () => {};      // ✅ 函数也是对象
const d: object = new Date();    // ✅
const e: object = 'str';         // ❌
const f: object = 42;            // ❌
```

```text
error TS2322: Type 'string' is not assignable to type 'object'.
error TS2322: Type 'number' is not assignable to type 'object'.
```

**`object` 的含义是：任何非原始类型**（不是 string / number / boolean / symbol / bigint / null / undefined）。
两个容易混的写法：

| 写法 | 含义 |
|---|---|
| `object` | 非原始类型（小写 o） |
| `Object` | **几乎等于 `any`**，别用（大写 O 是 JS 的包装对象接口） |
| `{}` | 除 null/undefined 外的任何值 |

`Object` 有多坑？`const x: Object = 'str'` 是**合法**的。**一律别写大写 `Object`。**

**`Record<string, never>`：真·空对象。**
真想表达"这个对象必须是空的"，只有这个写法管用：

```ts
const empty: Record<string, never> = {};        // ✅
const notEmpty: Record<string, never> = { a: 1 };
```

```text
error TS2322: Type 'number' is not assignable to type 'never'.
```

能用在什么地方？

```ts
type NoOptions = Record<string, never>;
function init(opts: NoOptions = {} as NoOptions): void {}
init();             // ✅
init({ x: 1 });     // ❌ 报错，x 不存在
```

**但说实话，日常几乎用不到。** 真需要"空对象"的场景很少。

**该用什么表达"任意对象"？**

```ts
// ❌ 别用这些
function f1(a: {}): void {}        // 什么都能传，包括 'str'
function f2(a: object): void {}     // 能传数组/函数/Date，但你没法访问属性
function f3(a: Object): void {}     // 约等于 any

// ✅ 用这些
function f4(a: Record<string, unknown>): void {}   // 明确说"是个字典"
function f5<T extends object>(a: T): void {}        // 泛型保留具体类型
```

**我的建议：永远不要用 `{}` 和 `Object`。**
需要"任意字典"就 `Record<string, unknown>`，需要"任意对象但保留类型"就用泛型约束 `T extends object`。

> **一句话记住它：`{}` 是"除 null 和 undefined 外的任何值"（不是空对象！），`object` 是"任何非原始值"，真·空对象只有 `Record<string, never>`；日常请用 `Record<string, unknown>`。**

## 3.14 实战：写一个类型安全的 `ApiClient`

**先定接口：**

```ts
interface ApiClientConfig {
  baseUrl: string;
  timeout?: number;                     // 可选参数
  headers?: Record<string, string>;     // 索引签名
}

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';   // 联合类型 -> 只能用 type

interface RequestOptions {
  readonly method?: HttpMethod;
  readonly headers?: Readonly<Record<string, string>>;
  readonly signal?: AbortSignal;
}

// 核心：泛型方法 + 可选参数
interface ApiClient {
  get<T>(path: string, options?: RequestOptions): Promise<T>;
  post<T, B = unknown>(path: string, body: B, options?: RequestOptions): Promise<T>;
}
```

**为什么 `post` 有两个类型参数？** 因为返回值类型和请求体类型经常是两回事：
你 POST 一个 `CreateUserBody`，拿到的是一个 `UserDTO`。
`<T, B = unknown>` 里的 `B` 有默认值，所以不写也能用。（泛型第 05 章细讲。）

**实现：**

```ts
function createApiClient(config: ApiClientConfig): ApiClient {
  const base = config.baseUrl.replace(/\/$/, '');

  async function request<T>(path: string, body?: unknown, options?: RequestOptions): Promise<T> {
    const res = await fetch(`${base}${path}`, {
      method: options?.method ?? 'GET',
      headers: { 'Content-Type': 'application/json', ...options?.headers },
      body: body === undefined ? undefined : JSON.stringify(body),
      signal: options?.signal,
    });
    if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
    return (await res.json()) as T;   // 边界处：外部数据进来，从这行之后都是类型安全的
  }

  return {
    get: <T>(path: string, options?: RequestOptions) => request<T>(path, undefined, options),
    post: <T, B = unknown>(path: string, body: B, options?: RequestOptions) =>
      request<T>(path, body, { ...options, method: 'POST' }),
  };
}
```

**注意 `as T` 这一行。** 这是全文件唯一一个类型断言，它意味着：
"**我保证服务器返回的就是 `T`；如果它撒谎，运行时会炸，编译器帮不了我。**"
**这不是偷懒，这是所有类型系统的边界。** 外部数据（网络、文件、`localStorage`）
进来时类型系统是断的——你必须在某个点上"接上"。
好的做法是**只有这一个点做断言**，然后用运行时校验（zod 等）兜底。第 09 章会讲更严谨的做法。

**关键一步：给响应定义类型。**

```ts
interface UserDTO {
  id: number;
  name: string;
  tags: string[];
}
const api = createApiClient({ baseUrl: 'https://api.example.com' });
const user = await api.get<UserDTO>('/user/1');

user.name.toUpperCase();   // ✅ 编译器知道是 string
user.tags.join(',');       // ✅ 知道是 string[]
user.age;                  // ❌ TS2339: Property 'age' does not exist on type 'UserDTO'.
```

**"改一个字段所有调用点都报错"的体验，就发生在这一步。**
假设后端把 `name` 改成 `nickname`，你只改一行：

```ts
interface UserDTO {
  id: number;
  nickname: string;    // 只改这一行
  tags: string[];
}
```

然后：`user.name` → 立刻 `TS2339: Property 'name' does not exist on type 'UserDTO'.`；
编辑器（VS Code）会在"问题"面板里列出**所有**用到 `user.name` 的地方。
**不用全局搜索，不用靠记忆，不会漏。**
**这就是"类型是资产"最实在的体现。** 你花 3 分钟写 `UserDTO`，
省下的是未来某次改字段时 3 小时的排查。

**一个反直觉的地方：多写字段不报错。**

```ts
function renderUser(u: UserDTO): string { /* ... */ }
renderUser({ id: 1, nickname: 'Tom', tags: [] });   // ❌ TS2353

const tmp = { id: 1, nickname: 'Tom', tags: [] };
renderUser(tmp);      // ✅ 通过了！
```

```text
error TS2353: Object literal may only specify known properties,
and 'nickname' does not exist in type 'UserDTO'.
```

**又是"多余属性检查只针对对象字面量"这条规则。**
所以：直接把 API 返回的数据（`any`/`unknown`）塞给函数时，**不会**有多余属性检查。
**想要真正的健壮性，必须做运行时校验**（第 09 章）。

> **一句话记住它：`ApiClient` 的价值不在"能发请求"，而在"你给响应定了类型"——那一步之后的每一次字段改动，编译器都会替你列出所有受影响的地方。**

## 3.15 本章常见坑速查

| 坑 | 报错 | 解法 |
|---|---|---|
| 回调参数写窄了 | `TS2345 ... Property 'bark' is missing in type 'Animal'` | 参数照抄来源类型，在函数体里收窄 |
| 可选参数放前面 | `TS1016: A required parameter cannot follow an optional parameter` | 必需参数放前 |
| 类型写进解构里 | `TS7031` + `TS2304` 一起出现 | 类型写在解构外面，描述整个对象 |
| 异步函数返回类型写成 `T` | `TS1064 ... Did you mean 'Promise<T>'` | 写 `Promise<T>` |
| 重载的实现在声明前面 | `TS2394: This overload signature is not compatible...` | 声明在实现前，实现要兼容所有声明 |
| 重载调用不匹配 | `TS2769: No overload matches this call` | 从上往下读它列的每一条 |
| 漏了必需属性 | `TS2741: Property 'x' is missing` | 补上，或改成可选 `?` |
| 多写了属性（字面量） | `TS2353: Object literal may only specify known properties` | 检查拼写；变量赋值不触发这个检查 |
| 改只读属性 | `TS2540: Cannot assign to 'x' because it is a read-only property` | 去掉 `readonly`，或改设计 |
| 隐藏了 `this` | `TS2683: 'this' implicitly has type 'any'` | 加 `this` 参数，或写进对象/类里 |
| 摘下来的方法丢 `this` | `TS2684: The 'this' context of type 'void' is not assignable...` | `.call()` / `.bind()`，或用箭头函数 |
| 索引签名和属性冲突 | `TS2411: Property 'x' of type 'A' is not assignable to index type 'B'` | 放宽索引签名类型 |
| 点号访问索引签名的 key | `TS4111: ... must be accessed with ['x']` | 用方括号访问 |
| 用了 `{}` 当空对象 | 传 `'str'` 也不报错 | 用 `Record<string, never>` 或具体 interface |
| 改名引起大面积报错 | `TS2339: Property 'x' does not exist` | **这是好事**，照着改 |
| `interface` 多继承冲突 | `TS2320: cannot simultaneously extend` | 修正冲突字段，或改用 `&`（但会变 never） |
| 交叉类型属性冲突 | `TS2322: Type 'string' is not assignable to type 'never'` | 去搜 `&`，找出冲突的两个类型 |

## 3.16 本章小结

```
函数类型 ──────── type Fn = (a: A) => B      ┐ 两者等价
                 interface Fn { (a: A): B }    ┘ 类型位置的 => 只是「函数」
     │
参数 ──────────── ? 可选（必须放最后）/ 默认值（自动可选）
                 ...rest（必须是数组）/ 解构（类型写在整体上）
     │
返回值 ────────── void（漏勺）/ Promise<T>（async 必须这么写）/ this（链式调用）
     │
重载 ──────────── 多个声明 + 一个实现；能不用就不用，优先联合类型
     │
this ──────────── 假参数，只在编译期；箭头函数没有自己的 this
     │
可变性 ────────── 参数逆变（只能更宽）/ 返回值协变（只能更具体）
                 方法简写双变（官方后门）/ 泛型比较是盲区
     │
兼容性 ────────── 少要求一点没关系，多要求就不行
     │
对象类型 ──────── interface { 必需 / 可选? / 只读readonly / 方法 }
     │
interface vs type  对象形状用 interface；联合/元组/函数用 type
                   interface 能声明合并 + 多继承；type & 冲突变 never
     │
索引签名 ──────── [key: string]: T —— 解决动态 key，代价是吞掉拼写检查
     │
readonly ──────── 只防第一层；深只读要 DeepReadonly<T>
     │
{} ────────────── 「除 null / undefined 外的任何值」，不是空对象
```

**四句话带走：**

1. **类型位置的 `=>` 只是"函数"两个字，它跟箭头函数没有半点关系。**
2. **函数参数只能"要求得更少"，不能"要求得更多"**——这是逆变的人话版，也是面试最爱问的。
3. **对象形状用 `interface`，其他用 `type`**；两者真正的区别只有声明合并和冲突时机。
4. **`readonly` 是浅的，`{}` 不是空对象**——这两条能帮你在面试和实际代码里各躲一个坑。
