## 9.0 这一章要给你什么

前面八章你学的是一块块零件：类型注解、联合、收窄、泛型、工具类型、类与模块。
这一章不讲新语法，只讲**七个把零件拼成工程结构的套路**。

丑话说在前面：**这七个模式都不是"必须用"**。它们各自解决一种特定形状的痛点，
你的需求不是那个形状，用了就是给自己找麻烦。所以每一节都有"什么时候不该用"。

| # | 模式 | 它替你解决的问题 |
|---|---|---|
| 1 | `Result<T, E>` | 可预期的失败被异常掩盖，调用者不知道函数会失败 |
| 2 | 判别联合 + 状态机 | "一个宽 status 字段 + 一堆 if" 让非法状态也能写出来 |
| 3 | Branded Type | `UserId` 和 `OrderId` 都是 `string`，传错了编译器不吭声 |
| 4 | 类型安全 API 层 | 路由、请求体、响应体的关系只存在于文档里 |
| 5 | Builder + 泛型累积 | 对象一步步攒出来，构造过程毫无约束 |
| 6 | 依赖注入 + 结构化类型 | 为了写测试要引一整套 mock 框架 |
| 7 | `satisfies` | 要么丢掉推断（写 `: T`），要么丢掉检查（什么都不写） |

## 9.1 模式一：`Result<T, E>` —— 不抛异常的错误处理

### 它解决什么问题

```ts
function parseAge(input: string): number {
  const n = Number(input);
  if (!Number.isInteger(n) || n < 0) {
    throw new Error('年龄不合法');
  }
  return n;
}
```

签名 `(input: string) => number` 在说："给我字符串，我还你数字。" **但这是个谎言，它还可能炸掉。**

调用者不看实现，永远不知道要包 `try`：

```ts
const age = parseAge(userInput);   // 类型上毫无破绽，用户输入 "abc" 就在这里崩
```

问题的本质：**"会失败"这件事没有写进类型。**

### 为什么 `catch` 里是 `unknown`

你可能想用 `try/catch` 兜住，但会遇到另一个问题：

```ts
try {
  JSON.parse(text);
} catch (e) {
  console.log(e.message);
}
```

```text
error TS18046: 'e' is of type 'unknown'.
```

TS 为什么故意为难你？**因为这是真话。** JS 里 `throw` 后面可以跟任何东西：

```js
throw new Error('正常错误');
throw '一个字符串';        // 合法
throw { code: 500 };      // 合法
throw undefined;          // 还合法
```

既然运行时什么都能扔出来，编译器说"`e` 是 `Error`"就是骗你，
它只能说 `unknown`——"我不知道这是什么，你先验证再用"。于是每个 `catch` 块开头都得写：

```ts
catch (e) {
  const message = e instanceof Error ? e.message : String(e);
}
```

**写得多了你会发现：`try/catch` 把类型信息丢在了门口，你要在门口重新捡一遍。**
这就是它"丢掉错误信息"的含义——不是信息没了，而是类型上没有了，全靠手工还原。

> 类比：`throw` 像**拉响火警**。整栋楼的人都得停下手里的事跑出来，
> 但火在哪一层、什么火，警报里没说。
>
> `Result` 像**填一张报修单**。修好没修好、没修好为什么，
> 都写在同一张单子上，跟着流程走。

### 术语：`Result` 是一个判别联合

```ts
export type Ok<T> = { readonly ok: true; readonly value: T };
export type Err<E> = { readonly ok: false; readonly error: E };
export type Result<T, E> = Ok<T> | Err<E>;

/** 构造一个"成功"结果。显式标注返回类型，避免字面量被推成 boolean。 */
export function ok<T>(value: T): Ok<T> {
  return { ok: true, value };
}

/** 构造一个"失败"结果。 */
export function err<E>(error: E): Err<E> {
  return { ok: false, error };
}
```

零件你都在第 04、05 章学过：**判别联合**（判别字段是 `ok`）+ **泛型**
（`T` 是成功的数据，`E` 是失败的原因）。

> 为什么要写 `: Ok<T>` 这个返回类型？因为 `{ ok: true, value }` 里的 `true` 会被推断成
> `boolean`，那就不是判别字段了，`r.ok` 判断之后 TS 收窄不了。
> **显式返回类型在这里是功能性的，不是装饰性的。**

### 用法：收窄是天然的

（下面的 `declare const` 是"假装有这种类型的变量"，专门看类型用，**不能运行**，第 01 章讲过。）

```ts
declare const r: Result<number, string>;

if (r.ok) {
  r.value;   // 这里 r 是 Ok<number>
  r.error;   // 编译错误：Ok 上没有 error
} else {
  r.error;   // 这里 r 是 Err<string>
}
```

不判断就取值：

```ts
declare const r: Result<number, string>;
const v = r.value;
```

```text
error TS2339: Property 'value' does not exist on type 'Result<number, string>'.
  Property 'value' does not exist on type 'Err<string>'.
```

**读报错的方法**：第二行是关键。它在说"联合里 `Err<string>` 这一支没有 `value`"。
看到 TS2339 后面跟一行 "Property ... does not exist on type ..."，基本就是这个意思。

### 组合子：`map` 和 `unwrapOr`

真实项目里 `if (!r.ok) return r;` 会写到手酸，所以要配组合子
（组合子 = 把小操作拼成大操作的函数）。

```ts
/** 成功就变换其中的值，失败就原样透传。Result 版的 Array.prototype.map。 */
export function map<T, U, E>(r: Result<T, E>, f: (value: T) => U): Result<U, E> {
  if (!r.ok) return r;      // 失败分支直接透传，这里类型上已经是 Err<E>
  return ok(f(r.value));
}

/** 成功就取出来，失败就用兜底值。Result 版的 ?? 。 */
export function unwrapOr<T, E>(r: Result<T, E>, fallback: T): T {
  return r.ok ? r.value : fallback;
}
```

跑一个完整的（下面这段自包含，存成 `result-demo.ts` 直接 `node result-demo.ts` 就能跑）：

```ts
// ── 可运行 ──
type Result<T, E> = { readonly ok: true; readonly value: T } | { readonly ok: false; readonly error: E };

function ok<T>(value: T): Result<T, never> {
  return { ok: true, value };
}
function err<E>(error: E): Result<never, E> {
  return { ok: false, error };
}
function map<T, U, E>(r: Result<T, E>, f: (value: T) => U): Result<U, E> {
  if (!r.ok) return r;
  return ok(f(r.value));
}
function unwrapOr<T, E>(r: Result<T, E>, fallback: T): T {
  return r.ok ? r.value : fallback;
}

const good: Result<number, string> = ok(21);
const bad: Result<number, string> = err('解析失败');

console.log(map(good, (n) => n * 2));   // { ok: true, value: 42 }
console.log(map(bad, (n) => n * 2));    // { ok: false, error: '解析失败' }
console.log(unwrapOr(bad, 0));          // 0
```

> 项目里 `ok` / `err` 的签名是 `ok<T>(value: T): Ok<T>`，比上面这版直白，
> 代价是推断不出 `E`，调用点要写类型注解。**两种写法都对，选团队习惯的那个。**

### `assertNever`：`Result` 的错误类型通常是判别联合

项目里的 `TaskError` 就是这样：

```ts
export type TaskError =
  | { readonly kind: 'invalid-id'; readonly raw: string; readonly reason: string }
  | { readonly kind: 'empty-title' }
  | { readonly kind: 'repo'; readonly cause: RepoError }
  | {
      readonly kind: 'invalid-transition';
      readonly id: TaskId;
      readonly from: Task['status']['kind'];
      readonly to: Task['status']['kind'];
    };
```

把它翻成中文的函数必须以 `assertNever` 收尾。**因为你早晚会加一个新分支，而那时你多半忘了这里。**

```ts
export function assertNever(value: never): never {
  throw new Error(`未处理的分支：${JSON.stringify(value)}`);
}
```

忘了处理就是**编译期红灯**：

```ts
declare const someKind: 'todo' | 'doing';
assertNever(someKind);
```

```text
error TS2345: Argument of type '"todo" | "doing"' is not assignable to parameter of type 'never'.
  Type '"todo"' is not assignable to type 'never'.
```

**注意这行的写法**：`never` 是"不可能有值"的类型，能传给它的只有 `never` 自己。
所以 `switch` 一旦漏了分支，剩下的类型就不是 `never`，这行立刻报错。

### 什么时候抛异常，什么时候返回 `Result`

判断标准只有一条：**这个失败是不是"正常业务流程的一部分"。**

| 用 `Result`（可预期的业务失败） | 用 `throw`（程序员错误 / 不可恢复） |
|---|---|
| 用户填的 ID 格式不对 | 数组越界、在 `undefined` 上取属性 |
| 邮箱已被注册 | 配置项缺失，程序根本没法启动 |
| 库存不足、余额不够 | 数据库连不上（整个请求都没意义了） |
| 状态机不允许的转换 | 我写错了代码，这是 bug |

一个更短的判断法：

> **能写出"失败了该怎么办"的，用 `Result`；写不出来的，用 `throw`。**
>
> "邮箱已注册" → 能办：提示用户换一个。用 `Result`。
> "数组下标是 -1" → 没法办，代码写错了。让它崩，或者抛。

**别走极端。** 我见过把所有 `throw` 都改成 `Result` 的项目，
结果 `Result<Result<Result<T>>>` 三层嵌套，作者自己都写不清楚。
业务流程之外的失败，就让它抛。

### TS 没有 Rust 的 `?`，实际项目里怎么优雅地链式处理

如果你写过 Rust，会想念这个：

```rust
let user = repo.find(id)?;      // 失败就自动 return
```

`?` 的意思是"成功就取出值，失败就立刻把错误 return 出去"。
**TypeScript 没有这个运算符**，而且因为类型擦除（第 01 章），也不可能有。
实际项目里的"优雅"其实是三招：

**第一招：早返回（卫语句），覆盖 95% 的场景。**

```ts
transition(id: TaskId, to: StatusKind): Result<Task, TaskError> {
  const taskResult = this.#repo.find(id);
  if (!taskResult.ok) return err(fromRepo(taskResult.error));   // ← 失败就地出局

  const task = taskResult.value;                                 // ← 收窄已完成
  // ... 后面所有代码都活在"成功世界"里，不用再嵌套
}
```

**这段真实代码在 `examples/project/service.ts` 的 `transition` 方法里。**
`if (!x.ok) return` 之后 TS 自动把 `x` 收窄成 `Ok<T>`，后面直接 `.value`。

**第二招：链式的 `andThen`（要串三步以上时）。**

```ts
export function andThen<T, U, E>(r: Result<T, E>, f: (value: T) => Result<U, E>): Result<U, E> {
  if (!r.ok) return r;
  return f(r.value);
}

const flow = andThen(taskId(raw), (id) => service.createTask(id, title));
```

**第三招：生成器 + runner（`yield*` 风格）。** 有些库（如 `neverthrow`）用 `function*` 把 `yield` 当 `?` 用。
**我不推荐在业务项目里上这个**——它会让团队里其他人看不懂，收益也只是省几行 `if`。

**一句话记住它：异常适合"程序坏了"，`Result` 适合"业务没成"——把后者写进类型，调用者才不用靠猜。**

## 9.2 模式二：判别联合建模业务状态（状态机）

### 它解决什么问题

你要做表单提交，顺手就这么写了：

```ts
interface FormState {
  loading: boolean;
  error: string | null;
  data: User | null;
}
```

三个字段能组合出 `2 × 2 × 2 = 8` 种状态，业务上只有 4 种合理：

| 真实状态 | loading | error | data |
|---|---|---|---|
| 还没提交 | `false` | `null` | `null` |
| 提交中 | `true` | `null` | `null` |
| 成功 | `false` | `null` | `User` |
| 失败 | `false` | `'...'` | `null` |

剩下 4 种是**非法状态**（`loading: true` 同时 `error: 'xxx'`、
`error` 和 `data` 同时有值……），类型系统一视同仁，全部放行。

**这种结构会在你脑子里留下一张"隐含的合法组合表"，而表只存在于你脑子里。**
三个月后接手的人不知道这张表，他会在 `loading: true` 的时候去读 `data`，然后线上崩。

### 术语：让非法状态无法表示

正式名字：**make illegal states unrepresentable**（让非法状态无法表示）。
做法就是把"隐含的组合表"变成"几个互相排斥的形状"——第 04 章的判别联合。

> 类比：`{ loading, error, data }` 像一张**表格**，允许你随便勾格子，勾出什么组合都可能。
> 判别联合像**开关面板上的几个物理按钮**——同一时刻只能按下一个，因为结构上就互斥。

### 项目里的真实代码（`types.ts`）

```ts
export type TaskStatus =
  | { readonly kind: 'todo' }
  | { readonly kind: 'doing'; readonly startedAt: string }
  | { readonly kind: 'done'; readonly startedAt: string; readonly finishedAt: string };
```

**每个分支带的字段不一样**，这正是它比 `status: string` 强的地方：

- `todo` 的任务**没有** `startedAt` 这个字段，你想读都读不到。
- `done` 的任务**一定**有 `finishedAt`，你不需要写 `if (finishedAt)` 兜底。

真实报错：

```ts
declare function describeStatus(status: TaskStatus): string;
declare const st: { kind: 'doing' };     // 忘了带 startedAt
describeStatus(st);
```

```text
error TS2345: Argument of type '{ kind: "doing"; }' is not assignable to parameter of type 'TaskStatus'.
  Property 'startedAt' is missing in type '{ kind: "doing"; }' but required in type '{ readonly kind: "doing"; readonly startedAt: string; }'.
```

**第二行就是判据**：它明确说"doing 这一支要求 `startedAt`，你没给"。
如果 `TaskStatus` 是带 `status: string` 的接口，这个错误永远不会出现，bug 会跑到运行时。

### 状态机：把"合法的走法"写成数据

光有互斥状态不够，还要回答"能不能从 A 走到 B"。我把这张图直接写成对象（`service.ts`）：

```ts
export type StatusKind = Task['status']['kind'];

export const ALLOWED = {
  todo: ['doing'],
  doing: ['done'],
  done: ['done'], // 已完成是终态；允许"再完成一次"= 幂等
} as const satisfies Record<StatusKind, readonly StatusKind[]>;
```

`as const satisfies ...` 的效果（9.7 节专讲）：**值被检查了**（每个状态都得列出来），
**同时字面量信息没丢**（`ALLOWED.done` 真的是 `readonly ['done']`）。

### 真实报错：一个我实际踩到的坑

最自然的写法：

```ts
export function canTransitionDirect(from: StatusKind, to: StatusKind): boolean {
  return ALLOWED[from].includes(to);
}
```

这行看着天经地义，但编译不过：

```text
error TS2345: Argument of type 'StatusKind' is not assignable to parameter of type 'never'.
  Type '"done"' is not assignable to type 'never'.
```

**为什么？** `from` 是联合类型 `'todo' | 'doing' | 'done'`，
所以 `ALLOWED[from]` 是三种类型的**交集**：

```
readonly ['doing'] & readonly ['done'] & readonly ['done']
```

一个"只能装 doing"又"只能装 done"的数组，元素类型只能是 `never`，
于是 `includes` 的参数类型成了 `never`，`to` 传不进去。

**修法只有一行**——用带注解的本地变量把三个分支合并回联合：

```ts
export function canTransition(from: StatusKind, to: StatusKind): boolean {
  const allowed: readonly StatusKind[] = ALLOWED[from];   // ← 这一行是修复
  return allowed.includes(to);
}
```

**这个坑代表一整类错误**：在联合类型上做索引访问，得到的是"所有分支的交集"，
不是"所有分支的并集"。想合并，先落到一个带注解的变量上。
（上面的 `canTransition` 就在 `examples/project/service.ts` 里。）

### `assertNever`：让编译器追着你改

状态机里每个 `switch` 都该这么收尾：

```ts
export function describeStatus(status: TaskStatus): string {
  switch (status.kind) {
    case 'todo':
      return '待办';
    case 'doing':
      return `进行中（开始于 ${status.startedAt}）`;
    case 'done':
      return `已完成（${status.startedAt} → ${status.finishedAt}）`;
    default:
      return assertNever(status);      // ← 少一个 case 就在这里报错
  }
}
```

明天你加了 `{ kind: 'archived' }`，这个函数立刻编译不过。
**你不用记得去搜"哪些地方用了 TaskStatus"——编译器替你搜了。**

### 项目里的状态转换

`service.ts` 的 `nextStatus` 同时吃到了两个模式的好处：

```ts
function nextStatus(status: Task['status'], to: StatusKind): Task['status'] | undefined {
  if (!canTransition(status.kind, to)) return undefined;

  switch (to) {
    case 'todo':
      return { kind: 'todo' };
    case 'doing':
      // 如果本来就是 doing，保留原来的开始时间（不要重新计时）
      return status.kind === 'doing'
        ? status
        : { kind: 'doing', startedAt: new Date().toISOString() };
    case 'done':
      return status.kind === 'done'
        ? status
        : {
            kind: 'done',
            startedAt: status.kind === 'doing' ? status.startedAt : new Date().toISOString(),
            finishedAt: new Date().toISOString(),
          };
    default:
      return assertNever(to);
  }
}
```

**这段代码用到了本章两个模式**：

1. **模式二（判别联合 + 状态机）**：每个分支返回的形状不同，`done` 必须给 `finishedAt`，
   `todo` 一个字段都不能给——给错了编译不过。
2. **模式一（`Result` 的接壤）**：它自己返回 `Task['status'] | undefined`，
   由调用方 `transition` 转成 `Result`。**纯函数判合法性，边界处转 `Result`，这是分层的好习惯。**

### 什么时候不该用

- **状态少于 3 个、转换规则杂乱无章**：收益不大。`'yes' | 'no'` 用 `boolean` 挺好，
  别为了"模式"给 `true` / `false` 各建一个 interface。
- **状态之间字段高度重合**（五种状态都带同样的 8 个字段）：判别联合会让每个 `case` 都在复制粘贴。
  这时**共享字段 + 一个窄的判别字段**更实际：

  ```ts
  interface Job { id: string; payload: string; status: 'queued' | 'running' | 'ok' | 'failed'; error?: string }
  ```

  代价是 `error` 又变可选了——**这是权衡，不是错误。**
- **状态是外部 API 给的、你控制不了**：先按 API 的形状建模，在边界做运行时校验，
  再转成你的内部状态机。

**一句话记住它：判别联合让"合法的组合"变成唯一的写法，"非法的组合"连写法都没有。**

## 9.3 模式三：Branded Type —— 给 `string` 加上语义

### 它解决什么问题

```ts
declare function findUser(id: string): Promise<unknown>;
declare function findOrder(id: string): Promise<unknown>;

const userId = 'u-001';
const orderId = 'o-888';

findUser(orderId);      // 传错了，但 TS 觉得完全没问题
findOrder(userId);      // 同上
```

两个 ID 都是 `string`，在编译器眼里**一模一样**。它拦不住你，因为在这个层面上确实没法拦。
问题在于：**`string` 丢掉了"这是谁的 ID"这个信息。**

> 类比：`string` 像一张**白纸**，你可以在上面写"用户 ID"或"订单 ID"，但白纸不知道自己写了什么。
> Branded Type 像一张**印好抬头的信纸**——抬头写着"用户 ID"，
> 你拿它去寄订单的信，窗口直接退回来。

### 术语：在结构化类型系统里模拟"名义类型"

- **结构化类型**（structural typing）：TS 的默认哲学，"看形状不看名字"（第 00 章）。
- **名义类型**（nominal typing）：Java / C# 那样"看名字，名字不同就是不同类型"。
- **Branded Type / Opaque Type**：用交叉类型在结构化系统里**模拟**名义类型。

解法（`types.ts`）：

```ts
export type Brand<T, B extends string> = T & { readonly __brand: B };

/** 任务 ID：只能由 taskId() 造出来，普通字符串赋值会报错。 */
export type TaskId = Brand<string, 'TaskId'>;
```

读懂 `string & { readonly __brand: 'TaskId' }`：

- 它**首先是一个 `string`**（交叉类型，第 03 章），能 `.trim()`、能拼字符串、能当 Map 的键。
- 它**额外**要求有一个 `__brand` 属性，值是字面量 `'TaskId'`。
- 普通的 `string` **没有**这个属性，所以不能被赋值给它。

那个 `__brand` **运行时根本不存在**。我实测过：

```ts
// ── 可运行 ──
type Brand<T, B extends string> = T & { readonly __brand: B };
type TaskId = Brand<string, 'TaskId'>;

const id = 't-001' as TaskId;
console.log('值本身        :', id);
console.log('typeof        :', typeof id);
console.log('自有键        :', Object.keys(id));
console.log('有 __brand 吗 :', '__brand' in Object(id));
```

```text
值本身        : t-001
typeof        : string
自有键        : [ '0', '1', '2', '3', '4' ]
有 __brand 吗 : false
```

（那几个 `'0'`…`'4'` 是字符串的字符索引，不是我们的标记。）
**`__brand` 是纯类型层面的东西，编译后一个字节都不剩**——第 01 章"类型擦除"的直接体现。

### 真实报错

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };
type UserId = Brand<string, 'UserId'>;
type TaskId = Brand<string, 'TaskId'>;

declare const userId: UserId;

const a: TaskId = 'task-1';     // 报错 1
const b: TaskId = userId;       // 报错 2
```

```text
error TS2322: Type 'string' is not assignable to type 'TaskId'.
  Type 'string' is not assignable to type '{ readonly __brand: "TaskId"; }'.
error TS2322: Type 'UserId' is not assignable to type 'TaskId'.
  Type 'UserId' is not assignable to type '{ readonly __brand: "TaskId"; }'.
    Types of property '__brand' are incompatible.
      Type '"UserId"' is not assignable to type '"TaskId"'.
```

**第二个报错是本节最漂亮的地方。** 看它第三、四行：
`Types of property '__brand' are incompatible. Type '"UserId"' is not assignable to type '"TaskId"'.`

编译器明确告诉你："**`__brand` 这一栏写的是 UserId，我要的是 TaskId。**"
白纸变成了带抬头的信纸，错误信息也能说人话了。

### 代价：必须有校验/构造入口

品牌类型换来安全，付出的是**一点点不方便**：

```ts
const id: TaskId = 't-001';      // 编译不过
const id = 't-001' as TaskId;    // 能过，但你在对编译器撒谎
```

`as` 是"我对编译器打包票"。所以**全项目只允许有一个地方出现 `as TaskId`，而且那里必须真有校验**：

```ts
/**
 * 唯一的构造入口（也叫"智能构造器"）。
 * 所有外部字符串想变成 TaskId，都必须从这里过一道校验。
 */
export function taskId(raw: string): Result<TaskId, string> {
  const trimmed = raw.trim();
  if (trimmed.length < 3) {
    return err(`任务 ID 至少 3 个字符，收到：${JSON.stringify(raw)}`);
  }
  // 这里是全项目唯一允许把 string 断言成 TaskId 的地方。
  // 类型断言是"我对编译器打包票"，所以只准出现在有真校验守着的地方。
  return ok(trimmed as TaskId);
}
```

**注意它返回 `Result`，不是直接 `throw`**——这就是模式一和模式三在这里的配合。
命令行传进来的 `ab` 变成了可预期的失败，而不是崩溃：

```text
[FAIL] 建立 ab（故意失败） -> 任务 ID 不合法：任务 ID 至少 3 个字符，收到："ab"（原值 "ab"）
```

**这段代码在 `examples/project/types.ts` 里，`main.ts` 的 `toTaskId()` 是它的调用方**——
命令行参数永远是 `string`，必须过构造器才能变成 `TaskId`。

### 再加一个：给数字做范围约束

`string` 是语义丢失最严重的类型，但**任何原始类型都能贴品牌**，数字最典型的用法是范围约束：

```ts
type PositiveInt = Brand<number, 'PositiveInt'>;

function positiveInt(raw: number): Result<PositiveInt, string> {
  if (!Number.isSafeInteger(raw) || raw <= 0) {
    return err(`必须是正整数，收到：${raw}`);
  }
  return ok(raw as PositiveInt);
}
```

好处是"**校验一次，之后一路放心**"：

```ts
declare function fetchPage(page: PositiveInt): void;

fetchPage(0);      // 拦在编译期，不用等服务端返回 400
fetchPage(-1);     // 同上
fetchPage(1);      // 也报错，因为 1 是 number，不是 PositiveInt
```

最后一行最容易让人不爽：**字面量 `1` 也不能直接传**，必须走 `positiveInt(1)`。
我不否认它啰嗦，但要看场景：

- **只在内部传两层的小工具**：不值得，`number` 加一句注释就够。
- **贯穿几十个函数、值来自用户输入 / 数据库 / 第三方接口**：**非常值得**，
  因为你只需在入口校验一次，后面几十处调用点全部免检。

### 面试考点

"**TS 是结构化类型，怎么实现 Java 那种名义类型的效果？**" 标准答案三步：

1. **用交叉类型加一个假字段**：`T & { readonly __brand: 'X' }`。
2. **它只在类型层面存在**，运行时零开销（类型被擦除）。
3. **配合一个智能构造器**，保证只有合法值才能拿到这个类型。

追问一："为什么要 `readonly`？"——不加的话别人可以 `id.__brand = 'TaskId'` 伪造一个，`readonly` 挡住这条路径。

追问二："为什么不用 `declare const __brand: unique symbol`？"——那是更严密的写法
（`unique symbol` 无法伪造），但多写几行样板，而且类型提示里显示成一串看不懂的 symbol 描述，
**报错可读性变差**。业务代码里我推荐上面这个朴素版本：够用，且报错好读。

### 什么时候不该用

- **只为了一两个函数做区分**：`type UserId = string` 的别名就够了（拦不住错误，但文档作用达到了）。
- **品牌类型跨边界传播时**：`JSON.parse` 出来的东西**永远**没有品牌。
  数据库、HTTP、命令行拿到的都是普通类型，每个边界都要重新过一次构造器。
  **边界特别多的项目里，品牌类型会变成一堆 `taskId(x)` 的噪音。**
- **团队还没养成"不乱写 `as`"的习惯时**：品牌类型的安全性完全依赖这一点。
  这一条不成立，它就是个心理安慰。

**一句话记住它：品牌类型是把"这个 string 是什么意思"从注释和会议里，搬到了编译器眼皮底下。**

## 9.4 模式四：类型安全的 API 层

### 它解决什么问题

```ts
// ❌ 你可能这么写
async function createTask(body: any) {
  const res = await fetch('/api/tasks', { method: 'POST', body: JSON.stringify(body) });
  return res.json();          // 返回 any
}

const created = await createTask({ name: '买牛奶' });  // 字段名写错了
console.log(created.status);                            // 运行时才发现是 undefined
```

这里有三处信息**只存在于文档和同事脑子里**：
`POST /api/tasks` 要哪些字段？响应长什么样？哪些路由要路径参数？
类型系统完全不知道，所以 `body` 是 `any`，响应也是 `any`。

### 术语：用一张表描述所有路由

做法是**先把整张路由表写成一个 interface**，再让 `request` 从表里取类型。

```ts
interface ApiRoutes {
  'GET /tasks': {
    params: Record<string, never>;                 // 没有路径参数
    query: { status?: 'todo' | 'doing' | 'done' }; // 可选筛选
    body: void;                                    // GET 没有请求体
    response: { id: string; title: string }[];
  };
  'POST /tasks': {
    params: Record<string, never>;
    query: Record<string, never>;
    body: { title: string };
    response: { id: string; title: string };
  };
  'GET /tasks/:id': {
    params: { id: string };
    query: Record<string, never>;
    body: void;
    response: { id: string; title: string; status: 'todo' | 'doing' | 'done' };
  };
}
```

三个细节：

- **路由名直接用 `'GET /tasks/:id'` 这样的字符串**——第 04 章的字面量类型，
  它让"路由名"变成可检查的类型，而不是随手的字符串。
- **没有路径参数时写 `Record<string, never>`，不是 `{}`**。
  `{}` 在 TS 里几乎什么都能赋值（它表示"没有已知属性"），`Record<string, never>` 才真是"一个属性都不能有"。
- **没有请求体时写 `void`**。

### 实现：`keyof` + 索引访问 + 泛型约束

```ts
type Route = keyof ApiRoutes;

/** 把路由的参数、查询、请求体打包成一个对象。 */
type Req<K extends Route> = {
  params: ApiRoutes[K]['params'];
  query: ApiRoutes[K]['query'];
  body: ApiRoutes[K]['body'];
};

declare function request<K extends Route>(route: K, req: Req<K>): Promise<ApiRoutes[K]['response']>;
```

拆开看（复习第 05、06 章）：

| 零件 | 在这里干什么 |
|---|---|
| `K extends Route` | 泛型约束：`K` 只能是路由表里的键，拼错就报错 |
| `ApiRoutes[K]['body']` | **索引访问类型**：从表里取出这个路由的请求体类型 |
| `ApiRoutes[K]['response']` | 取出响应类型，于是返回值类型**跟路由绑定**了 |

关键是**调用点不用写任何类型参数**——`K` 从第一个实参（路由名）推断出来，
`Req<K>` 和 `ApiRoutes[K]['response']` 跟着自动算出来。这是第 02 章的哲学："类型从值推断"。

### 真实报错

**错误 1：路由名打错。**

```text
error TS2345: Argument of type '"GET /task"' is not assignable to parameter of type 'keyof ApiRoutes'.
```

**错误 2：`query` 值写错。**

```ts
request('GET /tasks', { params: {}, query: { status: 'finished' }, body: undefined });
```

```text
error TS2322: Type '"finished"' is not assignable to type '"done" | "todo" | "doing" | undefined'.
```

**这一行就是字面量类型自动生成的枚举**——你一个 `enum` 都没写（也不能写），
但调用点看到的就是"只能填这三个值"。

**错误 3：请求体字段写错。**

```text
error TS2353: Object literal may only specify known properties, and 'name' does not exist in type '{ title: string; }'.
```

**错误 4：把响应当成别的形状用。**

```ts
created.status;   // created 的类型是 { id: string; title: string }
```

```text
error TS2339: Property 'status' does not exist on type '{ id: string; title: string; }'.
```

**这四个错误加起来，就是这个模式的全部价值**：请求体和响应体的形状，
从"文档里的约定"变成了"改一个字就变红的红线"。

### 一个能全程跑通的版本

上面用了 `declare function` 不方便验证。把"网络"换成"内存模拟数据"，这段就是完整可运行的：

```ts
// ── 可运行：api-demo.ts ──
interface ApiRoutes {
  'GET /tasks': {
    params: Record<string, never>;
    query: { status?: 'todo' | 'doing' | 'done' };
    body: void;
    response: { id: string; title: string }[];
  };
  'POST /tasks': {
    params: Record<string, never>;
    query: Record<string, never>;
    body: { title: string };
    response: { id: string; title: string };
  };
}

type Route = keyof ApiRoutes;
type Req<K extends Route> = {
  params: ApiRoutes[K]['params'];
  query: ApiRoutes[K]['query'];
  body: ApiRoutes[K]['body'];
};

// 真实项目里这里换成 fetch()，但类型签名一模一样。
async function request<K extends Route>(route: K, req: Req<K>): Promise<ApiRoutes[K]['response']> {
  console.log(`  -> ${route}`, JSON.stringify(req));
  if (route === 'GET /tasks') {
    const tasks: { id: string; title: string }[] = [
      { id: 't-001', title: '通读第 09 章' },
      { id: 't-002', title: '手写 Result 工具函数' },
    ];
    // 这里的断言是必要的：K 是泛型，TS 无法把 tasks 关联到 ApiRoutes[K]['response']。
    // 换成真实 fetch 之后，这个断言所在的位置就是"运行时校验"该站的位置。
    return tasks as ApiRoutes[K]['response'];
  }
  const title = (req.body as { title: string }).title;
  return { id: 't-003', title } as ApiRoutes[K]['response'];
}

async function main(): Promise<void> {
  // 路由名、query、请求体、响应类型全部自动推导，调用点一个类型注解都没写
  const list = await request('GET /tasks', { params: {}, query: { status: 'todo' }, body: undefined });
  console.log('  取回', list.length, '条：', list.map((t) => t.title).join(' / '));

  const created = await request('POST /tasks', { params: {}, query: {}, body: { title: '写第 09 章' } });
  console.log('  新建：', created.id, created.title);
}

await main();
```

```text
  -> GET /tasks {"params":{},"query":{"status":"todo"}}
  取回 2 条： 通读第 09 章 / 手写 Result 工具函数
  -> POST /tasks {"params":{},"query":{},"body":{"title":"写第 09 章"}}
  新建： t-003 写第 09 章
```

### 最重要的一句提醒：响应类型是"承诺"，不是"保证"

> **`ApiRoutes` 里的 `response` 类型是你手写的。**
> 它描述的是"我以为后端会返回什么"，不是"后端真的会返回什么"。

后端某天把 `status` 字段去掉、改成数字、或者返回 `{ error: 'xxx' }`，
**你的编译器一声不吭**——它在类型层面本来就无从知道。所以必须再加一层**运行时校验**：

```ts
// 用 zod 的写法（本章结尾会推荐你学它）
import { z } from 'zod';

const TaskSchema = z.object({
  id: z.string(),
  title: z.string(),
  status: z.enum(['todo', 'doing', 'done']),
});
type Task = z.infer<typeof TaskSchema>;     // 类型从校验器推导，别手写两遍

const raw: unknown = await res.json();      // 注意：这里一定是 unknown，不是 Task
const parsed = TaskSchema.safeParse(raw);
if (!parsed.success) {
  /* 处理"后端返回的东西不符合约定" */
}
```

**记住这个顺序**：边界处（`fetch`、数据库、命令行、文件）必须校验，
校验之后再交给内部那些"完全靠类型"的代码。
**类型系统管得住代码内部，管不住外部世界**——第 01 章埋的伏笔，现在闭环了。

### 什么时候不该用

- **接口数量很少（三五个）**：直接写 `fetchXxx(): Promise<Xxx>` 更少代码、跳转更好用。
  路由表在规模化时才划算。
- **后端接口天天改**：维护成本可能超过收益。更好的做法是**从后端 schema 自动生成类型**
  （OpenAPI / tRPC / GraphQL codegen），别手写。
- **团队里没人维护这张表**：它会慢慢变成谎言，**比没有它更糟——
  过期的手写类型比 `any` 更危险，因为它看起来是对的。**

**一句话记住它：把"接口约定"从文档搬进类型表，让调用点的请求体和响应体自动对号入座。**

## 9.5 模式五：Builder + 泛型累积类型

### 它解决什么问题

```ts
// ❌ 你可能这么写：5 个可选参数
function createServer(host?: string, port?: number, tls?: boolean, timeout?: number, retries?: number) {}

createServer(undefined, undefined, true, 3000);   // 位置参数，天书
```

改成配置对象好一点，但出现新问题：**构造过程没有任何约束。**

```ts
interface ServerConfig { host: string; port: number; tls: boolean }

const draft: Partial<ServerConfig> = {};
draft.host = 'localhost';
// 中间省略 50 行代码……
draft.tls = true;
// 忘了 port 也照样能往下走，直到运行时报错
```

Builder 模式想让这件事变成：**每加一个字段，类型就长一点；没攒齐就不许收尾。**

> 类比：`Partial<T>` 像一张**空白的乐高说明书**，你随便翻到哪页都行。
> 泛型累积的 Builder 像**一张会自己长大的清单**——勾掉"主机"，
> 那一栏就变实心；全部实心了，"完成"按钮才会亮。

### 术语：类型参数在每步之间传递

核心只有一句：**每一步返回一个新的 Builder 类型，类型参数是"已累积字段"的交叉。**

```ts
interface Shape { a: number; b: string }

class TypedBuilder<TBuilt extends object> {
  readonly #data: unknown;

  constructor(data: unknown) {
    this.#data = data;
  }

  set<K extends keyof Shape, V extends Shape[K]>(
    key: K,
    value: V,
  ): TypedBuilder<TBuilt & Pick<Shape, K>> {   // ← 返回类型带着"新旧合并"
    const prev = (this.#data ?? {}) as Record<string, unknown>;
    return new TypedBuilder<TBuilt & Pick<Shape, K>>({ ...prev, [key]: value });
  }
}
```

拆开那个 `set`：

- `TBuilt` 是"到目前为止已经攒了哪些字段"。
- `K extends keyof Shape` 约束键名（第 05、06 章的招式）。
- `V extends Shape[K]` 约束值的类型——**注意不是 `V extends any`，而是 `Shape[K]`**，
  也就是"这个键该有的类型"。这是整个模式里最精妙的一行。
- 返回 `TypedBuilder<TBuilt & Pick<Shape, K>>`：**把这一步的字段并进累积里。**

调用链就变成 `TypedBuilder<Pick<Shape,'a'>>` → `TypedBuilder<Pick<Shape,'a'> & Pick<Shape,'b'>>`。

### 真实报错

**错误 1：值类型写错。**

```text
error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

**错误 2：键名不存在。**

```ts
builder.set('z', 1);
```

```text
error TS2345: Argument of type '"z"' is not assignable to parameter of type 'keyof Shape'.
```

**错误 3（最有意思的）：没攒齐就想收尾。** `build()` 是这么声明的，注意那个 `this` 参数：

```ts
build(this: TypedBuilder<Shape>): Shape {
  return this.#data as Shape;
}
```

`this: TypedBuilder<Shape>` 的意思是："**只有累积类型已经满足 `Shape` 的 Builder，才配调用我。**"
于是：

```ts
class Wrapper {
  readonly #builder = new TypedBuilder<object>(undefined);

  notEnough(): Shape {
    return this.#builder.set('a', 1).build();   // ← 只攒了 a
  }
}
```

```text
error TS2684: The 'this' context of type 'TypedBuilder<object & Pick<Shape, "a">>' is not assignable to method's 'this' of type 'TypedBuilder<Shape>'.
  Property 'b' is missing in type 'Pick<Shape, "a">' but required in type 'Shape'.
```

**第二行就是全部意义**：`Property 'b' is missing`——"你只攒了 `a`，还差 `b`，不许收尾。"

### 一个必须知道的坑

`this` 参数有个真实限制：**它在链式调用里会失效。**

```ts
// 在类方法里这样写：报错（上面那个例子）
return this.#builder.set('a', 1).build();

// 换成普通函数这样写：不报错
function notEnough(): Shape {
  return builder.set('a', 1).build();
}
```

原因：`set()` 的返回类型被显式声明成 `TypedBuilder<...>`，
TS 处理链式调用时**不会把接收者的实际类型继续传下去**，`this` 参数这第一道检查就被绕过了。
我在 TS 5.9.3 上实测确认了。**这是语言限制，不是你的错。**

所以真实项目里想要"没攒齐就不许用"，我更推荐**更土但更可靠的 `satisfies`**：

```ts
const draft = { a: 1 } satisfies Shape;
```

```text
error TS1360: Type '{ a: number; }' does not satisfy the expected type 'Shape'.
  Property 'b' is missing in type '{ a: number; }' but required in type 'Shape'.
```

一样是"少了 `b`"这一句，而且**没有任何类型体操**，任何人一眼看懂。

### 什么时候不该用

这是全章我劝退最狠的一节。

- **字段少于 5 个、或者都是必填的**：**别用。**
  一个 `interface` + 对象字面量 + `satisfies` 就够了，代码少十倍。
- **你需要"构造过程的中间状态"能被传给别人**：泛型累积的类型会变得极长，
  报错里全是 `TypedBuilder<Pick<Shape, "a"> & Pick<Shape, "b">>`，团队里没人愿意读。
  **报错可读性是真实成本。**
- **编译速度敏感的项目**：这种递归累积的类型参数对检查器不友好，大项目里能明显拖慢 `tsc`。
- **该用它的地方**：你要写一个**给别人用的库**（查询构建器、请求构建器、
  `zod` 那种 schema 组合器），而且**构造顺序真的重要**。业务项目 95% 的情况够不上这个门槛。

**一句话记住它：Builder 的泛型累积让"构造过程"本身有了类型——
但它的报错可读性和编译开销都很贵，只在写库的时候才掏这笔钱。**

## 9.6 模式六：依赖注入 + 结构化类型做测试替身

### 它解决什么问题

你要给业务逻辑写测试，但它依赖数据库。大多数团队的答案是：装一个 mock 框架，
写一堆 `jest.mock(...)`、`vi.fn().mockResolvedValue(...)`，然后是配置文件、类型断言、
和 mock 失效后的诡异失败。

**但如果你用的是 TypeScript，很多时候你不需要 mock 框架。** 你只需要一个对象字面量。
为什么？回到第 00 章那句话：**TS 认形状不认户口本。**

### 做法：业务代码只依赖一个 interface

```ts
export interface Repository<T extends { id: string }> {
  find(id: string): Result<T, RepoError>;
  list(): readonly T[];
  save(item: T): Result<T, RepoError>;
  upsert(item: T): Result<T, RepoError>;
  remove(id: string): Result<T, RepoError>;
}
```

`TaskService` 的构造函数只要求这个接口：

```ts
export class TaskService {
  readonly #repo: Repository<Task>;

  constructor(repo: Repository<Task>) {
    this.#repo = repo;
  }
}
```

**两个细节**：

1. **`service` 内部没有 `new InMemoryRepository()`**，谁用谁传进来——
   这就是"依赖注入"（Dependency Injection）的字面意思：依赖从外面给，不在里面造。
2. **没有构造函数参数属性**（`constructor(private repo: ...)`），
   因为 Node 直接跑 `.ts` 的 strip 模式不支持它（第 07 章）。
   多写两行 `readonly #repo` + 赋值，换来 `node x.ts` 能直接跑，很划算。

### 测试替身：一个对象字面量

项目里 `main.ts` 的 `fakeRepoTest()` 就是完整示范：

```ts
function fakeRepoTest(): void {
  const calls: string[] = [];
  const fake: Repository<Task> = {
    find: (id) => {
      calls.push(`find(${id})`);
      return err(repoError(RepoErrorKind.NotFound, id));
    },
    list: () => {
      calls.push('list()');
      return [];
    },
    save: (item) => {
      calls.push(`save(${item.id})`);
      return ok(item);
    },
    upsert: (item) => {
      calls.push(`upsert(${item.id})`);
      return ok(item);
    },
    remove: (id) => {
      calls.push(`remove(${id})`);
      return err(repoError(RepoErrorKind.NotFound, id));
    },
  };

  const isolated = new TaskService(fake);      // ← 注入假仓库
  const created = isolated.createTask('x-999', '用假仓库建的任务');
  printResult(created, '假仓库 createTask');
  console.log(`  假仓库记录到的调用：${calls.join(' -> ')}`);
}
```

```text
  [OK]   假仓库 createTask -> x-999 待办
  假仓库记录到的调用：save(x-999)
  注意：全程没有行为 mock 库，只有一个对象字面量。
```

**这段代码用到了本章的模式六（依赖注入 + 结构化类型做测试替身）**，
同时它的每个方法都返回模式一的 `Result`——所以假仓库的返回值也必须是那个形状。

**为什么这就够了？** 因为参数类型标注是 `Repository<Task>`，
TS 会检查这个对象字面量是否有全部五个方法、签名是否对得上。
**少写一个方法、参数写错、返回类型写错，全部在编译期报错。**

### 真实报错

**漏实现方法：**

```ts
interface UserRepo {
  findById(id: string): Promise<{ id: string; name: string } | undefined>;
  save(user: { id: string; name: string }): Promise<void>;
}

declare function findUser(repo: UserRepo, id: string): Promise<string>;

const halfFake = { findById: async (id: string) => ({ id, name: 'x' }) };
findUser(halfFake, 'u-1');
```

```text
error TS2345: Argument of type '{ findById: (id: string) => Promise<{ id: string; name: string; }>; }' is not assignable to parameter of type 'UserRepo'.
  Property 'save' is missing in type '{ findById: (id: string) => Promise<{ id: string; name: string; }>; }' but required in type 'UserRepo'.
```

**多余字段反而没问题**（这是结构化类型的"宽进"，第 00 章）：

```ts
const fullFake = {
  findById: async (id: string) => ({ id, name: 'x' }),
  save: async () => {},
  extra: 1,                 // 多出来的字段不影响赋值
};
findUser(fullFake, 'u-1');  // 通过
```

**这就是不用 mock 库的底气**：多的不管，少的报错。

顺带一个常和它出现在同一文件里的报错——`catch` 里是 `unknown`（对照 9.1 节）：

```ts
function parse(text: string): unknown {
  try {
    return JSON.parse(text) as unknown;
  } catch (e) {
    return e.message;
  }
}
```

```text
error TS18046: 'e' is of type 'unknown'.
```

### 什么时候不该用

- **依赖本身就是一个纯函数**：`function formatDate(d: Date): string` 直接 import 就好，
  为它建 interface 是自找麻烦。
- **只有一个实现、且你能确定永远只有一个**。**"未来可能换实现"是经典的过度设计借口。**
  判断标准很简单：**你现在需要测试它吗？** 需要 → 抽接口；
  不需要 → 先用具体类型，等真需要时再抽，改动很小。
- **依赖有几十个方法**：手写假对象会很长。要么用 `Pick<RealRepo, 'findSomething'>` 缩小接口，
  要么承认"这个类太胖了，该拆"。

**一句话记住它：接口是合同，结构化类型是"不看公章只看内容"——
于是测试替身可以是一个普普通通的对象字面量。**

## 9.7 模式七：`satisfies` 操作符（TS 4.9）

### 它解决什么问题

你想要两件**互相冲突**的事：

```ts
const config = { mode: 'dark', retries: 3 };
```

- **要类型检查**：确认 `mode` 只能是 `'dark' | 'light'`，没有拼错。
- **但不想丢掉推断**：`config.mode` 最好就是 `'dark'` 这个具体的字面量类型。

以前只能二选一：

```ts
interface Config { mode: 'dark' | 'light'; retries: number }

const a: Config = { mode: 'dark', retries: 3 };
a.mode;        // 类型是 'dark' | 'light'  ← 具体信息丢了
```

`as const` 也不对，它只管锁死，不管校验：

```ts
const b = { mode: 'drak', retries: 3 } as const;
// b.mode 是 'drak'（推断保留了），但没人检查 'drak' 是不是合法值
```

`satisfies` 就是补上这个缺口的：

```ts
const config = { mode: 'dark', retries: 3 } satisfies Config;
// config.mode 的类型是 'dark'   ← 推断保住了
// 同时它的形状被 Config 检查过  ← 校验也做了
```

> 类比：`: Config` 像**把水倒进固定形状的模具**——出来的一定是模具的形状，细节全被抹平。
> `as const` 像**把水冻成冰**——细节全在，但没人管你是不是倒进了对的杯子。
> `satisfies` 像**拿尺子量一下，但不改你**——量完了，你还是你，但已经确认合格。

### 真实场景

**场景 1：路由表 / 命令表。** 这是项目里的真实代码（`main.ts`）：

```ts
type Handler = (args: readonly string[]) => Result<Task, TaskError>;

const commands = {
  add: (args: readonly string[]): Result<Task, TaskError> => { /* ... */ },
  start: (args: readonly string[]): Result<Task, TaskError> => { /* ... */ },
  done: (args: readonly string[]): Result<Task, TaskError> => { /* ... */ },
  rm: (args: readonly string[]): Result<Task, TaskError> => { /* ... */ },
} satisfies Record<string, Handler>;
```

**它换来了什么？** 看这两行：

```ts
type CommandName = keyof typeof commands;      // 'add' | 'start' | 'done' | 'rm'

function isCommand(name: string): name is CommandName {
  return Object.hasOwn(commands, name);
}
```

如果当初写成 `const commands: Record<string, Handler> = {...}`，
`CommandName` 就变成 `string`，下面这个收窄完全失效：

```ts
if (!isCommand(name)) {
  console.error(`未知命令：${name}`);
  return 1;
}
const handler: Handler = commands[name];    // 这里 name 已收窄成 CommandName
```

**这段代码用到了本章的模式七（`satisfies`）**，它和模式二（判别联合）是绝配：
值这一侧用对象字面量写命令表，类型这一侧用 `keyof typeof` 收窄。
项目的演示输出里能看到这张表的键：

```text
【5】satisfies：命令表既是值也被类型检查
----------------------------------------------------------------
  已注册命令：add, start, done, rm
```

注意输出里**没有 `list`、`stats`**——它们在 `main.ts` 里是显式 `if` 分支。
真实项目里这种"一部分走表、一部分走特判"的混合写法很常见，不用强求统一。

**场景 2：状态机的允许表。** `service.ts` 里那一行：

```ts
export const ALLOWED = {
  todo: ['doing'],
  doing: ['done'],
  done: ['done'],
} as const satisfies Record<StatusKind, readonly StatusKind[]>;
```

`as const` 和 `satisfies` 可以叠加，**而且这是状态机的标准搭配**：

- `as const` 保住字面量，让 `ALLOWED.done` 真的是 `readonly ['done']`。
- `satisfies Record<StatusKind, ...>` 保证**每个状态都列了**——
  你明天给 `TaskStatus` 加一个 `'archived'`，这行立刻报"少了一个键"。

### 真实报错

**错误 1：字面量越界。**

```ts
const bad = { mode: 'drak', retries: 3 } satisfies Config;
```

```text
error TS1360: Type '{ mode: "drak"; retries: number; }' does not satisfy the expected type 'Config'.
  Types of property 'mode' are incompatible.
    Type '"drak"' is not assignable to type '"dark" | "light"'.
```

**错误 2：漏键。**

```ts
const ALLOWED = { todo: ['doing'], doing: ['done'] } satisfies Record<StatusKind, readonly StatusKind[]>;
```

```text
error TS1360: Type '{ todo: string[]; doing: string[]; }' does not satisfy the expected type 'Record<StatusKind, readonly StatusKind[]>'.
  Property 'done' is missing in type '{ todo: string[]; doing: string[]; }' but required in type 'Record<StatusKind, readonly StatusKind[]>'.
```

**错误 3：`satisfies` 不拦"多余属性"（这是它和 `: T` 的一个重要区别）。**

```ts
const withExtra = { mode: 'dark', retries: 3, radius: '8px' } satisfies Config;   // 不报错
const withExtra2: Config = { mode: 'dark', retries: 3, radius: '8px' };
```

```text
error TS2353: Object literal may only specify known properties, and 'radius' does not exist in type 'Config'.
```

两个都不算错，**区别是语义**：`satisfies` 说的是"我这个值满足 `Config`"，
不是"我这个值只能是 `Config`"。所以"带额外调试字段的配置"不会被误伤。

### 四种写法的对照

| 写法 | 类型检查 | 保留字面量推断 | 多出的属性 |
|---|---|---|---|
| `const x: Config = {...}` | 有 | 丢掉，擦成 `Config` | 报错 TS2353 |
| `const x = {...} as const` | 没有 | 保留，且全部 readonly | 保留 |
| `const x = {...} satisfies Config` | 有 | 保留，非 readonly | 保留 |
| `as const satisfies Config` | 有 | 保留，且 readonly | 保留 |

**记忆法：`satisfies` = "检查一下，别改我"。**

### 什么时候不该用

- **你本来就想把类型擦成宽泛的**（比如马上要传进参数类型是 `Config` 的函数）：
  直接写 `: Config` 更清楚。加了 `satisfies` 反而带来"字面量类型传染"——
  某处推断出 `'dark'`，下游需要 `'dark' | 'light'` 时你又要解释半天。
- **TS 版本低于 4.9**：语法不存在，直接报解析错误。**先确认 tsc 版本**（本教程是 5.9.3）。
- **团队里还没人用过**：引入新语法时在 PR 描述里贴一次官方文档链接，
  别让同事在你合并后第一次见到它。

**一句话记住它：`satisfies` 是"检查一下，别改我"——它同时保住了编译器的把关和你的字面量推断。**

## 9.8 什么时候不要玩类型技巧

上面的模式我都给了"不该用"的场景，这里收成一张判断清单。**加新技巧前把四个问题过一遍。**

**问题一：团队里有多少人能读懂它？**

- `satisfies`、判别联合、`Result`：**大部分写过 TS 的人能读懂，放心用。**
- 泛型累积 Builder、递归 `infer`、模板字面量类型：**可能只有你一个人能读懂。**
  规则：**读过的人少于 2 个，就别合并进主分支。**

自测方法很简单：**把这段代码给同事看 30 秒，问他"这段在干什么"。**
答得上来 → 留着；答不上来 → 换笨写法。

**问题二：报错信息还能读吗？**

这是最容易被忽视、也最贵的一条。对比两个报错：

```text
error TS2345: Argument of type 'string' is not assignable to parameter of type 'TaskId'.
```

```text
error TS2345: Argument of type 'Builder<Pick<Schema, "a"> & Pick<Schema, "b"> & Record<never, never>>' is not assignable to parameter of type 'Builder<Schema & { c: boolean }>'.
```

两个都是"类型不对"，但**第一个你能立刻去修，第二个要盯三十秒才找到重点**。
一个类型技巧如果需要你每次都花半分钟读报错，它就在**天天收税**。

**问题三：编译速度还行吗？**

```bash
cd examples
npx tsc --noEmit --extendedDiagnostics
```

看输出里的 `Check time` 和 `Total time`，在加技巧前后各跑一次对比。
大型项目里，几百个深递归泛型能把检查时间从几秒推到几十秒，
**这个代价会落在团队每一次保存文件上。**

**问题四：它防住的那个 bug，真的发生过吗？**

- "**我们线上出过 UserId 和 OrderId 传错的事故**" → 品牌类型立刻上，值。
- "**理论上这种东西可能会传错吧**" → 先记在 issue 里，等真出问题再加。

> **类型安全是拿"复杂度"换"确定性"的买卖。** 单价是团队的理解成本和编译时间。
> 没人会因为你少写一个高级类型而说你不行；但所有人都会因为你的报错看不懂而骂人。

### 三条可以直接抄的底线规则

1. **公共 API（导出给别的模块用的函数）必须有明确签名**，
   类型技巧只能用在其内部实现里；反过来，**别把类型技巧用在公共 API 上**。
2. **一个类型定义超过 5 行就该怀疑**：能不能拆成两步、加个名字？
3. **每个花哨的类型旁边写一行注释说明"为什么需要它"。**
   半年后你会感谢自己——因为那时候你也是"新来的同事"。

**一句话记住它：类型技巧的成本是团队的读代码时间，收益是拦住的 bug 数量——这笔账算不过来时，选笨写法。**

## 9.9 从这份教程到真实项目

学完这章，你已经把 TS 的核心都用过一遍了。接下来是把它搬进你手上的真实项目。
**按这个顺序做，每一步都能当天看到效果。**

### 第 1 步：把 `strict` 打开（半天到两天）

投入产出比最高的一步。在 `tsconfig.json` 里写 `"strict": true`。
**老项目直接开会炸出几百个错误，这是正常的。** 三条实操建议：

- **用 `// @ts-expect-error` 逐个标记**来不及处理的地方（别用 `@ts-ignore`：
  前者在错误消失后会自己报错，逼你回来清理）。
- **不要一次改完。** 按目录分批，每批一个 PR，别搞千行大 PR——没人能 review。
- **项目太大就先只开 `strictNullChecks`。** 它一个人就能拦住现代 JS 里最多的一类 bug。

### 第 2 步：装 ESLint + `typescript-eslint`（半天）

类型检查管"类型对不对"，lint 管"写法好不好"。**两件事，别指望一个工具。**

```bash
pnpm add -D eslint typescript-eslint
```

（`typescript-eslint` 是新版的统一包名，以前要分别装 parser 和 plugin。）

**最少要开这几条规则**：

| 规则 | 拦什么 |
|---|---|
| `@typescript-eslint/no-explicit-any` | 拦住"用 any 麻药止痛" |
| `@typescript-eslint/no-floating-promises` | 拦住忘了 `await` 的 Promise |
| `@typescript-eslint/no-unnecessary-condition` | 拦住多余的空判断 |
| `@typescript-eslint/consistent-type-imports` | 配合 `verbatimModuleSyntax`，自动帮你写 `import type` |

**为什么 `no-floating-promises` 值得单独说**：它需要类型信息（要配 `projectService`），
但它是**唯一能拦住"异步函数忘了 await"的规则**——这种 bug 不报错、测试也常测不出来，
只会在生产环境偶发。

### 第 3 步：在边界处加 zod（一天）

**这一步把 9.4 节那个"承诺 vs 保证"补上。**

```bash
pnpm add zod
```

只做一件事：把所有**外部数据入口**包上校验——`fetch` 响应、`JSON.parse` 结果、
环境变量、从数据库读出来当业务对象用的行、`process.argv`、表单输入。

```ts
import { z } from 'zod';

const TaskSchema = z.object({
  id: z.string().min(3),
  title: z.string().min(1),
  status: z.enum(['todo', 'doing', 'done']),
});
type Task = z.infer<typeof TaskSchema>;    // 类型从校验器推导，别手写两遍

// 边界：raw 是 unknown，出来的时候就是 Task 了
const raw: unknown = JSON.parse(text);
const task = TaskSchema.parse(raw);
```

**注意 `z.infer`**：它让"校验规则"成为**唯一的事实来源**。
你以前是"写一遍类型 + 写一遍校验，然后祈祷两边一致"，现在只有一份了。

### 第 4 步：写一个 `Result` 工具（半天）

**别一上来就全项目改。** 先挑**一个**业务流程（比如"注册用户"），
它的失败路径是**可预期的**（邮箱重复、密码太弱、验证码过期）：

- 把这个流程的返回类型从 `Promise<User>` 改成 `Promise<Result<User, RegisterError>>`；
- 在调用点用 9.1 节的"早返回"处理。

跑一周看团队反应：觉得"错误处理终于不用猜了" → 推广；
觉得"到处 `if (!r.ok)` 比 `try/catch` 还烦" → **那就退回去**，只在最核心的一两个流程里保留。

**这一步的目的不是"证明 Result 更好"，而是让你亲手感受它的甜和苦。**
你不实际用一次，看再多文章也不知道自己项目适不适合。

### 第 5 步：给公共 API 显式写返回类型（持续）

几乎零成本，收益稳定。

```ts
// ❌ 推断出来的返回类型：改实现时可能悄悄变宽
export function getUser(id: string) {
  return db.users.findOne({ id });
}

// ✅ 显式声明：改实现时如果破坏了约定，编译器立刻报错
export function getUser(id: string): Promise<User | null> {
  return db.users.findOne({ id });
}
```

为什么？因为**推断出的类型是"实现的副产品"**。你在函数体里改一行 `return`，
导出的类型就可能跟着变，而**下游的报错会出现在别人的文件里**——那个人会一脸茫然地来找你。

**规则**：`export` 出去的函数、类的 public 方法写返回类型；内部局部函数不用写
（第 02 章的"能推断就不写"依然成立）。

### 下一步学什么（按性价比排序）

| 学什么 | 为什么现在学它 | 建议投入 |
|---|---|---|
| **zod**（或 valibot / arktype） | 第 3 步已经用上了。运行时校验 + 类型推导的事实标准 | 1~2 天 |
| **React + TS 的类型** | `useState<T>`、props、`children`、事件类型、泛型组件。前端岗必考 | 3~5 天 |
| **tsconfig 项目引用（`references`）** | monorepo 拆包、增量编译，项目一大就绕不开 | 2~3 天 |
| **`tsd` 或 `expect-type` 类型测试** | 给"类型本身"写测试。写库、写公共工具时必需 | 半天 |
| **官方 Handbook 的 Mapped / Conditional 章节** | 第 06 章是"够用版"，这是完整版。想读 zod、tRPC 源码就得看 | 持续 |

**我建议的顺序：先 zod，再 React + TS。**
zod 解决的是"你每天已经在痛的问题"，学完当天就能用上；
React + TS 更像"换个技术栈重新学一遍类型"，值得慢慢来。

### 最后一句

这份教程从头到尾只想让你记住一件事：

> **类型不是写给别人看的文档，是让编译器替你记住那些你记不住的东西。**

`Result` 记住失败的形状，判别联合记住状态的互斥，品牌类型记住 ID 的归属，
`satisfies` 记住配置的字面量。**你脑子里少存一样东西，就能多放一样真正重要的东西。**

## 9.10 动手练习

五道题，难度递增。**每题都要求"先写错，看报错，再写对"**——这是本教程最值钱的动作。

### 练习 1（热身，20 分钟）：给 `Result` 加两个组合子

在 `examples/project/types.ts` 里加上：

```ts
export function andThen<T, U, E>(r: Result<T, E>, f: (value: T) => Result<U, E>): Result<U, E>;
export function orElse<T, E, F>(r: Result<T, E>, f: (error: E) => Result<T, F>): Result<T, F>;
```

要求：

1. 实现它们，**只用 `if (!r.ok) return ...` 早返回**，不许写 `try/catch`。
2. 用它们把"`taskId(raw)` → `service.createTask(id, title)`"串成一行。
3. **故意把 `orElse` 里失败分支的 `return` 写错**（比如返回 `r.error` 而不是 `r`），
   看看 TS 报什么错，把报错原文抄进注释。

### 练习 2（半小时）：给任务加一个 `archived` 状态

1. 往 `TaskStatus` 里加一支 `{ readonly kind: 'archived'; readonly archivedAt: string }`。
2. **先别改任何其他地方**，跑一次类型检查：

   ```bash
   cd examples
   & 'C:\Users\admin\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe' '.\node_modules\typescript\bin\tsc' --noEmit --pretty false --strict --target es2022 --module nodenext --moduleResolution nodenext --allowImportingTsExtensions --lib es2023 'project/main.ts'
   ```

   数一数**编译器帮你找到了几处需要改的地方**。
3. 把它们全部改对（`describeStatus`、`nextStatus`、`ALLOWED`、`stats` 都会报错）。
4. 回答一个问题：**如果当初用的是 `status: string`，你要靠什么才能找全这些地方？**

### 练习 3（一小时）：把状态机改成"可撤销"

给 `TaskService` 加一个 `reopenTask(id)`：允许 `done → doing`（任务做错了要重开）。

要求：

1. **先只改 `ALLOWED` 表**，看会发生什么：`nextStatus` 里 `case 'doing'` 能处理这条新路径吗？
2. 处理一个真实问题：从 `done` 回到 `doing` 时，`startedAt` 怎么办？`finishedAt` 该不该清掉？
   **注意类型上 `doing` 这一支不允许有 `finishedAt`**——写
   `{ kind: 'doing', startedAt, finishedAt }` 会报什么错？
3. 用 `Result` 表达失败：对一个 `todo` 状态的任务调用 `reopenTask`，应该返回什么错误？

### 练习 4（两小时）：给项目接上真实的持久化

现在数据全在内存里，进程一退就没了。改成 JSON 文件持久化：

1. 定义 `interface TaskStore`，提供 `load(): Task[]` 和 `persist(tasks: readonly Task[]): void`。
2. 写一个 `FileTaskStore`，用 `node:fs` 读写 `project/tasks.json`。
3. **关键要求**：从文件读出来的是 `unknown`（9.4 节！），你必须写**运行时校验函数**，
   逐条检查每个对象的形状，非法数据返回 `Result` 的失败分支。
   **不许写 `JSON.parse(text) as Task[]`。**
4. 写一个 `MemoryTaskStore`（就是现在这个），让 `main.ts` 通过**依赖注入**选择用哪个。
5. 自测：手动把 JSON 里的 `status` 改成 `{"kind":"doing"}`（故意漏掉 `startedAt`），
   看程序是**优雅报错**还是崩掉。

### 练习 5（半天，挑战题）：给命令行做真正的参数解析

现在命令行是 `add <id> <标题>` 这种位置参数。升级它：

1. 支持 `--title="买牛奶" --id=t-001 --status=todo` 这样的**具名参数**。
2. 每个命令支持的参数**不一样**（`add` 有 `--title`，`list` 有 `--status` 筛选）。
   用 9.4 节的路由表思路，给每个命令建一张"参数表"。
3. 未知参数要报错，并且**报错信息里列出这个命令支持哪些参数**。
4. `--status` 只允许 `todo` / `doing` / `done`，别的值在类型层面和运行层面都要拦住。
5. 加分项：`--help` 的输出**从参数表自动生成**，不要手写。

**这题的难点不在类型，而在"运行时的解析结果怎么安全地变成类型"。**
你会不可避免地遇到：解析出来的是 `Record<string, string>`，
而你需要的是每个命令各自精确的参数类型。
**那个"卡住"的瞬间，就是这份教程想让你走到的地方。**

## 9.11 本章小结

### 七个模式，各一句话

1. **`Result<T, E>`**：把"会失败"写进返回值，让调用者不用猜、不用 `try`。
2. **判别联合 + 状态机**：让合法的组合是唯一写法，非法状态连写法都没有。
3. **Branded Type**：把 `string` 的语义搬到类型上，配合唯一构造器守住入口。
4. **类型安全 API 层**：用一张路由表绑住请求体和响应体，但别忘了响应只是"承诺"。
5. **Builder + 泛型累积**：让构造过程也有类型，但只在写库时才值得掏这笔钱。
6. **依赖注入 + 结构化类型**：接口是合同，"不看公章只看内容"，假实现可以是对象字面量。
7. **`satisfies`**：检查一下，别改我。

**第 3 步的那个点，就是工程能力。** 它没有标准答案，只能靠做过几次才长出来。
